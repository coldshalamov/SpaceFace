## Findings (ranked)

### F1 — The stepped journal publish can never commit across presents: the consumer's own fallback dooms every suspended attempt

- evidence: `presentationRunner.js:875` (`rebuildJournalIfNeeded` pumps the stepped job per present, publishing ≤`JOURNAL_REBUILD_SLICE_ROWS=512` rows via `getLastRebuildRecordCount` deltas at :801-806) → `:898` `populateJournalFrame` mints `journalValid = !(needsRebuild())` — `rebuildRequired` stays true the whole suspension (:841-842) → `registry.renderUpdate` (:903) → `renderer.js:23250` `consume()` → `presentationPublisher.js:151` `journalValid === false → fallbackFromState` → `:81-84` calls `requestRebuild(journal, 'presentation-journal-invalid')` unconditionally → `presentationJournal.js:247` `if (rebuildInProgress) rebuildInvalidatedDuringSteps = true` — no condition on the caller → next `publishIter.next()` hits the `%64` bail at `presentationJournal.js:583-585` → `'invalidated'` → `presentationRunner.js:821-824` counts a strike → at `JOURNAL_REBUILD_INVALIDATED_MAX=3` → `syncJournalRebuildEscalation` (:744-755) runs `collectJournalPresentationEntities` (sync O(entities)) + `rebuildFrom` (full sync drain) inside `presentLastCompletedSnapshot`, i.e. inside the presented frame.
- mechanism: any rebuild that publishes more rows than one present's 512-row debit is mathematically incapable of committing stepped. The publish suspends at the budget boundary; the very next presented frame's fallback chain re-requests the rebuild the journal already has in flight, flagging it doomed before it resumes. Each suspended frame also pays the full fallback price inside `drawPreparedFrame`: `world.rebuildFromEntities` (`presentationWorld.js:804-818` — `clear()` retires all active slots then `allocateEntity` per live entity), `result.rebuilt = true` → `_rebindPresentationMeshes()` (`renderer.js:23251` → `20515-20522`, O(_meshes) with `resolveWorldPresentationEntity` per mesh) and the fence repack `packPresentationWorldToFence` (:23262-23276, gated by `publication.rebuilt === true`). So a >512-row rebuild = up to 3 doomed attempts, each paying O(entities) collect + O(slots) mirror rebuild + O(meshes) rebind + repack per suspended frame, followed by the atomic sync drain the entire stepped machinery exists to prevent — strictly worse than the pre-stepped single atomic rebuild. Triggers are in-flight-real: ring overflow, `recordDestroy` during kill storms (`:361-` always flags — correctly), `entity:spawnRequest` cohorts (spawn of an out-of-set entity flags at :328), and the `requestPresentationRebuild` bus events (`coreSystem.js:425` undock-resume, `:253-264` save/game/relocate). Dense sectors publish well over 512 rows, so the stepped path is dead code exactly when it would matter — the deterministic in-flight hitch class this wave was built to remove.
- the flag itself is correct — a mid-publish `clearRetained` corrupts the in-flight range; committing a truncated set would drop entities off the mirror. The flaw is purely that the consumer re-requests a rebuild that is already in progress.
- fix sketch (minimal): add `getRebuildInProgress: () => rebuildInProgress` to the journal API (`rebuildInProgress` stays true while the generator is suspended — it clears only in the `finally` at :587-590), then gate the publisher's request: `presentationPublisher.js:82` → `if (journal.getRebuildInProgress?.() !== true) requestRebuild(journal, reason);`. The mirror still rebuilds from live entities every suspended frame (correctness backstop preserved), foreign `requestRebuild` callers still invalidate a genuinely stale publish, and the stepped publish finally commits across presents. Companion (optional): publish on the same 4 ms wall-clock debit the collect leg already uses (`:773`) instead of a 512-row cap — `publishSpawn` is a cheap ring append, so most rebuilds would finish inside one present and the fallback frames disappear entirely.
- effort: S (gate) / M (gate + wall-clock publish). magic-frame impact: H — removes the only mechanism that can still land a multi-ms atomic span inside presented frames during churn, and it converts every qualifying rebuild from "sync brick + wasted rebuilds" into spread work. risk: medium — touches the presentation-critical consume path; needs a focused test that a mid-flight publish commits under steady writes and that a doomed attempt (foreign write) still escalates to sync.

### F2 — In-set suppression drops one-shot VISUAL writes: a `ship:appearanceChanged` during a suspended publish is lost, not deferred

- evidence: `presentationJournal.js:390-399` (`recordCoalescible`) and `:253-279` (`prepareRecord`) — suppressed writes flag the attempt only when `kind === 'destroy' || entityId === 0 || !rebuildSourceIds.has(entityId)`. `recordVisual` is `recordCoalescible(VISUAL)` (:463-471); its only driver is the one-shot `ship:appearanceChanged` listener → `markEntityVisualChanged` (`coreSystem.js:249,226-231`).
- mechanism: the W85 narrowing assumes suppressed writes "re-derive on that entity's next write" — true for transforms (per-tick stream), false for visuals. A suppressed visual write produces NO record; the entity's spawn row already captured publish-time visual state, so a `recordVisual` landing between that entity's publish row and the commit is lost permanently — the mirror keeps the old appearance until an unrelated record or a fresh rebuild arrives (which, per F1, means the sync escalation window). The lod lane's F3 documented the sibling case for transform/pose staleness between collect-read and publish; this is the distinct suppressed-during-publish loss mode: no stale row, no row at all — and unlike a pose, an appearance change does not re-emit on the next tick.
- fix sketch: add `kind === PRESENTATION_JOURNAL_KINDS.VISUAL` to the flag clause in both suppression early-outs (visual writes are rare enough that re-flagging cannot re-import the rebuild-storm class the narrowing killed), or persist a `lostVisualEntityIds` set during suspension and re-emit those entities' visual records at commit. The lod-F3 read-set-membership fix would also cover this case if it keyed on write-time rather than read-time.
- effort: S. magic-frame impact: M — a stale appearance is a visible stand-in-grade defect (wrong material/hull on screen), though the window needs a suspended publish, i.e. it mostly co-occurs with F1's blast radius. risk: low-medium — flagging visuals re-dooms attempts on appearance storms; bounded by the 3-strike escalation.

### F3 — `_flushMeshReleasePending` is not batch-depth-gated: async recook sweeps split the union walk (verified safe, note-grade)

- evidence: `renderer.js:20216-20221` — `_meshReleaseBatchEnd` decrements depth and flushes only at 0, but `serviceRenderMeshResidency` (:2024-2030) calls `_flushMeshReleasePending()` unconditionally every frame. Two batch scopes span `await`s: the live-sector leftover sweep (:12318-12344, `await yieldLiveSectorGpu()` at :12336) and the jump departure sweep (:14825-14844, `await providerYield()` at :14839). While those are suspended, presented frames flush the accumulating pending set early.
- mechanism: a mid-batch flush drains a partial set, so one sweep's intended single 5-registry union walk becomes one walk per presented frame it overlaps. Correctness holds: `releaseMeshSet` clears only `rec.mountMesh === mesh` refs (`shipMicroMotion.js:2292-2297`), the clear is idempotent, and the next per-entity update re-scans on `rec.mountMesh !== mesh` (:1727), so even a rebind-before-flush self-heals within a frame. The deferred pin's only cost is ≤1 frame of extra reachability for detached trees plus the split walks.
- fix sketch: none required; if the split walk is ever worth reclaiming, gate the service flush on `_meshReleaseBatchDepth === 0` — but note that trades a bounded per-frame pin for an unbounded pending set across a long async sweep, so the current behaviour is arguably the better design. Documented, not actionable.
- effort: n/a. magic-frame impact: L. risk: n/a.

### F4 — `_syncWorldPresentationTableMeshes` re-costed under the unforced second compose: calculus unchanged

- evidence: `renderer.js:22759-22832` — gated on `fieldVersion/originSeq/count` and `dressingVersion/originSeq/count` before the poseRow closure even exists (:22778); steady frames skip entirely; dirty-journal path (`field.dirtyPoseIds`) walks only journaled ids (:22805-22809); the full `field.rocks`/`dressing.rows` walk fires only on `originSeq` rebase or pre-journal tables (:22794-22801).
- mechanism: the prompt asked whether the now-unforced second compose changes the deferred calculus — it does not. The compose's cost is the DFS visit itself (independent of what these pose writes do), and the table sync's residual atomic span is the per-rebase full walk: ~O(rocks+rows) scalar `position.set`/`rotation.y` writes plus `updateMatrix()` only on frozen roots (:22791). At dense-field scale that is a bounded sub-ms pass once per origin shift, not per frame. It also can't be sliced mid-frame without presenting a split-origin field, so the atomic placement is load-bearing.
- fix sketch: none — keep as monitored residual. If origin rebases ever prove hot, a two-phase rebase (fence-space row cache) belongs in a dedicated wave, not a pacing tweak.
- effort: n/a. magic-frame impact: L. risk: n/a.

## Lane hunts — resolution

- (a) pending-release flush ordering: **clean.** `_unbindPresentationMesh` still runs `releaseEntityMesh(id)` ×5 synchronously (:20269-20275); only the identity-keyed straggler walk defers to the per-frame flush (:20282-20284). No live driver can address a dead-keyed record, so no motion write can land on a disposed node inside the ≤1-frame window — identical observable semantics to the old immediate-null path, plus the self-healing `mountMesh !== mesh` rescan covers even the exotic rebind case. Nil finding beyond F3's note.
- (b) nested batch scopes: **flush order proven.** `_meshReleaseBatchEnd` flushes only at depth 0 (:20216-20220), so an inner end can never release the shared pending Set while an outer scope mutates it; the per-frame service flush CAN fire mid-async-batch (F3) but the pending Set is write-only from the scopes' side — `flush` nulls it before `releaseMeshSet` runs (:20224-20226), so a mid-flush `add` lands in a fresh Set, never an in-iteration one. No release-ever-escapes-live-scope hazard. Residual = F3.
- (c) remaining private-clock per-frame walks in the service chain: enumerated — `drainDespawnDisposeQueue` (2 ms deadline + count-scaled cap + 2-skip ledger, :1891-1932), `driveProtectedFirstFlightDrain` (4 ms or paced-spend gate, :1940-1969), `_cacheLeaseIter` drain (4 ms + paced gate, :2286-2307), `_arrivalRosterIter`, `enqueueHoldExemptMeshBuildsSliced`/`drainDeferredEnterSlice` (4 ms beats, :2062/:2081/:2183), hold-exempt `_drainMeshBuildQueue` (cap sized to remaining hold frames, :2092-2103). All bounded; `_syncWorldPresentationTableMeshes` = F4.
- (d) journal rebuild suspended across presents: **F1** (doom loop) and **F2** (suppressed one-shot visuals). Starvation verdict: bounded — `acknowledgePresentedJournal` is correctly gated on `!needsRebuild` (:857-859), and the fallback mirror keeps presentation current each suspended frame (the mirror is fresh; only the journal commit is pending); the 3-strike sync escalation guarantees termination. The starvation that exists is inverted — the machinery starves ITSELF of commits via the consumer's re-request.
- (e) atomic registry/queue drains ranked by worst-case rows per call inside a presented frame: (1) **F1 fallback chain** — `collectJournalPresentationEntities` O(journaled entities) + `world.rebuildFromEntities` O(active slots + entities) + `_rebindPresentationMeshes` O(_meshes) + `packPresentationWorldToFence` repack — unbounded, per suspended frame, plus the terminal `syncJournalRebuildEscalation` O(entities + journal rows); (2) `_flushMeshReleasePending` 5 × O(registry records) when pending non-empty (:20223-20232) — record maps are pruned to live ids by `_pruneMotionTrackerRecords`, so ≈O(active entities); (3) `settleRebuildBridges` O(_rebuildBridges) (:1999-2022); (4) `drainDespawnDisposeQueue` bounded slice; everything else is iterator/cadence-bound per hunt-(c).

## Bottom line

Not saturated. **F1 is the headline**: the W85 stepped journal rebuild is end-to-end self-defeating — its own consumer re-requests the in-flight rebuild every suspended frame, so every publish longer than one 512-row present burns up to 3 doomed attempts (each paying the full O(entities)+O(meshes)+repack fallback chain) and then lands the sync atomic drain the machinery exists to remove. The fix is a ~10-line gate on `rebuildInProgress` in `fallbackFromState`, optionally plus a wall-clock publish debit. F2 closes a one-shot-visual loss window that mostly co-occurs with F1. F3/F4 are verified-safe notes. Golden `892f88c9` and zero-degradation are untouched by everything above.
