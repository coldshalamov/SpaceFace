# wave86 audit — boot-loading lane

- **lane**: boot-loading (frozen/stalled loading screens, un-paced work inside shell-visible frames)
- **audited head**: `devin/1791064509-perf-w60` @ `20c4f0e38` (W85 commit) — NOT master
- **saturated**: `false` — legal contract-preserving improvements remain (F1, F2, F4)

## Findings (ranked)

### F4 — `reattachResidentGpuMeshes` re-sweeps the whole mesh set synchronously every loading-shell frame

- **Evidence**: `src/render/renderer.js:2032-2043` — under `_sessionRecookKeepGpu === true && mode === 'loading'`, `serviceRenderMeshResidency` calls `reattachResidentGpuMeshes(owner)` on **every presented shell frame**, then returns early. `reattachResidentGpuMeshes` itself (`:1783-1861`) iterates **all** `owner._meshes`, calls `resolveWorldPresentationEntity` per row, calls `owner._bindPresentationMesh(entity, mesh)` (:1816) for every matched row — and `_bindPresentationMesh` (`:20151-20200`) is not cheap: `stableMeshKeyForEntity`, `stampCanonicalSurfaceProgramKeys` guard check, `lanes.reserve`, `world.bindMesh`, matrixAutoUpdate freeze + `updateMatrix()`. When any mesh fails direct resolution, `stableEntityFor` lazily builds `stableIndex` via `collectMeshPresentationEntities(state)` (`:1794-1800`) — an O(entityList) census **rebuilt per call**. The batch wrapper (`:1836-1859`) merges only the *release* walks; the sweep itself is un-sliced.
- **Mechanism**: during the same-sector keep-GPU restore, `mode === 'loading'` holds for the whole shell — the shell's own presenter loop pays O(meshes) + per-row bind work each frame (O(entities) more whenever a stamped miss exists). This is the loading screen stalling on itself: progress/spinner frames contend with a full world rebind pass that is almost entirely idempotent re-attachment. On a restored sector with a large kept set this is the frozen-loading-screen signature this lane exists to kill.
- **Fix sketch**: keep the sweep, run it only when it can change state — gate the per-frame call on `_meshesVersion`/`entityList` generation/enterSerial deltas (or a `_reattachResidentDirty` set by restore/queue paths), or drive it as a Steps twin pacing ~N rows per shell frame with the same verdicts. The four one-shot call sites (`:11627`, `:16695`, `:17059`, `:17130`) stay synchronous — they run once per transition, not per frame. Mid-loading rekeys are still caught because restore/spawn paths bump the same version counters the gate would read.
- **Effort**: M (correct change detector). **Magic-frame impact**: H. **Risk**: M — must not starve genuinely-new rekeys; a version gate keyed on the entity table + mesh set covers it, but a missed invalidation leaves restored entities mesh-less until reconcile.

### F2 — stepped journal rebuild is doomed by *any* suppressed write during collect, so under write load it always escalates to the atomic sync rebuild it replaced

- **Evidence**: `src/core/presentationRunner.js:780-788` — after each ≤4 ms collect slice completes, `suppressedNow > job.suppressedAtStart` discards the job and `++journalRebuildInvalidations`; 3 strikes → `syncJournalRebuildEscalation` (`:744-755`) — the fully synchronous `collectJournalPresentationEntities` + `rebuildFrom` inside one present. Meanwhile `src/core/presentationJournal.js:253-262` (`prepareRecord`) and `:390-399` (`recordCoalescible`) bump `suppressedCount` for **every** write while `rebuildRequired` — including in-set transforms that the publish phase would absorb.
- **Mechanism**: the collect window spans multiple presents under any write load; ordinary flight emits transform writes every tick, so a multi-present collect almost always sees `suppressedCount` climb → doom → re-collect → doom → atomic escalation after 3 wasted attempts. The stepped path only ever completes on quiescent worlds — precisely the scenes that didn't need pacing. The fixable part: in-set suppressed writes are absorbed by the publish's live `fillPose(entity)` read at record-write time (`:342-349` via `publishSpawn`), and suppressed spawns/transforms of entities that stay out of the final set self-heal post-commit via `transform-without-spawn` → `requestRebuild` (`:263-277` order/identity early-outs force it). The one genuinely dangerous case is a suppressed **destroy** for an id that lands in the final collect set (alive at row-visit, dead before commit): its spawn gets published, the destroy is lost, the entity never writes again → zombie spawn with no self-heal.
- **Fix sketch**: instead of a count delta, record suppressed `(entityId, kind)` pairs in a small Set while the collect runs (writes are already dropping — an id-pair add is cheap); when the collect finishes, doom only if any suppressed *destroy* names a collected id, or any suppressed write names an id neither in the set nor re-collectable (conservative: any destroy; out-of-set spawns/transforms can be tolerated if you accept the self-healing follow-up rebuild). Everything else rides the publish's live re-read, identical output.
- **Effort**: M. **Magic-frame impact**: M-H — the escalated atomic collect+publish inside one presented frame is exactly the brick W85 was built to remove; under load it still lands. **Risk**: M — the doom is conservative-for-correctness today; the refinement must prove each absorbed class (documented above) before relaxing it.

### F1 — `updateMatrixWorldSteps` lacks the vendored `sfMatrixFrozen` prune; the *unforced* call recomputes traversal over every frozen subtree

- **Evidence**: `src/render/staticChildMatrices.js:168-173` — the child-push leg pushes every base `updateMatrixWorld` child (and calls overridden children atomically at :171) with **no** `sfMatrixFrozen` check; compare `vendor/three.module.js:137-141` (`!force && child.matrixWorldNeedsUpdate === false && child.userData.sfMatrixFrozen === true → continue`). The only unforced site: `src/render/renderer.js:22966-22972` — `yield* updateMatrixWorldSteps(this.scene)` in `_publishOpeningFirstPictureSteps`, whose own comment says "an unforced walk recomputes exactly those subtrees" — true for the vendored walk, false for the twin, which walks (but doesn't compose) the entire frozen set. Called twice per settle pass × up to 8 passes = up to ~16 whole-scene traversals during `prepareOpeningFirstPicture`.
- **Mechanism**: frozen subtrees (packaged stations/asteroids — the deepest trees in the scene, frozen precisely so compose walks skip them) are traversed anyway: stack push/pop + flag reads per node, and overridden children (`child.updateMatrixWorld !== base`) get their **whole subtree called atomically** at push — under `!force` the vendored loop would have skipped them at the parent. Output is identical (compose only fires on `matrixWorldNeedsUpdate || entryForce`), so this is pure traversal waste inside the most latency-critical boot loop — pacing doesn't shrink the work, it just spreads it, lengthening the settle wall-clock.
- **Fix sketch**: in the child loop, before the overridden-child check, skip `!childForce && child.matrixWorldNeedsUpdate === false && child.userData.sfMatrixFrozen === true` — mirrors vendored :139-140 bit-for-bit, including skipping overridden children the way the parent-level `continue` does. Forced callers (`:11177`, `:22940`, `visualFactory.js:3858`, `visualOverrides.js:923`) unaffected — `force === true` never takes the prune.
- **Effort**: S. **Magic-frame impact**: M (bounded waste on the boot path; ~×scene-node-count traversal per publish leg). **Risk**: L — vendored-parity predicate; the freeze pass itself (`freezeStaticChildMatricesSteps` :77-112) is untouched.

### F3 — stale `drainCensus` closure post-recook writes a superseded census onto `state.render` before the plan-identity guard can bail

- **Evidence**: `src/render/renderer.js:23937-23959` — the zero-refusal continuation captures `censusIter = this._openingFirstDrawIdentityIter` in a closure and schedules itself via `scheduleGap` chains; the recook reset (`:17060-17110`) clears `this._openingFirstDrawIdentityIter` and `_openingFirstDrawIdentityResult` but **not** `_openingFirstDrawDiagnosticsDeferred`, and nothing invalidates the in-flight closure. On completion it calls `persistAndFinish` (`:23905-23923`), which writes `state.render.openingFirstDrawIdentityCensus = identityBefore` **unconditionally** at :23906 — the plan-identity bails only exist *inside* `_finishOpeningFirstDrawDiagnosticsSteps` (:24090, :24164), i.e. after the stale census already landed. It also re-sets `_openingFirstDrawDiagnosticsDeferred = true` and mints a second diagnostics iterator while the stale one's `finally` (:24212) can clear the flag out from under it.
- **Mechanism**: a recook landing mid-drain produces: a few-tick window where `openingFirstDrawIdentityCensus` holds the *pre-recook* sector's identity map (consumed by external probes/witness scripts; the in-place validation block at :23977+ is gated off by the deferred flag so nothing in-engine reads it), plus duplicate deferred iterators and a flag that clears early. Diagnostic-only, self-correcting once the new arm's own persist overwrites — but it's a torn write with an available guard.
- **Fix sketch**: recook reset clears `_openingFirstDrawDiagnosticsDeferred` and bumps a census mint-epoch the closure checks before `persistAndFinish` (or `persistAndFinish` itself re-verifies `armedPlan === state.render.openingSubmissionPlan` before stamping — one line, mirrors the generator's own bail).
- **Effort**: S. **Magic-frame impact**: L (diagnostic-only; small wasted closure steps post-recook). **Risk**: L.

### F5 — a suppressed in-set transform landing *after* its spawn row was published leaves a stale committed pose until the entity next writes

- **Evidence**: publish-phase suppression at `src/core/presentationJournal.js:392-399` returns 0 for in-set ids without invalidation (correct — the id set is finalized); but an entity whose transform is suppressed *after* `rebuildFromSteps` already wrote its spawn row keeps the publish-moment pose forever unless it writes again — `poseChanged` (`:104-114`) only emits on pos/rot deltas vs `prevPos`, so a settled entity never re-records.
- **Mechanism**: a world object displaced once mid-publish renders at its pre-move pose indefinitely — a persistent positional misplacement for a still object near rebuild windows (restores/enters). No pop-in/hitch; pure correctness-of-presentation residue.
- **Fix sketch**: track suppressed in-set ids during the publish leg (same Set F2 wants for collect); on `commitJournalRebuild` replay them through `recordTransformIfChanged`-equivalent writes — bounded by the suppressed count, lands in the same commit tick.
- **Effort**: M. **Magic-frame impact**: L-M. **Risk**: M — replay must re-check liveness/eligibility and stay under the commit's row budget.
