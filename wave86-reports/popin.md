## Ranked findings

### F1 — Publisher consume fallback rebuilds the whole presentation world every presented frame while the stepped journal rebuild is suspended — presentationPublisher.js:81-96 (`fallbackFromState`), :126-205 (`consume`), presentationWorld.js:804-822 (`rebuildFromEntities` → `clear()` at :788-802), renderer.js:23250-23252

**Mechanism.** While `rebuildJournalIfNeeded`'s stepped rebuild is in flight, `presentationJournal.needsRebuild()` stays true, so `populateJournalFrame` stamps `journalValid=false` (presentationRunner.js:840-855) and `consume()` takes `fallbackFromState` every presented frame: `collectJournalPresentationEntities(state)` (O(live entities + ledger/dressing sources)) + `world.rebuildFromEntities` (clear → retire every active slot → allocateEntity per entity, O(capacity+entities)) → `publication.rebuilt=true` → `_rebindPresentationMeshes()` walks the whole `_meshes` map and re-binds every bound mesh (renderer.js:20515-20522 → `_bindPresentationMesh` at 20150 is itself a heavy per-mesh bind: material policies, batch counters, release-pending bookkeeping) → `snapshotNeedsPack` true → `packPresentationWorldToFence` O(active). So each presented frame inside the suspension window pays O(entities) + O(meshes) + O(active) — the exact whole-set drain the stepped rebuild exists to remove — and it fires precisely under the stress the rebuild responds to (dense-write invalidation storms, where the window is longest). The design comment at presentationRunner.js:715-723 acknowledges the fallback exists during suspension; the residual is its per-frame cost, not its presence.

**Fix sketch.** Gate the fallback by change, not by frame: rebuild the world only when a new completed tick was consumed (`completedTickCount > 0` flows through `presentLastCompletedSnapshot` → presentationFrame) or an entity-membership epoch moved; identical-tick presents can re-pack the fence from the unchanged world instead of clear+realloc. Alternative: diff-patch the world by id (retire stale ids / allocate new ids / applyTransform on survivors) instead of `clear()`+realloc — preserves the world as a live mirror without the slot-churn that forces the renderer's full mesh rebind; then `_rebindPresentationMeshes` can narrow to the changed-id set (spawnedSlots-style). All static, all under the existing consume() contract — the world stays the authoritative mirror during suspension either way.

**Effort:** M. **Impact:** H (the dominant remaining whole-set presented-frame drain; worst case = every frame for K frames under invalidation pressure at station-scale entity counts). **Risk:** M — the world must stay identical under both paths; a diff-patch bug manifests as stale slots, so land the tick-gate first (safe: same world reused verbatim) and the diff variant second.

### F2 — `prepareAuthoredVisualPipelines`' synchronous material-policy prefix is undebited contiguous work inside every commit continuation — partsLibrary.js:8377-8384

**Mechanism.** Every boundary commit awaits `prepareAuthoredVisualPipelines` (ship :9231 via `prepareAuthoredShipVisualPipelines`, place :4236, cargo :3231, packaged-body visualFactory.js:4365, packaged-prop visualOverrides.js:1178). An async function's body runs synchronously to its first await, so the four whole-subtree traverses at 8378-8383 — `configureRealtimeCanopyMaterials`, `configureTransparentSinglePassSurfaces`, `canonicalizeAuthoredProgramState`, `mountCanonicalProgramSpecimens` — execute contiguously inside the calling commit continuation, with no yield between them and no `notePacedFrameSpend` debit (they report only to `tier1.countPipelinePreparation` + `policiesMs`, not the paced ledger). On the packaged commit the preceding `legStarted` was reset at visualFactory.js:4358, so the next debit at :4423 folds this prefix into the tail's span — ledger-accurate by accident there, but in the partsLibrary commits the prefix lands wherever the continuation resumed, mid-presented-frame gap included. Station/place-scale authored roots make this 4×O(subtree) contiguous work.

**Fix sketch.** Mirror the paced-leg contract inside `prepareAuthoredVisualPipelines`: yield+debit between the four policy walks (they're independent traverses of a detached root — no ordering hazard), or hoist the prefix behind `yieldToBrowser()` + `notePacedFrameSpend` when `options.asyncAdmission`/a pace-yield port is present. Keep it before `preparePipelines` (program keys must settle before compile — order preserved automatically).

**Effort:** S-M. **Impact:** M-H (scales with largest subtree class — stations/place props; multiplied by every commit). **Risk:** L — pure walk-order change on a detached root; the only ordering requirement is "before compile," which the function's structure already enforces.

### F3 — `commitAuthoredPlaceBoundary` disposes the fallback subtree unpaced, where the ship commit paces the identical seam — partsLibrary.js:4273 vs :9312-9316

**Mechanism.** Ship commit wraps `disposeDetachedObject(fallbackRoot)` behind `options.yieldBetweenGpuStages && options.yieldToNextPresent()` (partsLibrary.js:9312-9314), deferring the fallback teardown past one presented frame. `commitAuthoredPlaceBoundary` calls `disposeDetachedPlaceFallback(fallbackRoot)` at :4273 synchronously inside the commit continuation — `root.traverse` collecting every geometry/material, then `dispose()` per resource (partsLibrary.js:15663-15681) — contiguous with the graft+publish+`touchAuthoredExactTarget` tail that just ran. **Effort:** S. **Impact:** M (per-commit contiguous teardown of the largest fallback subtrees). **Risk:** L — identical to the ship seam; stale/orphan guards already sit before the call.

### F4 — `updateMatrixWorldSteps` omits the vendored `sfMatrixFrozen` skip — staticChildMatrices.js:142-175, exposed at the unforced call renderer.js:22971

**Mechanism.** The vendored `Object3D.prototype.updateMatrixWorld` skips descending into a child when `!force && child.matrixWorldNeedsUpdate === false && child.userData.sfMatrixFrozen === true` (vendor/three.module.js:139-140 — the PERF-59 patch that makes frozen authored subtrees free per frame). The Steps twin pushes every child unconditionally (staticChildMatrices.js:166-173) — no frozen check. All four call sites are `force:true` except renderer.js:22971, the unforced second compose in the opening-picture path whose own comment says it should recompute "exactly those subtrees" carrying `matrixWorldNeedsUpdate`. Output stays identical (frozen subtrees' world matrices are final by definition — the vendor comment states output is identical either way), but the walk pays O(scene nodes) where vendored paid O(dirty paths); once authored/station content lands, the frozen fraction is the large fraction, so the "cheap second compose" is a full scene re-walk at a presented-adjacent seam.

**Fix sketch.** In the twin's child loop, `continue` when `!childForce && child.matrixWorldNeedsUpdate === false && child.userData && child.userData.sfMatrixFrozen === true` — placed before both the override-dispatch branch (171) and the stack push (172), matching vendored evaluation order (skip precedes the child call either way). Also gives the other three forced sites a free win under partially-frozen roots — vendored skips them too under `!force` only, so gate on `entryForce === false`/`childForce === false` exactly as vendored does.

**Effort:** S. **Impact:** M (O(scene)→O(dirty) for every unforced walk; currently one site, but the twin is the standing idiom for future unforced walks). **Risk:** L — output-identical by the vendor comment's own guarantee; the skip is pure traversal elision.

### F5 — Suppressed coalescible write for an already-published entity is silently dropped; recovery depends on the entity ever writing again — presentationJournal.js:390-399

**Mechanism.** During `rebuildInProgress`, `recordCoalescible` suppresses every write; a `recordDestroy` or a foreign-id write sets `rebuildInvalidatedDuringSteps` (prepareRecord :253-262), but a transform/visual for an entity already inside `rebuildSourceIds` returns 0 with no invalidation and no replay (:394-399). If that entity's `publishSpawn` already ran (the stepped publish walks the collected array in order, yields every 64 rows), its spawn row carries the pose minted at publish; the suppressed write is gone — not retained, not re-queued. The presentation world slot then holds the spawn-time pose/visualRevision until the entity's next write. Movers self-heal next tick (`recordTransformIfChanged` at coreSystem.js:478-486 re-emits every dirty tick). The residual is entities that go write-silent inside the window: a far-actor flush to dormant, a station entity whose pose stops changing, or a visual-revision change (damage/state flags via `world.applyVisual`) that never re-emits — the presented pose/flags stay one write stale until some later write, i.e. a small snap/wrong-visual-flags artifact, worst case persistent until the entity next mutates.

**Fix sketch.** Track a post-publish-suppressed id set (`Set` of entityIds suppressed while `rebuildInProgress && sourceIds.has(entityId) && publishIndex[entityId]` already emitted) and re-publish those entities' transform/visual rows in the commit tail (bounded by suppression count; writer load is already the gate). Cheaper variant: mark `rebuildInvalidatedDuringSteps` for suppressed writes whose entity's publish already passed — converts to the proven re-collect path at the cost of more invalidations.

**Effort:** M. **Impact:** L-M (narrow window — publish must have already passed the entity's index and the entity must go silent; consequence is a one-write-stale pose/visual until next emit, i.e. a position pop or stale damage flags, not a missing mesh). **Risk:** M — touching the suppression contract must not re-open the spawn-suppression storm W27 killed (`isEntityJournaled` predicate); the id-set variant is the safer shape.
