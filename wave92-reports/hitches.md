## Findings (ranked)

### F1 — `shouldSubmitEntityMesh`'s protected-root bypass defeats the W91 doomed-bit hide: a suppressed destroy on a player/forceRender/neverCull row never hides

- **Evidence:** the hidden loop submits `posed && shouldSubmitEntityMesh(_submitVisibilityOptions)` with `hidden:true` (`src/render/renderer.js:22468,22485-22486`), but `shouldSubmitEntityMesh` returns `true` for `isProtectedEntityMesh` — `isPlayer || forceRender || neverCull` (`src/render/entityMeshVisibility.js:19-21`) — BEFORE the `options.hidden === true` check at `:36`. For a doomed protected row the fence still packs the slot (doomed rows stay `alive===1` and active), so `posed` is true → `applyEntityMeshVisibility(mesh, true)` → the mesh stays submitted, `visibilityChanged` is false, and `world.clearDirty` (`:22491`) consumes the VISIBILITY mark. The slot is out of `visibleSlots` permanently (`presentationQueries.js:342-352` populates hiddenSlots only on the prior-visible→not-current transition), so the hide never retries: the doomed protected mesh draws until the `entity:destroyed` priority drain scene-removes it.
- **Mechanism:** the doomed bit exists to hide suppressed destroys mid-collect-window; for protected flags it silently no-ops and the row ghosts for the entire suppression window minus the bus-drain term — precisely the kill-storm frames where the window is longest. Ordinary doomed rows hide correctly; the gap is exactly the protected class (player, forceRender mission/cinematic visuals, neverCull).
- **Fix sketch:** fold the doom into the submit verdict ahead of the protected return — e.g. `const doomed = world.doomed && world.doomed[slot] === 1;` and `applyEntityMeshVisibility(mesh, !doomed && posed && shouldSubmitEntityMesh(...))`. The doomed row is already quarantined by `exactVisible`; a protected root must still keep its pose-retention semantics on `snapshotMissing` — the change only forces the hide, it does not touch pose writes.
- **Effort:** S. **Magic-frame impact:** L-M (narrow class — needs a suppressed destroy × protected flags — but it is a W91 contract hole: the promised hide silently does not fire). **Risk:** low — dooms are minted only under `retireSuppressed`/hiddenIds feeds and cleared atomically at feed-stamp/retire/unbind/allocate, so the gate cannot strand a live visible row.

### F2 — Hidden-loop iterations pay full pose + options + freeze machinery per transition; a mass-hide (doom wave or bulk cull) drains atomically in one frame

- **Evidence:** `renderer.js:22440-22505` — per hidden slot: `world.refreshVisibleEntity` with `entityVisualCullRadius` (`:22450`), `_applyPresentationPose` (`:22452`), `isProtectedEntityMesh` + `syncResolvingMarker` (`:22461-22464`), a ~20-field `_submitVisibilityOptions` fill (`:22465-22484`), `applyEntityMeshVisibility` (`:22486`), then the `matrixAutoUpdate` freeze with an extra `updateMatrix` compose (`:22499-22503`). The loop has no per-frame budget — it drains `hiddenCount` atomically inside the present.
- **Mechanism:** hiddenSlots is once-per-transition, so a mass-doom event — a fleet-clearing wave's worth of suppressed destroys stamped across consecutive feeds — pays the entire transition set in one frame exactly when the suspended-rebuild window is already thin on frame budget. For doomed rows specifically the pose write and options fill are dead work: the mesh is hidden the same iteration, and a revived (un-doomed) row re-poses through the visible loop on re-entry.
- **Fix sketch:** a doomed fast path inside the hidden loop — `if (world.doomed[slot] === 1)`: `syncResolvingMarker`, `applyEntityMeshVisibility(mesh, false)` (also fixes F1 unconditionally — no protected bypass), preserve the `_persistentSubmitLanes.markDirty`/`asteroidInstanceViewCulled` side effects, keep the matrixAutoUpdate freeze (re-entry correctness), `clearDirty`, and skip `refreshVisibleEntity`/`_applyPresentationPose`/the options fill entirely. A per-frame cap on ordinary hides is NOT recommended (deferred hides leave stale meshes submitted — that trades a hitch for a ghost, wrong direction under the magic-frame bar).
- **Effort:** S-M. **Magic-frame impact:** M — only inside mass-hide frames, but those are the frames that need it. **Risk:** medium — `refreshVisibleEntity` also maintains grid/band bookkeeping; skipping it for doomed rows is safe only because a doomed row is either retired soon or un-doomed and re-posed on re-entry. Audit the options fill's side effects (lane dirty marks, `asteroidInstanceViewCulled`) before cutting.

### F3 — `updateFromEntities`' absent-entity sweep scans `world.capacity`, not the dense active list — O(capacity) per diff-apply whenever any absent exists

- **Evidence:** `presentationWorld.js:975-987` — guarded by `retainedHits !== byId.size`, then `for (let s = 0; s < idCols.length; s++)` where `idCols = world.entityIds` is allocated at `world.capacity` (grown ×2 by `ensureCapacity`, never shrunk — `:244-254`). During a suspended stepped rebuild every tick-advanced present runs a diff-apply; while churn keeps absents non-empty, each pays a full capacity walk (`alive`/`lastSeenSeq`/`byId.get` per slot index). On a sector that peaked at 8k slots and settled at 3k, the scan still pays 8k.
- **Mechanism:** the sweep exists to collect `absent` before `retire()` mutates `byId`. Iterating `world.activeSlots[0..world.activeCount)` — the dense swap-compacted list the pack loop already walks — yields the identical set under the identical guards (`aliveCols[s]===1`, `lastSeenSeq[s]!==seq`, `byId.get(idCols[s])===s`), since `absent` is collected before any `retire()` runs and iteration finishes before mutation begins.
- **Fix sketch:** swap the domain to `world.activeSlots`/`world.activeCount`; keep all three predicates verbatim.
- **Effort:** S. **Magic-frame impact:** L-M — bounded (O(capacity), a few tenths of a ms on dense sectors) but paid per suspended present. **Risk:** low — activeSlots is the same live set; the retire ordering (collect-then-retire) is preserved.

### F4 — `projectileSkipsVisualFactoryMesh` re-classifies the weapon family per projectile on every diff-apply present

- **Evidence:** `presentationWorld.js:909-910` runs `entity.type === 'projectile' && projectileSkipsVisualFactoryMesh(entity)` for every projectile in every `updateFromEntities` feed. `projectileSkipsVisualFactoryMesh` (`src/render/weapons/recipes.js:755-762`) calls `resolveWeaponRecipe` → `classifyWeaponFamily` (`src/data/vfxProfiles.js:125+`), which does ~6 `String().toLowerCase()`, ~10 `id.includes()` probes, a `WEAPON_BY_ID.get`, and `pictureForWeapon` per call. The renderer-side twin at `renderer.js:1007` pays the same per entity per push.
- **Mechanism:** during suspended rebuilds `updateFromEntities` runs per tick-advanced present over the whole sample; with ~100-300 live projectiles in combat, that's hundreds of string operations per suspended present — pure churn, since a projectile's weapon fields are spawn-static.
- **Fix sketch:** memoize the verdict per `entity`/`entity.data` via a `WeakMap` (projectile data records are spawn-authored; a `weaponId`/`tracking` mutation mid-flight would serve a stale verdict — that fails closed, keeping the row, not losing it). Alternatively stamp `entity.data.sfSkipsVisualFactoryMesh` at spawn.
- **Effort:** S. **Magic-frame impact:** L-M — small per-call, paid per projectile per suspended present; largest in combat-heavy windows. **Risk:** low-medium — the memo key must be the mutable-scope object (`entity.data` if data is ever repointed), and the stale-verdict direction must stay fail-closed as noted.

### F5 — Concurrent `driveCompileShadowDepthPipelines` runs can close each other's held staging session → re-mint thrash (bounded)

- **Evidence:** drives are `await`-paced generators called from 5+ sites (`renderer.js:9553,9810,13530,14614,25305`) with no in-flight serialization. Session reuse requires sig + census epoch + `heldSession.light === light` (`shadowDepthAdmission.js:629-631`); the staleness-close (`:706-708`) `close()`s the held session when a second drive mints with different keys. Drive A suspended between `sliceSteps` batches resumes into `heldSession.session.closed` → `skipped:true` benign — but drive B just re-paid the session mint (census render + all-caster reparent/render/restore + private render pass), and `shadowCensusEpoch()` bumps on every light mutation (muzzle flashes in combat), so keys drift often.
- **Mechanism:** each `runSlice` batch is atomic and self-restoring, so interleaving is sequentially safe — the cost is wasted mints, not corruption, bounded by each drive's ≤4 stale-retry loop. Worst case: two overlapping drives alternate closes → each session mint is paid multiple times across the suspension window.
- **Fix sketch:** an in-flight lease — a second `driveCompileShadowDepthPipelines` while one is live should fuse into or await the current drive rather than close-reminting its session; or stamp a drive generation and let a stale-closed drive exit without retry once superseded.
- **Effort:** M. **Magic-frame impact:** L-M (thrash bounded by the retry loops; each remint is a whole-scene census + render). **Risk:** medium — serialization adds a coordination point that must not deadlock the paced yields.

## Hunt notes (a)-(e)

**(a) packDirty coverage — COMPLETE.** Enumerated every packed column (`position, quaternion, scale, tint, bank, pitch, entityId, archetype, flags, generation` — `presentationSnapshot.js:25-38`) against every world-side writer: position/rot/bank/pitch → `writePoseScalars`' `packedChanged` (note the deliberate split: prev* rebase terms are excluded — a prev-only change produces byte-identical packed bytes and correctly does NOT mark, `:409-414`); typeCodes/flags → `refreshMetadata`; entityId/generation/scale(1,1,1)/tint(no writer) are mint-static. A missed writer would silently serve stale rows — none found. The copy path is fail-closed in the other direction too: generation mismatch or map miss falls back to scalar write.

**(b) generation-column churn — zero added cost by construction.** A reminted slot is already `packDirty===1` (`allocateRecord:632`) — it pays the scalar write regardless; the generation gate only vetoes copies that were already headed to scalar writes (new entityIds miss `previousIndex.get` before the generation check even runs). Classes that remint hot: projectile destroy/respawn (new ids — map-miss, not generation-defeated) and pooled-visual id recycles (first post-remint pack is dirty anyway). **Stable-generation reuse is NOT contract-safe**: a recycled id inside one poseEpoch would alias the prior body's row for both copy AND blend → teleport artifact — the per-alloc remint is required.

**(c) `entityId→previousIndex` map cost — bounded O(N).** The map is populated inside `write()` as rows pack — the worst case "map build + zero copies" is N inserts paid regardless, plus ≤N `get`s only on clean slots; on an all-dirty frame the gets never run. Both ends are O(N) with a constant far below the 10-column scalar write / 9-column `copyRow` they gate, and the whole branch only runs when `previous.poseEpoch===poseEpoch`.

**(d) hiddenSlots accumulate/clear cycle — bounded once-per-slot.** hiddenSlots is transition-only (prior `visibleSlots` minus current marks, `presentationQueries.js:342-352`, plus the pose-dirty path `:246-255`), cleared and rebuilt per query (`:195,:243,:292,:403`). N doomed rows cost N hidden-loop iterations exactly ONCE across the suspension (a doomed slot stays out of the visible set — no repeat transitions), not N per frame. Per-iteration cost is the finding (F2), and the protected-root non-hide is F1 — both bounded; neither unbounds the cycle.

**(e) Drain escalation oscillation — bounded.** `backlog>32 → budgetMs×2` (`renderer.js:1955-1962`): a hovering backlog flips the per-frame spend between ~2ms and ~4ms — the oscillation window is bounded by corpse mint rate ≈ bus-drain rate, the escalation never exceeds ×2, and each elevated frame still drains `ceil(pending/4)` corpses so the hover self-terminates. No runaway mechanism found.
