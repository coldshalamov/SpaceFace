## Ranked findings

### F1 — Origin-crossing full walk in `_syncWorldPresentationTableMeshes` is provably redundant

**Evidence:** `src/render/renderer.js:22816-22837` (field) and `22838-22852` (dressing): the full-walk arm fires whenever `this._worldFieldPoseOriginSeq !== originSeq` (or the table has no `dirtyPoseIds` Set). But `frameOriginSeq` bumps only on an actual origin move (`src/core/coordinates.js:92-101`), which is exactly when `frameMembrane.sync` returns `changed=true` with the same `(dx,dz)` (`src/render/frameCoordinates.js:104-118`), and `_applyFrameOriginRebase` (`renderer.js:21894-21904`, invoked at `23308-23311`) already adds that identical delta to every mesh in `this._meshes` — including every rock/dressing mesh `poseRow` would re-derive (`22804-22814`) — plus `updateMatrix()` on frozen roots, several hundred lines *earlier in the same presented frame*. `toLocal(global)` for an unmoved row equals `old_local + (old−new)` up to a float ULP.

**Coverage proof for the delta path:** every pose/rot writer marks `dirtyPoseIds` — `asteroidField.js:167` (insert), `:293-299` (`advanceResourceBody` pos+rot), `dressingTable.js:84` (insert), `:96-102` (`markDressingRowPoseDirty`, sole external caller `automation.js:1424`). Newly mounted meshes self-pose at mount (`renderer.js:21618-21620`, `21796-21798`) under the current origin, so a mount landing mid-frame between the rebase (`23310`) and the table sync (`23440`) is already correct. `poseRow`'s extra effects are unaffected by an x/z delta: occluder y-sink is re-applied per frame by `_updateCameraOccluders` (`23371`, before the sync), and rotation.y is covered by `dirtyPoseIds`.

**Mechanism:** every membrane cell crossing pays an atomic `O(field.rocks + dressing.rows)` span — Map.get + toLocal + write + updateMatrix per row — inside the presented frame, on top of the same frame's `O(_meshes)` rebase + camera/VFX reproject. Cell crossings are the most loaded frames; in dense asteroid sectors the row count is the largest per-row span left in `prepareFrame`.

**Fix sketch:** drop the `!== originSeq` clause from both full-walk arms — take the dirty-set path whenever `dirtyPoseIds instanceof Set`, keeping the full walk only for pre-journal tables (`!(fieldDirty instanceof Set)`). Keep updating the `*PoseOriginSeq` stamps so the gate stays coherent. The `invalidateAsteroidInstancePool` call on `posedField>0` (`22836`) is already covered for crossings by `21917`.

**Effort:** S. **Impact:** M (eliminates the single largest per-crossing atomic span). **Risk:** low-mid — the `!(dirty instanceof Set)` fallback must be preserved; verified no pose writer escapes the dirty journal, and mount-time self-pose covers the mount-mid-frame case.

### F2 — Post-publish yield-throw skips fallback dispose; job catch then re-requests an already-committed boundary

**Evidence:** `partsLibrary.js:4273-4278` (place commit) and the identical pre-existing seam at `9329-9334` (ship commit): after `boundary.remove(fallbackRoot)` (`4236`) and the publish block (`4266-4271`, which sets `authoredAssetState='authored'` and `PRESENTATION_ADMISSION.ready`), `await waitForAuthoredAdmission(options.yieldToNextPresent(), options)` at `4275` can reject — `assertAuthoredVisualPreparationActive` (`8442-8450`) throws `AbortError` when `isResidencyOwnerActive()` goes false, and `asyncAdmission.wait` propagates aborts (the job catch at `7433-7436` classifies exactly this `AbortError`). The throw skips `disposeDetachedPlaceFallback(fallbackRoot)` (`4277`) / `disposeDetachedObject` (`9333`), then lands in the job catch, which — post-publish — runs `releaseBoundaryResidency` (`7459`, a no-un-release dead-owner mark) and `markAuthoredBoundaryForReadmission` (`7465`) on a boundary that already committed.

**Mechanism:** the abort must land in a ~one-present window (between publish and the paced dispose), so it's rare, but when it fires: (i) the detached fallback subtree's GL resources leak permanently — nothing else holds or disposes it; (ii) the committed boundary's residency claims are released while its authored root stays mounted, and readmission re-arming re-requests a redundant upgrade → a cache-warm re-decode + re-commit churn on an already-correct boundary. This is the verify-(c) item from the W86 checklist — `disposeDetachedPlaceFallback` does **not** run on every commit path; the yield-throw path misses it.

**Fix sketch:** wrap the deferred yield + dispose as `try { await waitForAuthoredAdmission(...) } finally { try { disposeDetachedPlaceFallback(fallbackRoot) } catch (e) { warn } }` — commit succeeded, so teardown must be unconditional. Optionally also gate the job catch's `releaseBoundaryResidency`/readmission on "did the run reach publish" (e.g. check `boundary.userData.authoredAssetState === 'authored'` before marking), so a post-commit abort doesn't churn a committed boundary. Apply to both the place (`4273`) and ship (`9329`) seams.

**Effort:** S. **Impact:** L-M (rare window, bounded per-hit leak + churn). **Risk:** low — a `finally` can't change the success path; the aborted bookkeeping remains correct pre-commit.

### F3 — Suspended journal rebuild pays a full `O(E)` fallback mirror rebuild on every tick-advanced present for the whole suspension window

**Evidence:** while `needsRebuild()` holds across presents (`presentationJournal.js:160-165`, `rebuildInProgress` true until the stepped `rebuildFromSteps` finishes, `548-656`), `populateJournalFrame` sets `journalValid=false` (`presentationRunner.js:847-862`), which drives `fallbackFromState` (`presentationPublisher.js:149-227`). The W86 reuse gate (`:96-101`) only reuses when `completedTickCount===0`; any present carrying a new sim tick pays `world.rebuildFromEntities` (synchronous clear+realloc per entity, `presentationWorld.js:804-822`) + `_rebindPresentationMeshes` (`renderer.js:20537-20544`) + fence repack — atomically inside the presented frame. Worst case the suspension spans the chunked collect leg + up to `JOURNAL_REBUILD_INVALIDATED_MAX=3` doomed attempts before the atomic escalation (`presentationRunner.js:795`, `:828-830`), so a fight that keeps writing transforms can stack several consecutive full-mirror rebuild frames — strictly heavier than the pre-journal path, since the 4 ms collect/publish legs are *also* running.

**Mechanism:** no consumer starves — the fallback covers freshness correctly (verified (d): `mergeJournalRange` deferred ranges are subsumed by `commitJournalRebuild`'s `[start,end]` at `:729-741`; `acknowledgePresentedJournal` gate `:866` retains the ring; capacity guard `journal:615` → `'rebuild-replay-capacity'` → invalidated → escalation bounds the window). The residual is pure cost: the degraded path is O(E) rebuild + O(E) rebind per tick-advanced present, vs the journal's O(delta).

**Fix sketch:** diff-apply inside `fallbackFromState` during suspension — walk the entity set once and mutate the mirror in place (add/remove/update surviving entries) instead of `rebuildFromEntities`'s clear+realloc, so the suspension present pays O(E) *reads* without O(E) slot-churn; or reuse the last mirror + apply only `mergeJournalRange`-eligible pending ranges. Cheapest variant: cap the fallback rebuild to every Kth suspended present (correctness holds — the mirror is one snapshot behind, the same freshness the journal provides anyway) — though K>1 delays spawn-on-glass, so prefer diff-apply.

**Effort:** M. **Impact:** M (suspension windows are episodic — restores, overflow storms, burst invalidations — but those are exactly the frames already loaded). **Risk:** medium — mirror mutation ordering must respect bind/unbind side effects in `_rebindPresentationMeshes`.

## Residual (a) — pending-release flush ordering: verified clean

`_unbindPresentationMesh` (`20256-20321`) releases id-keyed registry records immediately (`20292-20296`) and adds the mesh to `_meshReleasePending` for the identity pass (`20305`), flushed by `_flushMeshReleasePending` (`20245-20254`) at `serviceRenderMeshResidency:2030` — before `syncEntityViews` (`23362`), so tracker updates that frame see post-flush state. Between unbind and flush the only registry readers are the per-entity update passes (`22465-22509`), driven per *live* entity — a straggler record under a dead id is never addressed. A straggler under a *recycled* id can at most write inert dead-node transforms for ≤1 frame (the detached Object3D accepts writes; no GL survives `disposeObject`) before `releaseMeshSet` clears it or `shipMicroMotion`'s `mountMesh !== mesh` self-heal rescan (`shipMicroMotion.js:1727`) re-derives — versus the old immediate-null semantics the delta is unobservable and bounded. `drainDespawnDisposeQueue` (`2027`) running before the flush is safe for the same reason: the flush only releases *recorded refs*, and no reader resolves them in the interim.

## Residual (b) — nested `releaseMeshSet` batch scopes: verified clean

`_meshReleaseBatchBegin/End` (`20234-20243`) is a synchronous depth counter — the pending Set accumulates across nesting and flushes only at depth-0 end or the next service call. No tracker registration can be stranded inside a scope: `_bindPresentationMesh` (`20173-20228`) mints no motion records (tracker refs appear on first update via `scanMountPivots`, `shipMicroMotion.js:1128`, which happens in `syncEntityViews` — never inside a batch scope). A scope-end flush therefore cannot clear a record minted in-scope. Generators can't suspend mid-scope — all scope bodies are synchronous loops (`1836-1859` reattach, `8368-8384`, `12339-12364`, `14846-14865`, `20568-20577`, `20770-20805`, `20950-20994`); an `await` inside a `try` scope body would be a future hazard but none exists.

## Residual (d) — suspended rebuild consumer starvation: verified bounded, cost noted as F3

Consumers during `journalValid=false`: (i) `mergeJournalRange` (`883-886`) gates on `needsRebuild` — unmerged ranges are subsumed by the rebuild's `[start,end]` at commit (`729-741` + `simulationRunner.alignJournalCursor`); (ii) `acknowledgePresentedJournal` (`864-866`) retains the ring — overflow routes through the capacity guard into invalidation, not loss; (iii) the publisher's mirror is rebuilt by `fallbackFromState` — freshness preserved every present. Starvation is bounded: `JOURNAL_REBUILD_INVALIDATED_MAX=3` escalates to atomic `rebuildFrom` which no foreign write can interleave; `suppressedDestroyIds` doom (`:781-800`) only accelerates it. The real residual cost is F3.
