### 1. Retained-LOD release lanes stack unpaced whole-subtree teardowns inside one presented beat — W89's new microtask disposers — partsLibrary.js:8983–8996, fires at :9002–9011 (`disposeWholeShipLodRetained`) and :9017–9041 (`refreshWholeShipLodFamily`)

**Evidence:** W89 added two fire-and-forget release closures:

```js
const releaseComposedRetained = (composed) => {
  void Promise.resolve()
    .then(() => disposePreparedAuthoredShip(composed))   // :8985
    .catch(...);
};
const releaseRetainedRoot = (root) => {
  void Promise.resolve()
    .then(() => disposeDetachedObject(root))             // :8994 — ATOMIC sync traverse+dispose
    .catch(...);
};
```

`refreshWholeShipLodFamily` (a re-commit swapping in a fresh authored root) detaches every retained level root and fires one release per level (:9037–9041); `disposeWholeShipLodRetained` — invoked per-node inside the paced despawn drain via `disposeObjectNode` (renderer.js:26644) — re-grafts each retained root into the dying tree (`boundary.add(root)`, :9009) and still fires `releaseComposedRetained` per level (:9010). Microtasks drain sequentially before the next task/render, so K retained levels = K whole-subtree teardowns all completing inside the same task — a lod0–3 family re-commit fires up to 3 of them back-to-back.

`disposeDetachedObject` (:15740) is a synchronous `root.traverse` + per-node geometry/material dispose — for a capital-ship level root that's hundreds of nodes with GL deletes, paid atomically per level. `disposePreparedAuthoredShip` (:8779) is async but its awaits are per-item `attempt()` continuations — microtask-granularity interleaving, all still landing inside the same task boundary; per-item cleanup (`instance.dispose('authored-ship-preparation-failed')`, geometry/material teardowns, `root.clear()`) is synchronous per item. Neither lane calls `notePacedFrameSpend` — the teardown is both unpaced AND invisible to the ledger.

**Mechanism (popin-admission):** whole-ship LOD re-commits and boundary despawns land during exactly the moments this lane cares about — admission churn, sector bursts, despawn storms. A re-commit's demoted-level teardown runs as one silent burst of GL deletes in the beat before the next present; the wallet never sees it, so every sibling paced lane (journal collect/publish legs, census, compile drain, despawn drain) believes the frame had headroom while several ms of disposal just ran. Under a boundary-despawn burst the drain paces the node-level work while the composed teardowns sneak through as unaccounted microtask cargo — the frame blows its real budget with the ledger still reading ~0.

**Fix sketch:** route both closures through paced paths instead of bare microtasks. For `releaseRetainedRoot`, the stepped twin already exists — `disposeDetachedObjectSteps` (:15761, yields per 128, identical guard set): park one iterator per root on a module-level queue and drive it from the same deferred-commit slice clock the place/ship drives already use, or hand the detached root to the renderer's `_despawnDisposeQueue` via an exported enqueue (the roots are already `parent==null` at fire time — the drain's remount recheck fits). For `releaseComposedRetained`, at minimum `await yieldToBrowser()` between per-item `attempt()`s in `disposePreparedAuthoredShip` and debit each segment with `notePacedFrameSpend`; the items are already individually keyed and resumable via `preparedCleanupCompleted`.

**Effort:** S–M · **Impact:** M–H · **Risk:** L–M (teardown order is already unordered; keep `preparedCleanupCompleted` idempotence and the `.catch` belt)

### 2. Authored-commit dispose drives debit honestly now but still never consult `pacedFrameSpend()` — K concurrent commit disposes stack first-slices inside one presented beat — partsLibrary.js:4299–4314 / :9396–9410 — residual half of W89 finding 3, re-verified

**Evidence:** W89 fixed the debit half correctly — each drive now debits per slice (`notePacedFrameSpend(monotonicNow() - commitLegStarted)` per `disposeIter.next()` at :4305/:9402) and restamps after the `await waitForAuthoredAdmission(options.yieldToNextPresent())` at :4307/:9404 (correct `debit → await → restamp`, verified). What did NOT land: neither drive consults `pacedFrameSpend()` before minting or resuming a leg — the first `disposeIter.next()` runs unconditionally at the loop's first iteration and every resume drives one more 128-node slice regardless of wallet state. Compare the wallet-aware drivers that do it right: `drainGltfCompileQueue` gates on `pacedFrameSpend() >= GLTF_COMPILE_FRAME_MS` with `GLTF_COMPILE_MAX_SKIPPED_FRAMES = 2` aging (decodeTaskBudget.js:305+), `upgradeMintPass` gates `while (pacedFrameSpend() >= PACED_FRAME_BUDGET_MS && ledgerSkips < 2)` (renderer.js:17260s), and `drainDespawnDisposeQueue` gates `ledgerSkips < 2` at entry (renderer.js:1960s). These two drives have no equivalent gate.

**Mechanism (popin-admission):** during an authored-swap burst — K ships committing in adjacent frames — each commit's dispose drive mints a leg that contributes one ≤128-node slice per presented beat, additive with every other live lane. The ledger *records* the spend but the legs don't *throttle* on it, so the beat's real cost is K slices + the finding-1 microtask teardowns + whatever the wallet-checking lanes legitimately ran. This is precisely the "can a despawn storm still stack N paced legs inside one presented beat" residual the hunt asks about — answer: yes, through this lane and finding 1's.

**Fix sketch:** consult the wallet at each resume — `if (pacedFrameSpend() >= PACED_FRAME_BUDGET_MS && ledgerSkips < N) { ledgerSkips++; await waitForAuthoredAdmission(options.yieldToNextPresent(), options); continue; }` — mirroring the drain's aging bound so a permanently-spent stretch can't starve GL reclaim forever. The iterators and debit sites are unchanged.

**Effort:** S · **Impact:** M · **Risk:** L

### 3. `updateFromEntities` never rechecks the push-time eligibility predicates — `_noMesh`/`projectileSkipsVisualFactoryMesh` flips post-push keep feeding rows through prefix and completed collect alike — presentationWorld.js:856–867 vs presentationSources.js:108–112

**Evidence:** `pushAlive` gates `row.alive === false || row._noMesh || (row.type === 'projectile' && projectileSkipsVisualFactoryMesh(row))` at *push* time (presentationSources.js:109–110). `updateFromEntities` rechecks only `entity.alive === false` and `entityId === 0` (presentationWorld.js:858–861) — the other two predicates are never re-evaluated at apply. `_noMesh` is not spawn-static: the mesh-build retry path sets `e._noMesh = true; e._noMeshByRenderer = true` after ≥3 build failures (renderer.js:21842–21844), i.e., an entity pushed eligible can tombstone mid-collect. The journal writer-side predicate (`entityIsJournaled`, presentationSources.js:103–106) agrees with `pushAlive` — only the presentation apply diverges.

**Mechanism (popin-admission):** a row tombstoned after its push keeps arriving on every feed minted from that collect — the prefix publishes it every suppressed present (`rebuildCollectPrefix = job.entities.slice()`, runner :842-ish) and the completed collect carries it too. Each feed allocates/retains an `alive=1` presentation row: byId + spatial grid + active/special membership + `entityRefs` pin + `getSlotForEntityId` hits — for an entity that will never bind a mesh. Pre-W89 the per-present sync collect re-ran `pushAlive` and the row vanished the next fallback; now it persists until the *next* collect's push-time filter drops it (or a retire walk runs). Mostly inert — nothing renders — but it's a phantom row in every world query for the window, and the same asymmetry would hide any future dynamic `_noMesh`/`projectile-skip` flips.

**Fix sketch:** mirror the eligibility half in the apply loop — `if (entity._noMesh === true) continue; if (entity.type === 'projectile' && projectileSkipsVisualFactoryMesh(entity)) continue;` — two field reads per row, matching `entityIsJournaled`/`pushAlive`. Contract-safe: the row's data is presentation-only and the sim record is unchanged; a would-retire-on-next-collect row simply never mints.

**Effort:** S · **Impact:** L · **Risk:** L

### 4. Nit — partsLibrary stepped dispose twins push children in forward order, so sibling teardown runs reversed vs `traverse` — contradicting their own "identical DFS order (pre-order, root first)" comment — partsLibrary.js:15781 and :15821

**Evidence:** `disposeDetachedObjectSteps` does `for (const child of object.children || []) stack.push(child)` (:15781) — a LIFO stack pops `children[n-1]` first, i.e., siblings tear down in *reversed* order, not the pre-order `traverse` uses. Same forward push at :15821 (`disposeDetachedPlaceFallbackSteps`). The renderer twin got it right: `disposeObjectSteps` pushes `for (let i = children.length - 1; i >= 0; i--) stack.push(children[i])` (renderer.js:26698), which *is* pre-order. Comments on both partsLibrary twins claim "identical DFS order (pre-order, root first)" — root-first holds, sibling order doesn't.

**Mechanism:** mechanism-neutral today — the per-node work (stand-in release, site-presentation dispose, geometry/material dispose with shared-asset guards) is order-insensitive and the suspended-walk owns the same node set either way. Pure comment-fidelity + latent order-sensitivity if any future per-node hook assumes sibling order.

**Fix sketch:** push `children` reversed in both twins (one-line each), matching `disposeObjectSteps`.

**Effort:** S · **Impact:** L · **Risk:** L
