## Ranked findings

### F1 — reclaimWarm's consult is sector-blind: an entry's corridor label is the first poster's, forever

- **Evidence**: MECHANISM_VERIFIED. `src/render/assetResidency.js:459-479` — `reclaimWarm` returns true for (a) a resident-under-owner entry, re-stamping only `entry.lastWarmClaimAtMs`, and (b) an in-flight request where `request.key === exactKey && request.active`, again re-stamping only the claim clock. Neither path looks at `request.metadata.sectorId`. `beginRequest`/`commit` at `src/render/assetResidency.js:527-558` carry `request.metadata` into `retain(exactKey, owner, request.metadata)`, and `entryCorridorRank` at `src/render/assetResidency.js:871-881` ranks soft-eviction by `metadata.sectorId` per owner (rank -1 = outside the corridor = evicts first within its lease-weight class at `sortSoftEvictionCandidates`, lines 883-895). Consulted at `src/render/assetLoader.js:709-727` under the `ownerlessWarm` guard — every warm arm in `src/render/renderer.js` shares `runtime.defaultResidencyOwner`.
- **Mechanism**: warm arm A posts url::slot F under sector S_A (e.g. a sectorPredict/incoming-sector arm). While that request is in flight — or after it lands resident — warm arm B posts the same F under the sector that actually needs it, S_B (e.g. `warmEncounterPendingDecode` on the current sector). The consult returns true on the key match: B never mints, and the entry's owner metadata keeps S_A's stamp. Re-posts on later polls re-stamp `lastWarmClaimAtMs` only — the sector label is never widened or corrected for the entry's entire residency lifetime. When the eviction corridor ranks S_B but not S_A (B's sector in-corridor, A's dropped out — e.g. a stale predict arm, a demoted-sector arm that re-posted before demote, or a border-flip speculative sector), `entryCorridorRank` returns -1 for the entry and it releases first inside its lease-weight class despite live S_B demand. The next mount of F in S_B re-decodes on the live frame — the pop the warm exists to prevent.
- **Fix sketch**: in `reclaimWarm`, compare the caller's `sectorId` against the stored label. For the in-flight path, mismatch → fall through to `beginRequest` (a second same-key request commits `retain` with the second arm's metadata; last-commit wins the stamp — cheap, no shape change). For the resident path, mismatch → update/union the owner metadata's `sectorId` (or store a `sectorIds` set that `entryCorridorRank` maxes over). Alternative single-pass fix: carry `sectorIds: Set` in request/entry owner metadata, union on every consult hit, rank by best member — avoids the duplicate request record at the cost of touching `retain` + `entryCorridorRank`.
- **Effort**: S-M. **Magic-frame impact**: M. **Risk**: low — the consult's true-path semantics are untouched; the only behavior change is a fresh request mint or a metadata widen on a sector mismatch. Requires byte-pressure eviction inside the window for the visible effect, so impact is conditional — but the label wrongness is unconditional and the arms that mix sector ids in one window are live (predict lanes post incoming-sector ids; encounter/runway arms post `world.currentSectorId`).

### F2 — authoredPreloadPlanMemo is single-slot per entity; alternating option tuples thrash

- **Evidence**: UNVERIFIED. `src/render/partsLibrary.js:1182-1216` — the WeakMap stores exactly one `{key, plan}` per entity. Two call sites with different option tuples (`{lodLevel}` vs `{}` vs `{requiredWholeShip:true}`) on the same entity overwrite each other: each call misses, re-plans, and clobbers the other caller's entry. The W132 landed note measures 0.69 µs hit vs 1.16 µs cold — a thrash pair doubles the cold cost on every call instead of ~0. Call sites found: `authoredPreloadPlanForEntityAtLod` (partsLibrary.js:2556-2561, falls through on null LOD file) and `authoredUpgradePlan` (partsLibrary.js:7458-7471, `job.options`). Whether any live entity actually receives alternating tuples per poll is workload-dependent — not proven here.
- **Mechanism**: if alternation exists, the memo pays the full cold-plan cost every call plus GC churn on a per-poll-per-entity path — the residue class (d) asks about.
- **Fix sketch**: store a small `Map<key, plan>` per entity (cap 3-4 entries) instead of a single `{key, plan}` slot.
- **Effort**: S. **Magic-frame impact**: L. **Risk**: trivial.

### F3 — `ship.trafficRole` rides the warm roster but never reaches the spawn spec

- **Evidence**: UNVERIFIED (mechanism proven; impact is bytes-only). `src/systems/encounterDirector.js:1043-1054` emits `encounter:claimDefenseRoster` records carrying `{archetype, factionId, trafficRole}`, and `enemyHullDecodeKey`/`makeWaveHullDecodeStub` (`src/world/presentationSources.js:877-968`) honor the role axis — the warmed stub resolves faction-kit files the same way `applyFactionWholeShipKit` (`src/render/partsLibrary.js:2028-2052`) would. But `spawnShips` (`src/systems/encounterDirector.js:1344-1411`) never writes `sh.trafficRole` onto `spec.data` — it stamps team/hullFrac/doctrine/formation/cultureId/namedAceId/etc. only — and `makeEnemySpawnSpec` (`src/systems/combat.js:237-350`) stamps `lootTableId` but no `trafficRole`. So the live entity resolves the role-less selection while the warm may decode the role-selected kit file: a warmed file nobody mounts.
- **Mechanism**: wasted decode bytes (a kit file warmed instead of — or in addition to — the file the spawn actually draws). No visible pop: `spawnableShipArchetypePrewarmUrls` (`src/render/partsLibrary.js:2585-2608`) ambient-covers every hostile whole-ship, traffic-role, and faction-kit file, so the file the live entity mounts is decoded anyway.
- **Fix sketch**: either stamp `spec.data.trafficRole = sh.trafficRole` when the record carries one (aligns live resolution with the warm — but changes visual identity, needs a gameplay sign-off), or drop the role token when minting claim-roster warm records (aligns the warm with live resolution — byte savings only).
- **Effort**: S. **Magic-frame impact**: L. **Risk**: the first option changes drawn identity; the second is safe.
