## Ranked findings

### 1. Shadow-census first-mint sync fallback still pays one atomic O(scene) walk per scene inside a presented frame

- **Evidence:** `memo.sig` starts `null` on every fresh memo (renderer.js:28901-28906, re-minted whenever `memo.scene !== scene` — i.e. every sector cook / restart / context-restore swap). The drive consult (`_shadowCensusForFrame`, 28897-29025) drains the stepped mint ≤4 ms per pass (28987-28997, `lastDrainSeq` dedupe), then — when `sig` is still null — falls through to the sync fallback at 28999-29025: `sigFallbackSeq !== _viewSyncSeq` + `forcedFrameSpend() < FORCED_FRAME_BUDGET_MS`, then `mint` runs `collect ? _signatureFromSceneCollect(scene) : _signatureFromScene(scene)` (29013-29014) — a whole-scene traverse — synchronously in-frame, and stamps `sig` so subsequent consults hit the fast path.
- **Mechanism:** on the first presented pass that consults the census after each scene swap, the stepped mint's whole reason for existing (avoid the atomic walk) is defeated: the frame pays ≤4 ms of stepped drive *plus* the full O(scene) sync traverse it was pacing. Bounded — once per `_viewSyncSeq`, once per scene — but this is the single largest atomic whole-subtree leg still reachable inside a presented frame. Call-site classes that can arm it in-frame: every `_shadowCensusForFrame` consult (~15 sites: depthOpts lightSig 14142, park recheck 29511, arm sigs 29304/29333, coverage sigs 29801/29892, liveRadius sig 29647, additive radius 29297/29325/29798, additiveCovRadii 29873, cameraStats 30048, follow sigs 29780/30022, freeze classification 29431, disarm 29606, retain 29321/29354, drain 30763); the `sigFallbackSeq` dedupe collapses them to one walk per pass.
- **Fix sketch:** inside presented frames (`paceEpochNow() >= 0`), serve the null sig (unsigned → callers already read it as conservative-on, same as `sigParked`) while the stepped mint pends, and reserve the sync `mint` for non-presented contexts (harness/first-load where the Steps twin is absent). Alternatively bound the fallback mint to the same ≤4 ms slice budget and park it unfinished — worst case identical to today minus the atomic completion. The epoch-pairing rule is already correct for this (sync mint stamps `memo.epoch = sigEpochNow`, 29023).
- **Effort:** S. **Magic-frame impact:** H — removes the last unconditional atomic O(scene) traverse per cook, which is exactly a mid-flight hitch class (sector transition = heaviest scene mutation = first presented census consult). **Risk:** low-med — serving `sig == null` for a few more passes widens shadow policies (more casters than needed) for at most one pacing window; no correctness risk since unsigned consults already fall back to live recompute.

### 2. Warn telemetry is unlatched at the fault-driven sites — worst-case console volume per epoch is O(rows) + O(frames), and console I/O lands inside the presented pass it measures

- **Evidence (per-fault warns, no epoch latch):**
  - `notePresentationRowFault` — `console.warn('[render] presented row faulted; skipping to next row for the epoch', err)` on *every* row fault (renderer.js:2134-2136). Capped ≤3/row/epoch by the quarantine, but unbounded across rows: a widespread row-fault storm (~600 meshes) produces up to ~1,800 warns per epoch.
  - `_drainMeshBuildQueue` belt catch — `console.warn('[render] mesh build queue drain faulted mid-walk', drainError)` at 24429. No epoch latch, no fault counter, runs once per call while the queue is non-empty → ~60 warns/s sustained under a persistent skeleton fault (rows themselves are quarantined via `_meshBuildLastError`/`_noMesh`; this is the generator-skeleton class).
  - depth-stage arm catch — `console.warn('[render] depth-stage arm faulted; queued roots re-arm', armErr)` at 29546. Faults are *counted* per epoch (≥3 stamps `noteLaneFault('depthStageArm')`, 29540-29545) but the arm still re-arms in `finally` whenever `pending.size > 0` (29573-29574) → warns every ~48 ms idle arm for the whole epoch — the arm's own cadence, not a one-shot.
  - policy-root mint/drive — `console.warn('... mint failed; ...'/'... drive failed; ...')` per fault (31044, 31059); bounded to ~3+defer-warn per root per epoch by the ≥3-fault defer (31008-31011), but scales with distinct faulting roots.
  - census drive (`[render] shadow census drive failed`, ~28969) and sigFallback (`[render] shadow census sync mint failed; parked for epoch`, ~29016) — bounded (≤1/pass in the pre-sig window; ≤3/epoch via `sigFaults` park) but per-fault, not epoch-latched.
- **Mechanism (hunt c):** the ~20 epoch-latched warns (presentedTail labels, lane catches, quarantine first-fault) are fine — ~20/epoch worst case. The unlatched classes above are the residual: under the persistent-fault conditions this machinery exists for, the console becomes the amplifier — each warn allocates, formats, and flushes devtools I/O inside the presented frame, which is a real frame cost on loaded hosts (SwiftShader hosts especially — do not assume console writes are free).
- **Fix sketch:** per the brief's own suggestion — a `warnDedup` serial in `laneFaults` (or a per-epoch count cap in `noteLaneFault`/`notePresentationRowFault`) that warns the first ~8 faults per lane per epoch then summarizes once ("lane X faulted N times this epoch; parked until epoch flip"). Row stamps keep full fidelity in state; only console volume becomes O(1)/epoch/lane. For `_drainMeshBuildQueue` and depthStageArm specifically, reuse the existing `_presentedTailFault_${label}` epoch-latch pattern — a one-line epoch check before `console.warn`.
- **Effort:** S-M. **Magic-frame impact:** M — worst in exactly the fault-storm scenarios the rest of the machinery already defends. **Risk:** low — telemetry-only; stamped counters keep full truth.

### 4. A small set of machinery calls in the presented path is still un-belted — a machinery-level throw reaches `renderError` and kills the whole presented pass

- **Evidence:** at prepareFrame head, outside any `tryPresentedCall`/drive-belt: `this._frameMembrane.sync(focusTarget)` (27118), `this._applyFrameOriginRebase(alpha, worldPacket, this._frameMembrane)` (27119), `this._adaptive && this._adaptive.update(...)` (27123), `this._updateSectorPostTransition(...)`/`_updateSectorPaletteTransition(...)`/`_updateStarfieldClock(...)` (27121-27128), and `serviceRenderMeshResidency(this, _postPresentSectorBusy)` at 27143 — whose internal lanes are belted but whose glue (e.g. the `enqueueHoldExemptMeshBuildsSliced` machinery call at 2785, the `_meshBuildPoll*Latch` bookkeeping) is not. Same class: `_publishSnapshotFenceStats(step.value)` at 27060 and its twin-path call at 27102-27105 sit outside the `iter.next()` try — inside `prepareFrame` but unprotected. All propagate to `renderFrame` → `renderUpdatePhase` catch → `renderError` → the PRESENTATION STALLED shape the tail belts exist to prevent.
- **Mechanism (hunt b):** the per-row surfaces are covered (row quarantine in both counted loops, `settleRebuildBridges` per-row catch, `_drainMeshBuildQueue` row quarantine + skeleton belt, dispose drains per-iter, publisher `consume` internally belted end-to-end at presentationPublisher.js:322-506 — every apply/visit/collect drive has its own catch + paced 4 ms + wallet). What remains exposed is the *machinery glue* between belted lanes: membrane sync / rebase / adaptive / sector-transition bookkeeping, the residency service's own latch logic, and the fence-pack stats publish. Remote (these don't throw under normal corruption — they'd need a structural bug), but the blast radius is the maximum one.
- **Fix sketch:** wrap the prepareFrame head block in the same `tryPresentedCall` labels (one per site, consistent with the tail's granularity), or fold `serviceRenderMeshResidency` into `tryPresentedCall` at the call site and let its internal belts handle row classes (the outer belt then covers glue faults with `undefined` fallback — the lanes' own parked state already survives). For `_publishSnapshotFenceStats` — a cheap `try/catch` swallowing into laneFaults is enough; stats are advisory.
- **Effort:** S-M. **Magic-frame impact:** M — low probability, maximum blast radius; the audit's whole point is that no single machinery throw should stall a presented pass. **Risk:** low — every candidate site has a legal "skip this frame" degrade (membrane keeps last transform, sector transitions resume next pass).

### 5. `arrivalReserve`'s fault epoch keys on `enterSerial` only — context-restores don't reset its private retry ledger

- **Evidence:** `const epochKey = owner.state.world.enterSerial || 'x'` at renderer.js:3093 — while `serviceFaultEpoch(state)` = `` `${enterSerial|'x'}|${contextRestoreSeq}` `` (2367-2371) is what every sibling lane uses.
- **Mechanism:** on a context-restore without an `enterSerial` flip, the reserve's `FaultRetries`/`retryAt` survive — a restore mid-faulting-epoch keeps the lane parked at cap instead of starting fresh like its siblings. Bounded direction (retries never exceed 3; the bound still holds), but the degrade persists longer than the contract intends — drift, not leak.
- **Fix sketch:** `const epochKey = serviceFaultEpoch(owner.state)` — one line, restores sibling consistency.
- **Effort:** S. **Magic-frame impact:** L. **Risk:** trivial.

- **(b) Quarantine coverage gaps:** per-row presented paths and their coverage — `syncEntityViews` counted loops (row stamp + park ✓), `settleRebuildBridges` (per-row catch ✓), `_drainMeshBuildQueue` (rows quarantined via `_meshBuildLastError`/`_noMesh` + skeleton belt ✓), dispose drains (per-iter catches ✓), contact-shadow/instance-submission/pools (whole-lane belted via `tryPresentedCall` — fault skips the sync that frame, retries next frame, stale state legal ✓), publisher apply walks (internally belted + paced + fallback ✓). Epoch latch is not needed for per-row paths already belted — the whole-lane belt IS the correct degrade for pool syncs (stale pool = legal).
- **(c) Warn telemetry budget:** ~20 epoch-latched warns/epoch (fine) + unlatched classes: row faults ≤3/row/epoch (dominant), meshBuildDrain ~60/s sustained, depthStageArm ~20/s while pending non-empty, policy ~3/root/epoch+defer-warn, census ≤4/epoch — finding 2.
