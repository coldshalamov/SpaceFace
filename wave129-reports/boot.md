## Findings (ranked)

### F1 — `_slotStoreSignature()`'s enumerate+getItem walk still runs atomically inside the async Continue consult on a generation miss (hunt c)

**Evidence (MECHANISM_VERIFIED):**
- `src/save/saveSystem.js:2140-2146` — on a signature miss, `_slotStoreSignature()` loops `localStorage.length` and calls `localStorage.getItem(key)` for every `sf.save.*`/`sf.recovery.*` key in one synchronous task — the whole save+recovery corpus materialized as JS strings in a single leg.
- Called synchronously from the "async twin for the Continue lane": `_slotIndexWithFallbackAsync` fills `burst` via `this._slotStoreSignature()` at `saveSystem.js:2205-2206`; the pacing yield sits *after* the walk at `2221` ("The signature collect above already paid its getItem walk on this task — break before the scans"). The stale in-flight re-sign at `2216-2217` can pay the same atomic walk a second time.
- The generation flips on any tracked write — `bumpSaveStoreGeneration` covers `sf.save.*`, `sf.recovery.*` **and `sf.settings.*`** (`saveSystem.js:110-117`) — so a settings toggle mid-dwell, a Save/Load write, or an autosave between the last card render and the click stales `_slotIndexCache`/`_slotIndexValidationInFlight` (both keyed on the old sig) and lands the walk on the click chain: `_newerUnplayableSkipAsync`/`_latestSlotAsync` → `_slotIndexWithFallbackAsync` (`saveSystem.js:4563-4573`, `2790-2791`).
- The mitigation that covers the common case is real but partial: `_slotIndexWithFallbackAsync` rides `_slotIndexValidationInFlight` on signature match (`2209-2213`) and `_sharedStoreCollectCache` reuse exists (`2135-2139`) — but the validation pass does *not* republish its own materialized `primaryRaws`/`collected` map into that cache (`2314-2351`, `2387`), so a generation the background pass already walked gets re-walked atomically when consulted post-flip.
- **Mechanism (what the player sees):** on a mature profile (multiple ~sub-MiB envelopes + recovery copies — the file itself documents "several megabyte-scale envelopes" at `2120-2126`), the click→veil consult pays a multi-MB synchronous string materialization before the paced scans even start — a pause in the exact window this lane exists to keep painted.
- **Fix sketch:** give the async lane a chunked signature twin — generation-bracket the walk exactly like `_collectSharedStoreKeysChunked` (`saveSystem.js:494-503`: yield-batched collect, redo on a generation tear, bounded attempts then sync fallback) and feed the same `raws` into the existing scans; or have `_scheduleSlotIndexValidation` publish its already-collected raws into `_sharedStoreCollectCache` under the validated generation so the signature reuses them. Sync twin stays authoritative for sync callers.
- **Effort:** S-M · **Magic-frame impact:** M (conditional: needs a generation flip between last validation and the click, scales with store size) · **Risk:** low — the bracketed-retry pattern is already proven in-file; writes mid-collect just retry.

### F2 — The async slot scans run per-entry worker verdicts strictly serially; the identical verdicts fan out in parallel one function away (hunt b)

**Evidence (MECHANISM_VERIFIED):**
- `src/save/saveSystem.js:2572` (`_scanStoredSlotsAsync`) and `:2655` (`_scanRecoverySlotsAsync`) — each hash-untrusted blob `await`s its own `_prepareEnvelopeMetaAsync(raw)` worker roundtrip (parse+checksum, 2500 ms timeout at `4709`) before the loop advances; K untrusted entries = K sequential roundtrips on the consult.
- The same file already does the same verdicts in parallel: `_scheduleSlotIndexValidation` pushes `Promise.resolve(this._prepareEnvelopeMetaAsync(raw))` jobs and `await Promise.all(jobs)` at `saveSystem.js:2345-2351`. Worker parallelism is structurally safe — a busy warm worker falls through to a fresh spawn (`_checkoutSaveWorker` `3922-3935`), so N dispatches genuinely overlap.
- **Mechanism:** a store carrying several untrusted blobs (foreign writes, cards without `_blobHash`, recovery-only slots, first consult after a migration) pays the verdicts one-at-a-time inside `loadAsync`'s slot resolution — serializing real worker roundtrips between the Continue click and the envelope worker dispatch downstream. Hash-trusted entries skip the worker entirely, so this only fires on the untrusted subset.
- **Fix sketch:** keep the yielded 16-entry walk but collect the untrusted `[slot, kind, raw]` entries, then dispatch verdicts in bounded slices (e.g. `Promise.all` over ≤4 at a time) before the card-rebuild leg — verdict writes are per-slot independent (`verdicts[slot]`/`out[slot]`), so fan-out preserves results.
- **Effort:** S · **Magic-frame impact:** M-L (conditional on untrusted-blob count; 0 in the fully-trusted common case) · **Risk:** low — bounded fan-out only; ordering inside `out`/`verdicts` is irrelevant since every entry writes its own key.

### F3 — The target envelope's bytes are materialized 2-3× on the 'latest' consult (hunt b/c overlap)

**Evidence (MECHANISM_VERIFIED, minor):**
- `slotBurst.raws` already holds `LS_PREFIX + slot` bytes once the signature walk ran (the Map built at `saveSystem.js:2140-2146` rides `burst` through `_slotIndexWithFallbackAsync`), yet `loadAsync` re-reads `localStorage.getItem(LS_PREFIX + slot)` at `saveSystem.js:4586`.
- `_newerUnplayableSkipAsync` independently re-reads `localStorage.getItem(LS_PREFIX + best)` and `RECOVERY_PREFIX + best` at `saveSystem.js:2839-2841` after the same consult filled the burst.
- `specByteHit` then runs `spec.raw === raw` on the multi-MB pair at `saveSystem.js:4591-4592` — an O(len) string compare on the click task.
- **Mechanism:** one multi-MB envelope string is materialized by `getItem` up to three times per 'latest' consult (signature collect → skip-check → raw read) plus a full-length byte compare — pure duplicate main-thread string work on the click path.
- **Fix sketch:** consult `slotBurst.raws` before `getItem` under a generation re-check — `installSaveStoreWriteTracking()` + `('gen:' + _saveStoreGeneration) === burst.sig` is the identical freshness proof the `specHit` path already uses (`4581-4583`); on match the Map's bytes are definitionally current and the byte compare is unnecessary (raws hit proves bytes, not just identity).
- **Effort:** S · **Magic-frame impact:** L-M (bounded by envelope size; every 'latest' consult, small but pure waste) · **Risk:** low-medium — must re-verify the generation counter before trusting the Map (a write landing between walk and read bumps gen and forces the honest getItem, which is exactly what happens today).

## Measurement notes

All findings are code-mechanism level (`MECHANISM_VERIFIED` where stated). No before/after numbers were taken — SwiftShader on this box cannot produce meaningful GPU/frame-time evidence and the game cannot be launched here (Electron presents 0 frames). F1/F2 severity is a function of real profile size: a hardware/session run with `design/perf/scoreboard.json` benchmark commands on a mature multi-slot store (several `sf.save.*` + `sf.recovery.*` envelopes, plus a settings write between menu mount and click) would size both legs directly; the CPU-side counters that would carry it here — a `workNowMs` bracket around `_slotStoreSignature` and the per-entry `restore_prepare_meta` roundtrip times — can be measured headlessly if a richer fixture store is wanted.
