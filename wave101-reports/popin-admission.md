## Findings (ranked)

### F1 — W100 regression: `touchExactTargetSubjects` async inside a synchronous reveal/finally → every loading-mode `touchMany` group draws hidden subjects (a no-op)

**Evidence:**
- `src/render/renderer.js:10721-10729` — `async (subjects, drawableSession)`; the `await stampSubjectEnvAsync(subject)` loop at :10724 suspends on the first `await` **unconditionally** (microtask boundary even when `bindEnvironmentToStandardMaterialsSteps` yields zero iterations) and paces further via `admissionPaceYield` (:10699/:10730, rAF-bound).
- All four armed `touchMany` sites reveal-then-restore synchronously: `renderer.js:13327-13339` (pool seal, manual restores), `:14957-14970` (rock pools), `:15982-15987` and `:16143-16148` (both via `whileRevealedGroup`, :15944-15962). Each `finally` runs the restores the moment the call returns the pending promise — the deferred async body reaches `touchScenePipelines`/`touchSubjectOnExactTarget` only **after** every subject is re-hidden.
- `src/render/openingGpuAdmission.js:465-498` — `withOnlySubjectsDrawable` never sets `visible=true` on keep members; it only refrains from hiding them. A subject re-hidden by the early restore stays hidden in the touch draw → `projectObject` skips `visible===false` subtrees (three.module.js) → the group render draws nothing.
- `src/render/openingGpuAdmission.js:874` — `touched = touchMany(group)` is **not awaited**. Every row at :879 stores the pending Promise; the `try/catch` at :873-877 observes only synchronous throws, so a rejection (e.g. context loss mid-draw) is an unhandled rejection. The aggregate then masks the defect: `touched: results.length` (:911) counts rows pushed, not subjects drawn — telemetry reports full touch coverage while every touch was a no-op.
- `src/render/renderer.js:10725-10726` — secondary: the bloom branch calls `this.bloom.touchScenePipelines(list, cam.obj, scene)` **without** forwarding `drawableSession` (only the non-bloom fallback at :10728 passes `{ drawableSession }`), so on the production bloom route the pooled `drawableHideSession` minted by all four call sites is ignored — each ≤24-subject group re-pays the O(scene) `scene.traverse` enumeration at `openingGpuAdmission.js:486-491`.
- `git show 047bc1de8` confirms W100 flipped `touchExactTargetSubjects` sync→async; `openingGpuAdmission.js` was untouched by the wave, so the reveal contract and the un-awaited call were written for the sync version and never re-fitted.

**Mechanism:** the reveal contract is "the draw must issue inside the same task as reveal/restore" (the code says exactly this at :10692-10693 — then violates it). Loading-mode only: all four sites gate on `state.mode === 'loading'`. Net effect: the batched exact-target touch — the machinery that exists to absorb deferred program links and buffer uploads behind the loading shell — silently absorbs nothing for every grouped batch. Every subject presents cold → links/uploads land inside first presented frames → the pop-in/hitch class this wave was built to kill.

**Fix sketch:** `await touchMany(group)` at :874 **and** hold the reveal across the async body — either an async `whileRevealedGroup` (`try { return await run(); } finally { restores }`) or move reveal/restore inside `touchExactTargetSubjects` (pass a reveal factory). Extended reveal lifetime is safe in loading mode (the shell covers the scene). Keep `stampSubjectEnvAsync` pacing — alternative structural fix: stamp envs paced *outside* the reveal (the stamp is visibility-independent), then a sync reveal+draw. Also thread `drawableSession` through `bloom.touchScenePipelines(subject, camera, lightingScene, options)`. Effort **S–M**. Magic-frame impact **H**. Risk **low** — the reveal discipline is unchanged, only its lifetime.

### F2 — W100 regression: fence-pack `appendedSlots` sweep misses post-mint rows that end up below the mint bound → committed snapshot drops a live spawn for a frame

**Evidence:**
- `src/render/snapshotFence.js:460` — `mintedSlots = activeSlots.slice(0, active)` freezes the prefix; `:469-470` — `appendedSlots = activeSlots.slice(active, getDiagnostics().active)` covers only rows still at indices ≥ the bound at slice time.
- `src/render/presentationWorld.js:315-325` — `removeActive` swap-moves `activeSlots[activeCount-1]` into the freed position; `:308-313` `addActive` appends at `activeCount++`; `:722-745` `retireSlot` → `removeActive`.
- Hide path for a missing row: `renderer.js:23177, 23192-23198` — `snapshotIndexOf` −1 → `posed=false` → `applyEntityMeshVisibility(mesh, false)`.
- Introduced in `047bc1de8` (`git log -S appendedSlots`).

**Mechanism:** positional coverage can't survive swap-remove. Escape mode 1: pack parks with bound `N`; `addActive` appends row R at index ≥ N; a `retireSlot` at prefix position `p < N` swap-moves the tail into `p` — if the tail is R, R now lives at `p < N`: absent from `mintedSlots` (frozen pre-alloc) and outside `slice(N, current)` — R packs nowhere. Escape mode 2: a mid-park retire shrinks `activeCount` below `N`; a subsequent `addActive` appends at an index < `N` — below the bound and never minted — again missed by both sweeps. The in-code rationale at :467-468 ("rows only move toward lower indices under swap-remove, so the appended region can never duplicate a frozen-prefix slot") reasons about duplication but misses evasion. Trigger: alloc+retire inside one parked pack window — kill/spawn churn during combat, exactly when the stepped pack parks. Result: spawn absent from the committed snapshot → 1-frame hide → pop-out→pop-in flicker, self-healing next pack.

**Fix sketch:** identity coverage instead of positional — `minted = new Set(mintedSlots)` once per pack (or a per-pack epoch column), then sweep `activeSlots[0..currentActive)` packing rows whose slot isn't in the set; or a `packDirty`-only tail scan — missed rows keep `packDirty` set since `packRow` never ran on them. Same O(active) order. Effort **S**. Magic-frame impact **M** (rare real pop-out — the exact class). Risk **low**.

### F3 — `updateFromEntitiesSteps` retire tails never yield → unbounded burst inside the 4 ms drive window

**Evidence:** `src/render/presentationWorld.js:1328` (`for (const slot of deadResidents) retireSlot(slot)`) and `:1341` (`for (const entityId of absent) retire(entityId)`) — inside the stepped generator, no `yield`. Driven by `pendingApplyIter` under a 4 ms wall bound (`src/render/presentationPublisher.js:221-229`) that can only interrupt at yield points.

**Mechanism:** the apply's collect sweeps are paced (`:1308`, `:1336`), but the retire bursts they build execute atomically at generator end — hundreds of `retireSlot`s (grid-remove + swap-remove + `byId.delete` + freeSlots each) inside one presented frame, coincident with the largest visible set change. Trigger: mass-destroy on a suppressed-destroy feed (hiddenIds) or a large absent set on a full feed. The sync twin stays atomic by design — fine; the stepped twin exists precisely to amortize this. `clearSteps` (:897-921) already shows the pacing pattern for the analogous teardown.

**Fix sketch:** `if ((++sinceYield % every) === 0) yield;` inside both retire loops — `retireSlot` is row-atomic, so mid-burst parking leaves a consistent world. Effort **S**. Magic-frame impact **M** (a presented-frame hitch on the biggest deltas). Risk **low**.

### F4 — same W100 defect class on the compile leg: `compileSubjectColorAndDepth` defers `_compilePostRoute` past the restore — live defect for light-carrying subjects

**Evidence:** `renderer.js:10705-10711` — `await stampSubjectEnvAsync(subject)` before `_compilePostRoute`; all `compileOne` sites wrap via `whileRevealed`/`whileRevealedGroup` (`:13320-13321`, `:14943`, `:15977`, `:16141`) or issue-loop try/finally (`:14370-14377`). Three's `compileAsync` invokes `compile()` **synchronously** at call time (three.module.js:17419-17421); `compile` gathers lights via `traverseVisible` (:17323 targetScene, :17341 subject) — which skips `visible===false` subtrees — and materials via `traverse` (:17365, visibility-agnostic).

**Mechanism:** pre-W100 the whole synchronous critical section (env stamp + compile's light census + material init) ran inside the reveal; now the `_compilePostRoute` call runs after restore. Materials still init (traverse ignores visibility), but a re-hidden subject contributes **zero lights** to the census → program defines compiled with fewer lights than the presented pass gathers → relink at first draw. Narrower than F1: only subjects carrying lights miscompile (most carry none; lamp-bearing authored roots are the exposure). This also refines the sibling lane's F5 premise — `whileRevealed` around `compileOne` is *not* pure dead work; the light census makes the reveal load-bearing exactly when the subject ships a light.

**Fix sketch:** same structural fix as F1 — hoist the paced env stamp above the reveal (it's visibility-independent) and keep `_compilePostRoute` synchronous inside the reveal, restoring the pre-W100 invariant. Effort **S**. Magic-frame impact **M** (conditional on subject-borne lights). Risk **low**.

### F5 — stamped cull radius can go stale-large across a LOD-level change while continuously visible (over-admit, never a pop)

**Evidence:** `bindMesh` is the only `visualRadius` writer (`renderer.js:21028` → `presentationWorld.js:543` finite-gated write); the apply path passes none (`:1261`, `:855` falls back to `world.radii[slot]`); `drawnCullRadiusForMesh` re-derives on `lodLevel`/`childCount` change (`visualCullRadius.js:65-69`) but the stamp is re-read only on rebind or at hide-time (`renderer.js:23070` hidden-pass `refreshVisibleEntity`).

**Mechanism:** a LOD swap to a smaller measured envelope without rebind leaves the larger stamp → `exactVisible` over-tests → the entity enters the visible set earlier than its drawn envelope needs and pays admission churn at edges. Direction is waste, not pop-in: three's own frustum cull still applies at draw, and the stamp self-heals on the next hide. Effort **S** (re-stamp when the `drawnCullRadius` cache key changes, or on `wholeShipLodActiveLevel` transitions). Impact **L**. Risk **low**.
