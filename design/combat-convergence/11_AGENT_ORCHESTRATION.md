# 11 — Agent orchestration and execution contracts

**Purpose:** turn the owner's complaints into intelligent, coordinated engineering and art work without another queue, conflicting writers, or a pile of disconnected demos. This document is an execution plan, not a claim that subagents were launched. The planning PR starts no paid sessions, automations, or implementation jobs.

## The lead's responsibility

The lead owns the integrated player experience and exact evidence, not every file. Read current repository instructions, program status, the relevant existing packets, and these documents. Reconcile this source baseline with the current checkout and active work. Keep the owner's fixed outcomes intact while allowing specialist agents to select better mechanisms.

Map work into the existing program front door and admitted packet identities. CEC-A–F are local acceptance-scene names, not replacement dispatch IDs. Where an existing packet already owns the outcome, continue it. Where a missing outcome requires a new bounded leaf, create it through the current program mechanism rather than inventing a parallel planning hierarchy.

Do not turn a large historical document into a permanent subsystem lock. Claim exact current write paths for a bounded task. Preserve dirty foreign work and active fresh claims. Follow the repository's current single-checkout, pathspec commit, and handoff rules. A remote planning branch is not permission to absorb someone else's open PR.

## First work order: truth and a small integrated fight

The first implementation result should be a readable, controlled version of CEC-B with real current tools—not months of infrastructure before a player sees improvement. In parallel, obtain bounded research from 12 for the largest unknowns. Research may narrow the change; it may not defer every concrete repair into another plan.

The lead records the current source/route baseline, known active PR overlap, exact desired outcome, supported hardware access, and what can be judged in the current environment. A lack of GPU capture capability blocks visual/performance certification, not source tracing or focused deterministic tests. Produce a precise requisition and continue independent useful work.

## Shared-owner bottlenecks

The lead resolves exact paths before mutation. Likely collision points include `src/systems/input.js`, `src/systems/weapons.js`, `src/core/physicsAuthority.js`, combat damage/status ownership, system registration, save integration, the shared UI projection, and Look/light allocation. Treat these as candidate seams to inspect, not automatic exclusive claims over entire directories.

One agent writes a given shared file at a time. Other agents provide a precise interface proposal or a patch handed to the current writer. Integrate the smallest shared contract first, then let consumers proceed. Do not have separate agents independently adding target state, death events, attack ownership, or field registries and hope a final merge will reconcile semantics.

A data contract must specify authoritative owner, read/write direction, time base, units, identity/lifetime, accepted/rejected outcomes, persistence, and teardown. Reuse existing event names and structures where their meaning fits. New events follow the repository's canonical naming and are added only when there is an actual producer and consumer.

## Copyable adversarial review brief

> Review the candidate as a player who did not write it. Use its declared commit and ordinary route, not a hand-set success state. Try to confuse the target/weapon selection, break concealment without being seen, expose an AI omniscience path, destabilize a formation, duplicate mass/loot, shoot through a shield with a different weapon family, cancel a held input, and restore during the hardest lifecycle transition. Inspect whether effects tell the truth at normal camera and density. Compare full-scene performance at unchanged settings. Return concrete reproduction steps and the strongest unsupported claim. Do not rubber-stamp screenshots, test counts, or the author's description.

## Evidence and handoff contract

A handoff names the task and fixed outcome, parent/candidate commit, changed paths, current shared-owner agreements, source observations, chosen mechanism and alternatives, tests actually executed with outputs, normal-route instructions, image/video evidence where available, performance environment, save/lifecycle implications, and remaining limitations. Keep it in the repository's existing evidence/report location for the admitted task. Do not invent another global completion ledger under this folder.

Distinguish source-present, focused-tested, normal-route-observed, target-hardware-verified, and owner-accepted. An agent may deliver a useful partial result with honest remaining evidence; it may not mark a complete packet from a registration hook or a fake event emitter. A failing integrated route stays open even when every unit test is green.

## Decision freedom and stopping rules

Agents should use judgment: compare alternatives, simplify redundant controls, improve layouts, and tune after observation. Record consequential deviations with their evidence and compatibility cost. Do not discard fixed user goals because a narrower feature is easier, or protect an awkward first proposal after a better measured design emerges.

Stop blind retries when the same environmental blocker repeats. Preserve evidence, issue a precise capability requisition, and move to disjoint work. Fix owned regressions before presenting a finished slice. Do not spend the whole assignment rewriting instructions, expanding checklists, or producing compliance prose. The success measure is a better controlled, readable game encounter and the evidence that it genuinely works.
