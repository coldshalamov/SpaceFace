# Failure patterns this bank is designed to stop

**Do not send a vague feeling to a weak implementer and hope it invents the missing game.** Send the chosen packet, current owner and counterexample. A new mechanism is a strong planning decision.

**Do not count registries, files or completed tests as player value.** A mission needs a place, people, an action and consequence. A physical machine needs real operation and contact. An upgrade must change what the player can do.

**Do not build an already implemented subsystem again.** G-stick flight, bombs, field lifecycles, NPC jobs, custody, aftermath, Swarm drafting and the ecology planning program already have foundations. Improve or connect them.

**Do not trust prose over current code.** A module map can point to a moved screen. A defect ledger can retain a stale syntax report. A completed queue row can coexist with a weak ordinary route. Verify the exact claim you are about to change.

**Do not solve causality with a magic grant.** A loaded hauler needs a real mined lot. A recovered item needs surviving custody. A crusher outcome needs the current machine's physical law. A mission reward needs one valid settlement.

**Do not make the game 'fast' by removing the authored game.** Attribute cooking, linking, allocation, queueing and starvation separately. Preserve the default picture and real actors. A faster average with missing bodies is a regression.

**Do not turn review into another institution.** Inspect the actual work and fix it. Use the current task surface; no new ledger, queue, committee or permanent human approval gate.

**Do not make a giant first batch.** Finish a small causal chain, review it and use what the result teaches. The point of 300 plans is a rich prepared supply, not permission to dispatch 300 overlapping mutations at once.
