# Allocate expensive reasoning where the answer is not already known

## Three different jobs

**Strong planning** chooses the memorable player outcome, resolves real alternatives and defines the complete slice. This pack performs that job in advance for 300 proposals. **Bounded implementation** translates the chosen mechanism into the current owners, tests its explicit failure cases and completes the normal route. **Strong review** asks whether the implemented result is coherent, genuinely finished and worth keeping, not merely compliant with a checklist.

Do not assume a less-capable agent becomes reliable because a prompt is long. Give it a small context set and observable acceptance cases. Do not assume a strong model should only review: unknown-root-cause performance, save atomicity and custody accounting can require strong intervention before code is written.

## Routing by uncertainty

| Work | Before implementation | During implementation | After implementation |
|---|---|---|---|
| Existing-owner content extension with clear laws | Use the packet's choice; verify an equivalent is not already present | One bounded actor/place/tool change through current owners | Review the scene, counterplay and consequence in a compatible batch |
| Functional ORRERY task | Confirm current component and command/receipt path | Minimal change, complete pending/refusal/focus behavior | Walk controls on the real screen; no redesign by review surprise |
| Field, flight or Massline tuning | Establish one reproduced feel hypothesis and fixed comparison | Change one meaningful law/parameter group at a time | Strong comparison of agency, counterplay and physical consistency |
| Money, custody, save or asynchronous publication | Strongly adjudicate exact ownership/commit semantics when unresolved | Implement the bounded state/receipt transition plus adversarial tests | Strong check of duplication, loss, stale commit and interruption |
| Reported GPU/performance regression | Reproduce and attribute; never guess from total frame time | One quality-preserving algorithm/lifetime change | Paired route measurements and picture integrity, not average-only timing |
| New ecology layer | Reconcile with admitted canon and current architecture | Small selected slice, no global spread subsystem | Review information, embodied behavior, save boundaries and scope |

## Batch size and cost control

A starting heuristic is three to five completed, compatible outcomes per stronger review. This is not a claim about a provider's price, model ranking or optimal token ratio. Keep an unresolved shared seam to one executor/integrator. Increase parallelism only across disjoint current write sets; twenty tasks sharing `renderer.js` are not twenty independent jobs.

The highest-value review bundle contains the selected packets, the actual diff, the current owner contract, the observed player sequence and the exact failed/passed checks. It does not contain every historical report or all 300 proposals. Ask for the most consequential defects first, with exact failure scenarios and the smallest viable repair.

## Escalation rule

Escalate the decision, not the whole project, when the implementation needs a new authoritative state owner, changes a transaction boundary, contradicts current canon, changes save semantics, merges shader contracts, or fails the named case twice without locating the cause. The stronger pass should return one resolved seam and a narrowed implementation instruction, not another open-ended brainstorm.

A lack of available stronger review is not permission to claim acceptance or invent an unsafe patch. Complete disjoint safe work and state the exact unresolved decision. Do not turn optional review scheduling into a new permanent queue blocker.

## What the strong reviewer should reject

Reject decorative completeness, invented numerical claims, phantom custody, UI-only simulation, hidden stat buffs, missing ordinary entry, a reward with no physical cause, a 'fix' obtained by weakening a test, and improved frame time obtained by removing the authored game. Prefer a small completed causal chain over many disconnected features.
