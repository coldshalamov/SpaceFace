# Orchestration: expensive judgment, bounded production, independent review

## One captain owns the player outcome

A captain receives a current native assignment and a supporting program from this pack. The captain reads the live source, observes a real route, and decides what would most improve the experience. Workers receive bounded changes, not “make it AAA.” Model brands in historical workflow docs may change; allocate by demonstrated capability and available authorized tools rather than copying stale model names.

Use the strongest reasoning/taste capability for the highest-variance decisions: input law, solver/authority boundaries, game economy tradeoffs, mission geometry, visual composition and cross-system failures. Use reliable implementation agents for named production leaves. Use a different reviewer for code and ordinary-route evidence. Small mechanical INFERENCE work can use cheaper agents when its exact owner, change and done sentence are already resolved.

## The loop

**Observe:** run the shortest ordinary route that demonstrates the claimed weakness. Read the live owner and current authority. If a feature already satisfies the outcome, stop trying to improve it by prejudice.

**Frame:** write a one-paragraph player problem, likely cause and desired difference. Separate observed fact from hypothesis. Select one to three genuinely different interventions only when design uncertainty warrants it; don't create a mandatory brainstorming ritual for obvious defects.

**Choose:** prefer the smallest intervention that deepens an existing loop and preserves identity. Consider implementation risk, shared-owner collisions, required art/sound and how to prove it. Keep alternatives only when they teach a useful refusal.

**Partition:** assign exact paths and interfaces. One owner writes each shared file. If the world worker needs a VFX receipt, the world worker owns the semantic event; the effect worker consumes it. If an output isn't integrated yet, use a named interface contract, not a competing temporary engine.

**Build:** workers create the code and accompanying assets/tests required by their assigned leaf. The captain keeps the whole slice usable; it must not remain a set of orphan files waiting for a later glue agent.

**Review:** a second agent reproduces the actual change, including negative cases. Art is viewed in motion at the real camera; sound is heard in mix. Review finds remaining defects and proposes concrete changes, not a score-only verdict.

**Integrate:** apply current native completion states and path-safe commit practice. Update only relevant queue/acceptance rows. Preserve foreign diffs. State what was actually tested and what still needs a different host, device or audience.

**Continue:** choose the next unblocked weakness, not automatically the next number in this ZIP. Release completed path ownership promptly. A full exact-path collision is temporary; disjoint implementation, reading and review can continue.

## Avoid two opposite failures

Unbounded agent creativity makes incompatible systems. Overcontrolled microtasks can make a technically coherent but lifeless game. The captain supplies the scene, constraints and quality bar; workers retain room to solve concrete details. Weak agents do not choose new cosmology, combat laws or UI styles. Strong agents are not reduced to renaming columns.

A missing dependency is work to solve. An unproved optional invention is scope to defer. Neither should become a reason to do no useful work.
