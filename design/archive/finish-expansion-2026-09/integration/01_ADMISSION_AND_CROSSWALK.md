# Adoption into the existing development system

## No second queue

This ZIP is a design source. `catalog/task_catalog.json` inventories its candidates for search, cross-reference and validation. It has no leases, completion authority, live priority or native dispatcher schema. `INDEX.html` is just a reader. There is no “run all tasks” script.

Current ownership remains: root `AGENTS.md`; `build_map.md`; active native packets; `design/program/roadmap/program-queue.json`; current INFERENCE catalog and the single demo defect ledger. Product intent and current technical/UI/art authority retain their existing precedence. [S01–S06]

## Map by outcome, not by title

For an assigned local task, search the current queue, active packet, completed record and live implementation for the **player-visible outcome**. Choose one disposition:

- **Already true:** use current evidence; repair stale active guidance only if it matters, then take the next useful task.
- **Residual:** extend the current native packet with the missing end-to-end behavior.
- **New selected work:** give it a native identity through the current admission convention and link the supporting packet here.
- **Conflicting or superseded:** preserve this idea as history/optional context and do not implement it.
- **Missing dependency:** build or adopt the specific prerequisite, or take disjoint work. Do not block the entire fleet.

Do not allocate new PQ/AE numbers from this document. The current registry and active branch determine free identities. The inspected dispatcher validates `--id` as `PQ-` followed by three digits; a package ID or leaf suffix is not a supported CLI argument. Use its current help and native schema rather than guessing.

## INFERENCE contract

Each `SFQ-I` item is a narrow directed production candidate with a named program/path neighborhood, a change, done sentence and refusal. It is **not** an invitation to infer a new system. At adoption, select the one exact current owner file/function and confirmed reproduction; if that cannot be named, route the diagnosis to a strong-agent campaign first. Promote only tasks whose prerequisite system exists. Use the existing OPEN/CLAIMED/SHIPPED/CUT lifecycle in the repository's catalog, not in this static ZIP.

The small number of documentation reconciliation tasks are supporting work, not a substitute for game development. After repairing an active instruction that would cause a regression, continue to an actual production outcome when that is the assignment.

## Concurrency and integration

Inspect status and foreign diffs before edits. Respect fresh exact-path ownership; stale labels are not permanent subsystem locks. Separate workers by actual files. If two tasks both need one shared definition, one worker owns that definition and the other consumes its agreed result. Do not multiply frameworks to avoid a temporary collision.

Follow current repo policy for checkpoints and pathspec commits. Never wholesale-reset, clean, stash or restore another writer's work. Do not construct a commit from a stale snapshot/alternate index that can revert newer unrelated files. Use current VM import instructions for remote outputs; do not write into a remote-authoritative outbox.

## Package intake output

A useful intake is a small set of outcome mappings plus the first production improvement. It is not hundreds of copied queue rows. Link selected supporting documents and preserve their provenance. The receiving agent should update native status only after the correct live evidence exists.
