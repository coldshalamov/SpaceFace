# 09 — VALIDATION: proving "fun" when agents can't play in real time

The structural problem behind years of broken work: agents can't sit in the cockpit and feel
it, so they ship code that looks right and plays wrong. This plan is the standing measurement
harness every other Arcade Core plan cites. It has three layers; a task closes only when its
named layers pass.

## Layer 1 — Headless sim assertions (seconds, every change)

Deterministic, seeded, no renderer. The repo already has the harness idiom (check scripts,
golden routes, lab scenarios). Add the Arcade Core metric battery:

- **Kill economy:** pickups spawned per kill by victim class; % collected under fly-over
  steering; vacuum onset latency; credit/material values vs data-table bands.
- **Physics kit:** Δv delivered by each impulse source on reference masses (16 / 60 / 150);
  tumble threshold crossings; field coupling ratios (light vs heavy).
- **Style classifier:** fabricated kill events → correct cause buckets; chain compounding.
- **Pacing:** TTK table (starter weapons × enemy classes); time-to-first-contact on seeded
  island entries; kills/min and credits/min for a scripted competent bot.
- **Market:** continuity / smoothness / learnability scores and regime-blend bounds from 06.
- **Atmosphere:** escape-vs-burn outcomes per control state and entry velocity.

All of these are plain numbers with stated tolerance bands, regenerated by a single
`check:arcade-core` script so regressions fail fast in CI.

## Layer 2 — Bot routes (headless or minimal-render, per task)

Scripted input players driving the real game loop on canned scenarios: "kill this wing with
the starter fit," "concussion one into the rock," "well + explosive the clump," "escape the
atmosphere band," "watch the island for 10 minutes." Each plan names its routes. Bots record
the metric stream; they do not judge beauty.

## Layer 3 — Human gates (the owner's hand, on captures)

Some things only a person can judge: does the fireball read as a fuel tank, does the spiral
look clip-worthy, does the island feel alive. For these, the agent produces **short captures
at default zoom** plus its Layer 1/2 numbers, and the human answers a *specific question*
stated in the plan (e.g. "name the kill cause from the visuals alone"). No vague "does it
look good?" reviews.

## The tuning lab pattern

Agents can't iterate feel in real time — so give the *owner* the instrument:

- **`_combatlab.html`** (new, follows the existing `_vfxlab.html` / `_rcslab.html` pattern): a
  small arena page with sliders over every tuning surface named in plans 01–05 — magnet
  radius/authority, impulse values, tumble thresholds, TTK knobs, spawn density, vacuum
  params — writing to data and hot-reloading. The owner plays it in real time and lands the
  numbers; agents implement and wire the sliders and persist chosen values.
- Lab values are data, not code: the lab edits the same `src/data/` files the game reads.

## Rules

- Every Arcade Core packet names its Layer 1 metrics, Layer 2 route, and (if applicable)
  Layer 3 question *before* implementation.
- A failing metric is reduced to a seconds-scale regression test before rework (existing
  repo protocol — keep).
- No acceptance by screenshot or code reading (I-10).
- Metrics live in the receipt, not in chat.
