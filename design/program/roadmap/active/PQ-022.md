## Outcome

SpaceFace acquires a repeatable source→release→manifest→runtime→route pipeline that can ship ambitious authored ships, stations, rocks, wrecks, infrastructure, and props at professional quality without turning every asset into a one-off renderer branch or a performance liability. Each leaf packet promotes one exact asset/family and proves it in the default game path.

PQ-022 is not one implementation task. It is complete only when its named representative families and foundry outcomes are individually accepted. A worker may claim one leaf at a time.

## Leaf outcome contract

Every leaf ships all relevant stages:

```text
identity brief
  -> reproducible source (Blend/generator/reference provenance)
  -> validated source artifact
  -> optimized release artifact
  -> exact manifest/runtime identity
  -> resolve/prepare/admit
  -> stable transform/sockets/interaction envelope
  -> normal-route close/default/far/motion/damage/LOD review
  -> Browser/Electron + accessibility + performance + cleanup
  -> receipt
```

A Blender render, generated GLB, source validation, contact sheet, or isolated preview is an intermediate artifact. It is not the leaf outcome.

## Visual quality contract

At normal gameplay distance, communicate:

- **macro:** silhouette, scale, mass, propulsion/utility/weapon zones, faction/function;
- **meso:** construction, plate overlap, recesses, access, radiators, machinery, sockets, damageable regions;
- **micro:** material grain, controlled wear, fasteners, welds, scratches, heat and roughness response only where screen-space filtering can support them.

Hero and cast assets should be rich, not timid. The constraints are truthful construction, coherent identity, stable runtime behavior, and measured cost—not an arbitrary triangle or texture prestige number. Crowd assets can simplify aggressively where the normal camera cannot distinguish the difference.

Post-processing cannot hide unfinished silhouette, materials, lighting, or scale. Color swaps cannot substitute for faction/function construction.

## Live architecture to reuse

- Existing source/release manifests and exact runtime maps remain asset identity authority.
- Blender/source pipeline owns units, transforms, UVs, bakes, semantic material roles, sockets, proxies, and LOD construction.
- Release tooling owns compression, KTX2, quantization/mesh optimization, validation, and hash-bound metadata.
- Renderer/assets own cancelable load, residency, material/program sharing, LOD/HLOD, instancing/batching, culling, and cleanup.
- Gameplay descriptors own target/mining/salvage/tether/destruction semantics; renderer consumes them.
- Resolve→prepare→admit is shared by visibility, targeting, collision, interaction, and hostile action.

Do not add filename maps, a second asset registry, a special Electron asset path, or an acceptance-only renderer.

## Work breakdown for one leaf

### Phase 0 — critique and identity

- [ ] Capture current live result at close/default/far and relevant motion/lighting/damage states.
- [ ] Write a short identity brief: role, silhouette, scale, construction, materials, sockets, interaction envelope, LOD strategy, and largest visible deficiencies.
- [ ] Inspect existing source/donors. Whole-merge only if they are demonstrably stronger and contract-compatible; otherwise transplant bounded techniques or rebuild.
- [ ] Record exact acceptance shots/route and cost baseline before authoring.

### Phase 1 — source production

- [ ] Build/repair reproducible source with applied transforms/units and semantic naming.
- [ ] Author silhouette/meso construction first, then UV/material/wear/detail at screen-space-appropriate scale.
- [ ] Provide collision/interaction proxies and required sockets/markers.
- [ ] Build real decreasing LODs/HLOD/impostor strategy based on use, not an exported copy of LOD0.
- [ ] Retain source inputs, generator scripts, texture provenance, prompt/source records, and hashes.
- [ ] Produce contact/turntable/neutral evidence for critique, not as final acceptance.

### Phase 2 — release and runtime

- [ ] Validate glTF structure, normals/tangents, material/color-space roles, sockets, bounds, pivots, axes, LOD order, and texture references.
- [ ] Build release compression/KTX2/mesh optimization through existing tooling; compare visual delta.
- [ ] Register exact source/release identity and runtime mapping without duplicate filename tables.
- [ ] Prove prepare/admit/failure/cancellation/retry/cleanup and stable identity through LOD/frame-origin/instance changes.
- [ ] Ensure a pending asset cannot attack, collide, target, or offer misleading verbs as a placeholder.

### Phase 3 — game-camera review

- [ ] Ordinary route close/default/far, approach/recede, turn, acceleration, destruction/damage/interaction, and LOD transitions as applicable.
- [ ] Review under actual sector lighting, black-space negative space, bloom on/off diagnosis, reduced motion/flash, and supported UI/text scale when UI imagery is involved.
- [ ] Independent reviewer records concrete defects against identity/function, not a generic style checklist.
- [ ] Repair the largest coherent defects and run one causal re-review.

### Phase 4 — performance and promotion

- [ ] Matched before/after on identical route/settings/viewport/seed/hardware profile.
- [ ] Record admission latency, source/release bytes, texture/GPU residency, programs/materials, draw calls/primitives/triangles, LOD occupancy, frame p95/p99/hitches, resource high-water/end, and cleanup.
- [ ] Optimize via batching/instancing/material sharing/culling/LOD/HLOD/compression/cadence/preload, preserving accepted identity.
- [ ] Browser/Electron parity and exact manifest/source fingerprint.
- [ ] Promote only the exact accepted asset IDs/hashes and update the leaf receipt.

## Leaf write set

Every leaf names exact source, release, evidence, manifest, runtime map, focused test/check, capture/probe, and receipt paths before implementation. Shared renderer/loader changes require a separate runtime leaf with at least two representative consumers and characterization proving the shared defect.

Avoid editing `package.json` for aliases until direct commands pass and its mutex is free. Do not touch unrelated family source trees merely to normalize style.

## Non-goals

- Completing every visual family in one branch.
- A universal shader/material treatment applied to all assets.
- Replacing strong accepted work because a new tool exists.
- Fixed pass counts, technique quotas, triangle ceilings, one texture size, or “always use procedural/always use Blender.”
- Marketing renders that do not match in-game identity.
- Silent fallback/proxy acceptance.
- Reducing default quality to pass performance.

## Performance and quality budget

The leaf declares numeric baseline/after observations rather than arbitrary source limits. Required design posture:

- expected simultaneous count and screen-space class (hero/cast/crowd);
- LOD/HLOD thresholds and measured transition stability;
- material/program-sharing plan;
- texture formats/mips/color space and predicted/observed residency;
- instancing/batching and culling strategy for repeated/crowd families;
- no per-frame allocations or asset rebuilds;
- cancelable admission and full disposal; repeated route cycles return resources to a stable high-water band;
- no visible quality reduction in the accepted route.

## Review questions

- Does the asset communicate role/faction/function through construction and material, not a tint?
- Is it strong at the normal camera and still coherent close/far/motion?
- Do sockets, pivots, bounds, collision, and interaction agree with the visible object?
- Are LOD/HLOD/instance transitions stable and visually equivalent at transition distance?
- Does admission prevent misleading placeholders and clean up fully?
- Did the optimization remove invisible cost rather than authored quality?
- Would a screenshot from the actual route represent what a player receives?

## Stop conditions

- Exact leaf/route/owner/write set not selected.
- Active overlapping source/manifest/renderer/GPU owner.
- Unknown/ambiguous rights or non-reproducible source.
- Donor is weaker or contract-incompatible and no bounded transplant plan exists.
- Runtime requires a special path or duplicate registry.
- Sockets/transforms/proxies/LOD cannot be made consistent.
- Visual review rejects the normal-camera result.
- Performance can pass only by deleting accepted content or lowering default quality.
