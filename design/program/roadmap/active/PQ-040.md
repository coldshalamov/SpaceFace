## Outcome

Dynamic sprite, trail, authored-instance, and ship-auxiliary pools upload only the component span changed since the last acknowledged GPU upload while preserving the exact visible instances, matrices, colors, opacity, draw count, ordering, lifetime, growth, wrap, and teardown behavior. The ordinary proof route runs sparse and dense combat, trail churn, spawn/destroy, capacity growth, context recovery, and five-times population with identical presentation semantics; upload telemetry follows the dirty active span instead of allocated capacity and demonstrates a repeatable CPU/driver benefit or the abstraction is removed.

This packet starts with unleased pools. It does not seize `src/render/vfx.js` or any active VFX owner merely to make the migration list complete.

## Dirty-range contract

For each changed attribute, the owner records the lowest and highest changed **component** index in an unpublished pending span. Logical commits never call `addUpdateRange()` or set `needsUpdate` directly. Publication occurs only at the selected owner's chained pre-upload hook for an object that is actually about to draw—normally `onBeforeRender`, after any prior owner hook has run and after all ordinary writes, slot allocation, capacity growth, and attribute replacement for that draw have settled:

1. union every logical write with the unpublished pending span; a skipped/hidden/cull-only frame runs no pre-upload hook, allocates no public range, increments no attribute version, and never retires dirty state;
2. chain and preserve the existing pre-upload hook, invoke it first so any owner writes join the pending union, then resolve the **current** attribute object. When no generation is published, rebuild only this owner's public range metadata once, call `addUpdateRange(start, count)` once, retain the exact appended record, set `needsUpdate = true` once, record the resulting attribute version, move that span into an immutable published snapshot, and reopen an empty pending span for later writes;
3. after publication, never widen or republish the in-flight record from a logical commit. Any write that occurs before its callback—including a reentrant owner write from the chained upload callback—joins the separate unpublished next-generation span and cannot affect the upload already in progress;
4. chain and preserve any pre-existing `onUploadCallback`. At callback entry, require the current attribute and entry version to match the immutable published snapshot. Ordinary `bufferSubData` has already cleared the public list; initial `bufferData` must remove only the published snapshot's exact stale record by identity. Acknowledge and detach that snapshot **before** invoking the prior callback, run the prior callback under an upload-callback guard, and leave every callback-time owner write pending until a later pre-upload hook after `WebGLAttributes.update()` has returned;
5. existing chained callbacks must not directly call `addUpdateRange()`, `clearUpdateRanges()`, set `needsUpdate`, replace the tracked attribute, or otherwise change its version/range metadata. Characterization must prove that precondition. The adapter detects such mutation and fails the migration/evidence route rather than allowing Three.js to cache a callback-created version whose GL transfer never occurred;
6. first creation, ordinary capacity growth/reallocation **before publication**, and context restoration publish one full initialized-live-range generation on the final current attribute. If context loss or an interrupted renderer call leaves a published generation without a callback, record an explicit terminal `superseded-reset` state, remove only its exact owner record, carry the complete initialized union to the replacement attribute, and force a new full generation; superseded records are reported separately and cannot satisfy the steady-state allocation budget;
7. update active draw/instance count independently of capacity and publish logical/requested bytes, pending/published/acknowledged/superseded generations, range identity, attribute version, callback-guard violations, and cumulative `addUpdateRange()` counters without owner-created per-frame objects;
8. use a measured dense full-upload fallback only when its threshold is declared before capture and the complete initialized live range is published.

Three.js 0.184.0 allocates one `{ start, count }` record inside each `addUpdateRange()` call, clears ordinary partial-update ranges after `bufferSubData`, invokes `onUploadCallback`, and only then snapshots `attribute.version`. Initial `bufferData` also invokes the callback before Three.js snapshots the version and does not clear queued range metadata. Therefore owner writes remain unpublished until the actual pre-upload hook, callback-time writes are deferred to the next generation, and callback code may not mutate the public attribute version/ranges directly. Tests and telemetry count cumulative `addUpdateRange()` calls/record allocations, not only final `updateRanges.length`. Do not patch private Three.js internals or bypass the public range API without a separately reviewed version-pinned contract.

A zero-change draw performs no upload request or range-record allocation. A skipped-render `R1` followed by disjoint `R2` must keep only the owner-side union pending and publish `union(R1, R2)` once at the next actual draw. Growth anywhere in the 18-spawn-plus-one-integration pre-draw fanout must settle before publication so the replacement matrix/color/opacity attributes still allocate exactly three records total. Release via `ZERO_MATRIX`, immediate slot reuse, wrap, growth, callback reentrancy, interrupted upload, and context recovery must never expose stale GPU data.

## Performance and quality budget

- No per-frame allocation occurs in the pending-span utility or owner telemetry. The initial combat-plus-trail-streak stage permits only Three.js 0.184.0 range records: at most 23 cumulative `addUpdateRange()` calls/record allocations per ordinary actual-draw upload generation (four combat buckets × five dynamic attributes plus three trail-streak attributes), zero on unchanged or skipped/cull-only frames, at most 1,380 records/second at 60 acknowledged uploads/second, and at most 82,800 records in a 60-second target-profile window.
- The 23-record ceiling is independent of logical commit fanout and ordinary growth before publication. In the capital-debris regression, 18 spawn commits plus one integration commit and a capacity replacement before one draw still allocate exactly three trail records on the final matrix/color/opacity attributes; one-times and five-times population must not turn those writes into 57 records or the replacement into six.
- A context-loss/interrupted-render `superseded-reset` record is terminal recovery evidence, not an acknowledgement or an ordinary-budget success. Its old exact record and new forced-full publication are both counted and reported; any supersession in an uncontended ordinary target-profile window invalidates that window.
- Against the matched full-upload baseline, the initial stage adds no major GC, no more than one minor collection per 60 seconds, no more than 1.0 ms additional total GC pause per 60 seconds, and no more than 0.25 ms p95 GC-pause regression. Crossing any ceiling removes the range abstraction from that stage.
- Requested bytes follow the complete owner-side pending union published at the actual pre-upload hook, not total capacity, except explicit creation/grow/restore/full cases.
- Ordinary range metadata remains one public record and one attribute-version increment per changed attribute per actual upload. Owner pending state survives skipped renders, callback-time reentrancy remains unpublished until the next draw, and direct callback mutation of public range/version metadata is forbidden and fail-closed.
- The initial stage is retained only when sparse-route requested bytes fall by at least 25% and paired owner-plus-driver median time improves by at least 2% with a 95% paired interval excluding zero; otherwise it is removed even if correctness passes.
- Ribbon, authored-chunk, ship-auxiliary, and later VFX stages remain inadmissible until their packet revision declares numeric one-times/five-times aggregate records/upload-generation and records/second, the same or stricter GC limits, a population-scaled keep/remove threshold, and rollback behavior.
- Active count, capacity, high-water growth, wrap, release, acknowledgement, and reallocation remain explicit and deterministic.
- No stale matrix/attribute data may appear after skipped render, shrink, `ZERO_MATRIX` release, slot reuse, growth, or context recovery.
- Presentation output and default quality remain unchanged.

## Lab and broker gap

Pure tests can prove span math, acknowledgement transitions, and CPU-side buffer contents, but they cannot prove Three.js/driver upload behavior or visible output. After PQ-034's path-safe manifest loader is integrated and owner tests are green, add separate `performance-dirty-ranges-browser` and `performance-dirty-ranges-electron` manifests. Their literal contract test pins every acceptance-authority field. Each manifest owns one runtime kind, shares the same `sourceCandidateDigest`, scenario, harness, renderer, requested-byte, allocation/GC, and timer-confidence identities, and retains a distinct runtime broker candidate/artifact root. Direct probes remain non-promoting.

## Review questions

- Are all offsets/counts expressed in Three.js component units rather than logical items or bytes?
- Does the owner keep logical writes unpublished until the actual-draw pre-upload hook, publish once on the final current attribute after growth settles, and keep callback-time writes in a separate next-generation span?
- Do initial `bufferData`, ordinary `bufferSubData`, skipped render, grow-before-publication, callback reentrancy, interrupted-render supersession, shrink, wrap, `ZERO_MATRIX` release, slot reuse, and context recovery initialize every GPU-visible component without letting Three.js cache an unuploaded version?
- Does active draw count remain independent of allocation capacity?
- Is the chosen usage fixed before first upload and consistent with actual buffer lifetime?
- Did requested-byte reduction produce a repeatable owner/driver gain without changing output?

## Stop conditions

Return `BLOCKED` if the selected pool is leased, range units or the actual-draw pre-upload/acknowledgement lifecycle are ambiguous, an existing callback directly mutates tracked attribute version/range metadata, the candidate needs an unleased VFX/renderer owner, PQ-034's manifest loader/evidence binding is unavailable, a later stage lacks its numeric aggregate allocation/GC budget, or neither the public Three.js range API nor a separately reviewed version-pinned contract can meet the measured budget. Return `FAIL` on stale output after skipped render/release/reuse, identity/order/lifetime drift, any ordinary logical commit that publishes before the actual-draw hook, more than one cumulative public range-record allocation or attribute-version increment per changed current attribute in one ordinary actual upload, more than three trail records across the 18-spawn-plus-one-integration-plus-grow capital-debris fanout, callback-time writes folded into the already-uploaded generation, an ordinary target-profile supersession, any initial-stage allocation/GC ceiling breach, context-recovery divergence, or no repeatable benefit after correct integration. Never lower quality or pool population to continue.
