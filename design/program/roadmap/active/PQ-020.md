## Outcome

Ceres reads as a navigable industrial place rather than a loose pile of points: a civic/refinery
pocket, a production/mining pocket with one bounded existing-owner physical condition, a visible
transit/weigh checkpoint between the Helios and Tethys approaches, and an off-lane Cathedral
graveyard. Existing natural jobs and offscreen embodiment respond to industrial metadata, while map,
route, and physical positions remain exactly consistent.

The implementation is intentionally a small data/topology slice. It does not rewrite routing, traffic, the galaxy map, or World Site ownership to force the desired composition.

## Exact data lane

After live re-audit, the expected implementation remains five paths:

1. `src/data/sectors.js`
   - add Ceres industrial metadata such as `{ mining: true, refinery: true }` using current schema;
   - add one `poi_ceres_throughline` beacon declaration;
   - no unrelated Ceres edits.
2. `src/data/sectorAnchors.js`
   - add one local beacon anchor and existing lane-beacon asset identity;
   - keep `pos` canonical;
   - derive the map consumer's compatibility alias from the same object (`position === pos`) if the live consumer still requires it;
   - do not copy coordinates into another map owner.
3. `src/data/sectorZones.js`
   - recenter/tighten only the production belt if the route audit accepts the candidate;
   - encode one existing-owner local mechanical condition here only if the live schema already
     supports it; otherwise stop and create a narrow owner packet rather than accepting labels alone.
4. `src/data/authoredPlaces.js`
   - append one no-presence transit/checkpoint zone with exact local center/radius and DMC identity;
   - no RNG, global coordinate, discovery store, or new registry slot.
5. `test/pq020-ceres-topology.test.mjs`
   - exact IDs/math/round trips/consumer equality/non-drift;
   - live and offscreen metadata effects proven separately;
   - route destinations remain stations where required; beacon does not invent freight behavior.

If live code has moved, preserve these responsibilities but update paths in the claim receipt. Any need to edit galaxy-map, Atlas-index, traffic, embodiment, renderer, save-schema, or registry code is a stop/shared-owner request, not silent scope growth.

## Non-goals

- A new sector router or forced Helios→Tethys path through Ceres.
- A traffic attraction system for the beacon.
- New jobs, producers, embodiment schema, save store, registry slot, map implementation, renderer
  path, Cathedral state, or a new condition system.
- Moving existing stations/gates/fields/POIs to make the screenshot prettier.
- Multiple checkpoint assets or a broad Ceres art overhaul.
- Calling projected offscreen intent visible traffic.

## Performance and quality budget

- One static beacon/place and one no-presence zone; no added ambient spawn budget.
- Industrial metadata may alter role composition but not the existing live/offscreen caps.
- No new per-frame scans or destination search; use existing indexed owners.
- One admitted existing beacon asset, shared/cached materials, ordinary culling.
- No new save object; static content refresh/materialization is idempotent.
- Map labels must remain readable without suppressing Cathedral/beacon/civic/production identity.
- Matched route must not regress target/floor p95, p99, hitch count, map-open, or sector-entry beyond the declared packet threshold; investigate any regression causally rather than lowering quality.
