## Outcome

A stranger plays fifteen minutes — swarm first, then one adventure loop — on the owner's
integrated-GPU laptop and never once sees the ship lose its place, the fight freeze, an object
blink out, or an effect sit still. The owner signs the five demo bars in
[`DEMO_READINESS_2026-09-20.md`](../../DEMO_READINESS_2026-09-20.md) §1.

## Source

Owner direction 2026-09-20 (quoted at the head of the program document). Evidence: the live
readings in that document §2, reproducible in one minute with `npm run probe:smooth-flight` and
`npm run probe:smooth-flight:crucible`.

## How agents get this wrong

Warming synthetic stand-in materials instead of the real authored ones (measured 2026-08-28: the
live program key differs in five fields; stand-ins never converge). Spawning sim entities to warm a
hull (determinism). Lowering default quality, lights or hull detail to pass a frame number.
Declaring a perf win from a run without the whole-machine CPU line beside it — the same build read
59 fps and 40 fps minutes apart on 2026-09-20. Answering "limp" with more particles or shake
instead of the missing channel (it was sound, and effects silently stripped). Re-pinning the old
behaviour green: a draw-first frame, a pose hold against a running sim, a silent OS motion default.
Launching a long capture to close a leaf; every instrument here is one minute.

forty-screen frontend program (that stays `PQ-194` and §20). Any multi-session battery.

## Closing

Run both probes on a quiet machine. If swarm holds 60 with no freeze over 100 ms, nothing on the
glass unloads, every hit answers with sound, and the three demo screens read as hardware — hand
the owner the controller and stop.
