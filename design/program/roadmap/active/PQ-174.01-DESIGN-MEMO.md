# PQ-174.01 — DESIGN MEMO: ship sixty-second harvest waves

Author: GPT-6 Astra (codex, reasoning=high), read-only, 2026-09-10. Commissioned by the campaign
controller after the 2026-09-07 measurement pass concluded that no kill quota can satisfy the band.

**Ship sixty-second harvest waves.**

1. **The mechanism, in two sentences**

A wave ends after sixty seconds of active combat, regardless of kills; surviving enemies remain in play as the next wave begins. Killing efficiently earns more score, salvage and four-second openings through the existing pressure reservoir, while the reinforcement stream keeps supplying the fight until the boundary.

2. **Why the quota model cannot be rescued**

“Clear N kills” makes wave duration the **first time cumulative kill throughput reaches N**. That throughput depends on encounter geometry, target availability and kit efficiency; because deaths also create reinforcement opportunities, the player’s killing performance influences both progress and the supply of subsequent targets.

A quota changes the amount of work without removing this dependency. Under the optimistic approximation that throughput stays constant:

- Fastest completed cell: Physics/4242, `15 / 22.733 = 0.660 kills/s`.
- Slowest completed cell: Massline/8008, `15 / 51.733 = 0.290 kills/s`.
- Keeping the fastest above 45 seconds requires approximately **30 kills**.
- Keeping the slowest below 90 seconds permits at most **26 kills**.

There is no overlapping quota. Actual starvation makes the constant-throughput approximation optimistic, consistent with the failed tuning pass.

Strictly, the receipt contains **eight completed seed–kit cells across three seeds**, plus the Pulse/8008 death. The design must not count that death as a completed short wave. 3. **The exact implementation contract**

The seam is **`planWave(input) → plan.completionRules → survivalWave._checkCleared() → run:waveCleared`**. Keep that architecture and the existing phase machine.

The live streaming and completion owner is `survivalWave.js`. `survivalSwarm.js` is a ruleset helper, not the runtime state owner.

| Module | Required contract |
|---|---|
| `swarmMode.js` | Export `SWARM_WAVE_DURATION_TICKS = 3600`; increment `SWARM_SCHEMA_VERSION` to `2`. |
| `survivalWavePlanner.js` | Keep `planWave(input)` and `planSwarmWave(...)` signatures. Add `kind: 'duration'` and `durationTicks: 3600` to swarm `completionRules`. Preserve `requiredPackagesMaterialized: false`, `blockingRoles: []`, and `cleanupTicks: 45`. |
| `swarmMode.js` | Replace `swarmPlanBlock(wave).quota` with `rewardReferenceKills`, using the existing quota curve’s numbers solely to preserve per-kill chip valuation. Remove `requireBoss` as a completion condition. |
| `survivalWaves.js` | No recipe or signature changes. The pinned authored waves remain intact; the swarm planner generates its own plans. |
| `survivalWave.js` | Own `_waveStartedSimTime` and `_durationTicks`. Set them when `run:waveStarted` activates the planned wave; clear them on teardown/reset. |

The completion contract is:

```js
// In survivalWave, for the existing swarm ruleset:
elapsedSeconds = state.simTime - this._waveStartedSimTime;
durationSeconds = this._durationTicks / 60;
progress = clamp(elapsedSeconds / durationSeconds, 0, 1);

// Existing pressure curve; its input now means elapsed-time fraction.
target = Math.min(
  this._concurrent,
  swarmPressureAt(this._wave, progress)
);

// Existing scheduled arrivals and reservoir-controlled stream continue.
// Neither kill count nor a depleted "remaining quota" stops them.

if (
  run.phase === 'active' &&
  playerIsAlive &&
  !this._cleared &&
  elapsedSeconds >= durationSeconds
) {
  // Existing completion seam, exactly once.
  emitWaveCleared({
    completionKind: 'duration',
    durationTicks: this._durationTicks,
    killed: this._resolved,
    survivors: this._cohort.size
  });
}
```

Retain the existing receipt fields for wave, admissions, requests, starvation and tick; remove the quota field. Death ends the run, including a death at the boundary; it must not earn a surviving-wave award. Pausing must freeze simulation time. Menus and introductions occur outside the wave’s active interval.

**Every swarm wave uses this rule, including boss waves.** A living champion carries forward with its identity, health and momentum intact. It remains dangerous and pays its kill reward only when actually killed; the clock never fabricates a boss kill. Keeping boss death as an additional gate would reintroduce an unbounded duration.

**Reservoir composition is mandatory:**

- Preserve the existing three-kill threshold, 240-tick hold, bounded spend, telegraph and empty-board emergency. The receipt demonstrates `10 → 7 → four seconds → 10`; these are earned openings inside the combat minute. [Reservoir receipt](C:/Users/93rob/Documents/GitHub/SpaceFace/design/program/roadmap/receipts/PQ-174.08-REPORT.md:19)
- Remove the unconditional reservoir reset in `swarmArena._onWavePlanned()` for consecutive waves of the same run. Carry remaining hold time and stored pressure; reset on a new run or teardown.
- Wave-opening packages must not refill a protected hole. During a carried hold, suppress ordinary opening top-ups and defer champion arrivals until the hold finishes. Retain the empty-board emergency as the exception.
- Retain the hold’s remaining active ticks through cleanup, introductions and menus. Do not restart it, immediately spend it, or release its stored count above the new wave’s permitted deficit.
- Across automatic cleanup/introduction transitions, permit the existing stream’s **empty-board emergency only**, using the carried cohort and current plan. This uses the same materialization path and prevents a boundary from disabling the emergency.

Three connected consumer changes complete the contract:

- **Rewards:** `survivalRewards.chipValueForPlan()` divides by `rewardReferenceKills`. Every actual kill continues paying the existing score/style, XP and chip rewards, including kills beyond fifteen. There is no exhausted reward purse or score ceiling at the former quota.
- **Presentation:** replace `KILLS x / quota` with `NEXT WAVE 0:SS`; progress represents elapsed time. Publish a derived `run:waveProgress` payload `{ wave, remainingTicks, durationTicks }` from `survivalWave` at activation and when the displayed second changes. The HUD consumes it; it owns no gameplay clock. Announce **“Wave N survived”**, and use actual kills for any tally—the current announcer incorrectly uses admissions.
- **Legality:** the current `swarmLevel(wave)` increases level through eight. For this contract, return **1 at every swarm wave**, including opening and reinforcement materialization. This closes an existing route to HP escalation; count, composition, mass, hazards and bearings carry the difficulty curve. Update `swarmCurveIsSane()` to validate duration and concurrency instead of quota margins.

Keep draft cadence at five and refit cadence at ten. Preserve existing seeded spawn selection; the timing rule introduces no random draws.

4. **Predicted effect on the band**

For a cell that survives, the active wave lasts **60.000 seconds**, with at most one fixed timestep—**0.0167 seconds**—between the deadline and its observation by the phase machine.

Therefore:

| Measurement | Existing | Proposed |
|---|---:|---:|
| Completed-wave range | 22.733–51.733 s | 60.000–60.017 s |
| Range width | 29.000 s | ≤0.017 s |
| Extra wave-one combat, fastest cell | — | 37.267 s |
| Extra wave-one combat, slowest cell | — | 8.267 s |

The duration spread contracts by **more than 99.9%** because kill throughput no longer determines the boundary. This is a consequence of the contract, **not a measured gameplay result**; survival and engagement still require implementation evidence.

The fast player spends those additional 37 seconds harvesting more enemies, exploiting clear-created openings, collecting chips and setting up the next physical kill. The stream does not stop at kill fifteen. Existing physics style rewards continue applying throughout the same earning window; this memo does not claim to establish the separate physics-versus-gun scoring bar.

5. **What it costs**

**Mastery loses faster wave advancement.** A strong player cannot accelerate roster unlocks or reach the fifth-wave draft sooner by clearing efficiently. The first draft moves to approximately five combat minutes, plus transitions.

In exchange, mastery buys greater earnings and control within a predictable interval. Accept the resulting variation in salvage per wave: preserving per-kill value means a productive player can earn substantially more before advancing.

The other deliberate cost is **automatic escalation for weak clearing**. A slow player advances with unresolved enemies, potentially including champions. The clock guarantees cadence, not survival or a clean battlefield. Boss defeat also ceases to define a wave boundary. These are meaningful losses of the quota model’s progression semantics.

6. **The falsifier**

Run **Helios Core, seed 4242, `physics_toolkit`**, using the measurement pass’s same driver and loadout.

Measure **quiet seconds during wave one from 22.733 seconds through 60 seconds**, using the existing printer’s definition: a whole second containing no kill, verb, moment or shot.

**Any quiet second falsifies the claim that extending the fastest cell creates continuous playable combat.** This is the decisive risk: a timer can satisfy duration while extending a depleted farm. Four-second reservoir openings must remain opportunities to act among surviving enemies.

7. **Two implementation prohibitions**

- **Do not implement `elapsed >= 60 && kills >= quota`, retain the quota-based reinforcement stop, or wait for a boss/last survivor.** Any of these restores throughput-dependent duration or turns the added time into waiting.
- **Do not satisfy the clock by erasing earned space or slowing bodies.** No boundary reservoir reset, catch-up flood, hidden HP escalation, drag, momentum clamp, gyro or instantaneous counter-thrust.

**The 45–90-second band should remain.** A single 23-second introductory wave could be enjoyable, but these measurements do not establish that the shorter cadence produces the intended fifteen-minute experience. Sixty seconds gives each composition time for repeated clear–breath–arrival cycles while keeping progression predictable; I would change the ending mechanism before relaxing the band.
