## Outcome

SpaceFace ships on a supported Electron major while preserving the canonical Browser/Electron game route, security boundaries, lifecycle behavior, saves, input, audio, controller support, display handling, packaging, hardware acceleration, renderer identity, and deterministic/presentation semantics. The migration uses temporary compatibility checkpoints at Electron 37, 40, and 43 to isolate accumulated breaking changes; only the final supported line remains in the accepted dependency graph.

Support and security justify leaving Electron 31 even if matched performance is neutral. No checkpoint may create a browser-only gameplay fork or relax security to make the shell launch.

## Checkpoint contract

For each temporary checkpoint:

1. update Electron and the lockfile without unrelated dependency churn;
2. record resolved Electron/Chromium/V8/Node/ANGLE identities;
3. run focused non-headed shell, security, lifecycle, save/path, input, display, audio/controller, isolation, and package-layout contracts;
4. run `npm run build:bundle` followed by `npx electron-builder --dir --publish never`, hash the generated executable/package tree, and reject source-checkout launch as packaged proof;
5. after acquiring `browser-gpu`, publish the same deterministic/presentation route through the paired Browser/Electron broker manifests; the Electron producer must include the owned packaged-startup subroute against that exact generated executable;
6. run the fingerprint/package/source-bound platform checker, repair only documented or reproduced compatibility failures, and preserve a checkpoint receipt/diff summary before advancing.

Checkpoint versions are migration aids, not retained release branches. The final accepted diff contains only the supported target line and required compatibility code.

Gate order is strict: L0-L2 are non-headed only. Then acquire `browser-gpu`, build the unpacked package, run `performance-electron-modernization-browser` followed by `performance-electron-modernization-electron`, and only then run the fingerprint-bound `check:m6:platform` matrix. `check-electron-new-game-launch.mjs` is no longer a pre-L3 acceptance gate; its route is isolation-safe diagnostic coverage, while the broker-owned Electron release soak is authoritative. A checkpoint may not consume headed or packaged evidence from a different package, lockfile, source, or `sourceCandidateDigest`.

- `package` — dependency and lockfile graph.

## Non-goals

- Changing gameplay, visual quality, render scale, population, or default effects to offset runtime differences.
- Replacing Electron, moving to a native shell, or adding a second desktop route.
- Broad IPC/preload expansion, Node integration, disabled context isolation, or security relaxation.
- Retaining three supported Electron versions or permanent compatibility branches.
- Upgrading unrelated dependencies merely because the lockfile is open.
- Claiming performance improvement when the supported runtime is neutral.

## Performance and quality budget

- Browser/Electron deterministic and presentation-semantic results remain equivalent.
- Canonical launch, first controllable flight, save/load, station/dock, input/audio/controller, and lifecycle behavior do not regress.
- Hardware acceleration and the expected renderer/ANGLE path are active on accepted evidence; software fallback is reported, never hidden.
- Startup, first-visible, frame, GPU, memory, source-route, and generated-package differences are reported separately at each checkpoint.
- Every promoted Browser/Electron release-soak receipt resolves a consumed broker claim and shared `sourceCandidateDigest`; direct producers and source-only package claims are non-promoting.
- Security settings stay equal or stronger; no permanent evidence/test override reaches normal play.
- Final lockfile contains the selected supported Electron line without unrelated dependency churn.

## Lab and broker gap

Focused tests and `check-electron-platform-contracts.mjs` validate non-headed launch/platform structure, but native process/GPU/package claims require the paired `performance-electron-modernization-browser` and `performance-electron-modernization-electron` broker routes. Add them only after PQ-034's path-safe loader and checkpoint-focused gates pass. The approved release-soak wrappers must consume their externally issued claims, and the evidence checker must resolve each `claimId` against the canonical consumed ledger rather than trusting a receipt field. Both receipts require equal `sourceCandidateDigest`, distinct runtime `candidateDigest`, and the Electron receipt additionally binds the just-built unpacked executable and packaged-startup subreceipt. `check:m6:platform` consumes those two receipts; direct `runReleaseSoakCli`, `check-electron-new-game-launch`, or source-checkout Electron evidence cannot promote.

## Review questions

- Is every shell/code change required by a documented or reproduced runtime incompatibility?
- Are context isolation, Node integration, sandbox/preload, CSP, protocol, and single-instance policies equal or stronger?
- Do Browser and Electron still run the same game and produce equivalent deterministic/presentation results?
- Are save paths, packaged assets, `app.isPackaged`, lifecycle, input/audio/controller, display changes, and crash recovery proven from the generated executable rather than the source checkout?
- Do Browser and Electron evidence each resolve a consumed broker claim, share `sourceCandidateDigest`, retain distinct runtime candidate digests, and feed the same M6 checker?
- Is hardware acceleration active with exact Chromium/V8/ANGLE/renderer identity recorded?
- Did dependency/lockfile changes stay limited to the runtime migration?

## Stop conditions

Return `BLOCKED` if package/electron/lifecycle/broker/GPU owners conflict, the supported target changes and has not been revalidated from primary references, `build/web` or electron-builder unpacked packaging is unavailable, either runtime manifest cannot publish consumed-claim release-soak evidence, the generated executable cannot be identified safely, or a required change expands into an unowned shell/security redesign. Return `FAIL` on route/semantic divergence, security relaxation, direct/unclaimed evidence reaching M6, missing `app.isPackaged` proof, broken packaged asset/save/`userData` behavior, software rendering on expected hardware without understood cause, leaked PIDs/listeners/profiles, stale/mismatched source/package fingerprints, or unresolved checkpoint regressions. Performance neutrality is not failure; unsupported Electron 31 is not retained for a neutral result.
