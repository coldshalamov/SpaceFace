## Outcome

The player can read force, mass, velocity, attachment, charge, danger, damage, targeting, and recovery through a coherent hierarchy of motion, VFX, audio, camera, HUD, and accessible fallback cues. The game should look more spectacular—not more restrained—while every effect remains mechanically truthful, bounded, and usable in dense play.

PQ-023 is an umbrella. Implement separate leaves with distinct owners and routes:

1. **Physics cue vocabulary:** shared cause/state/intensity/ownership semantics for boost, RCS, Massline, fields, gravity, impacts, payload load, and recovery.
2. **Propulsion:** idle/cruise/boost/RCS/socket families and heat/load response.
3. **Weapons/impacts/destruction:** mechanically distinct projectile/beam/plasma/missile/flak/impulse and damage phases.
4. **Localized environment:** sector-specific depth, lighting, dust/debris/nebular structure without lifting all space into haze.
5. **HUD physics telemetry:** hierarchy for target, mass/load, Massline state, boost, fields, damage, warnings, and next action.
6. **Camera language:** acceleration, bank, scale, focus, impacts, tethers, planets, and reduced-motion alternatives.
7. **Dense-scene convergence:** cue arbitration, pooling, occlusion, accessibility, and target/floor performance across representative combat/travel/mining scenes.

A leaf may coordinate two cue channels when one mechanical event requires them, but it may not redesign every presentation surface at once.

## Entry conditions for a leaf

- [ ] Exact mechanical owner events/state and ordinary route traced.
- [ ] Existing VFX/audio/camera/HUD/profile owners and current cues characterized.
- [ ] Largest player readability/quality failure reproduced in motion, not inferred from source style.
- [ ] Renderer/VFX/HUD/styles/audio/camera/GPU mutexes free for the selected leaf.
- [ ] Baseline capture includes normal and dense representative scene, reduced-motion/flash, and target/floor cost.
- [ ] Cue can be expressed as a consumer of owner truth; no presentation-owned gameplay state.

## Cue contract

Every admitted cue family maps:

```js
{
  cueId,             // stable semantic ID
  sourceOwner,
  sourceReceiptId,
  state,             // armed/latched/taut/releasing/broken/etc.
  intensity,         // normalized from authoritative physical values
  origin,
  direction,
  targetId,
  priority,
  lifetimeTicks,
  accessibilityText,
  reducedMotionMode,
  reducedFlashMode
}
```

Exact fields follow current profile/event conventions. Identity and intensity derive from gameplay owners; rendering/audio/camera/HUD only project them. Event arrival order must not decide durable state. Transient duplicate suppression uses stable receipt/cue IDs and bounded windows.

For each mechanical state, specify:

| Question | Required answer |
|---|---|
| What caused it? | exact owner event/projection |
| What should the player infer? | force, ownership, risk, timing, direction, success/failure |
| Which channels carry it? | motion/VFX/audio/camera/HUD/text/haptic where applicable |
| What is critical vs flavor? | critical semantics survive channel reduction |
| How does it scale? | physical intensity and screen distance, bounded/capped |
| What is counterplay? | cue exposes a decision/window, not only spectacle |
| What happens in reduced motion/flash or no audio? | static/low-motion/text/non-color equivalent |
| How is cost bounded? | pool, cadence, culling, instancing, priority/arbitration |

## Work breakdown for a leaf

### Phase 0 — event and perception audit

- [ ] Trace exact owner event/state and current presentation consumers.
- [ ] Record state machine, physical ranges, duplicate/replay behavior, and current accessibility semantics.
- [ ] Capture current cue at normal route and dense stress route with motion/video where needed.
- [ ] Identify the smallest set of perceptual dimensions needed: silhouette, direction, phase, rhythm, color/value, scale, persistence, sound, camera, text.

### Phase 1 — declarative profile and focused contracts

- [ ] Extend one existing declarative cue/VFX/audio/camera/HUD profile rather than branching on feature names across render code.
- [ ] Normalize physical intensity once; cap and quantize where needed for deterministic/bounded presentation.
- [ ] Test owner-event mapping, phase ordering, duplicate suppression, cleanup, fallback semantics, and reduced modes.
- [ ] Preserve one gameplay/render route across Browser/Electron/probes.

### Phase 2 — implementation and composition

- [ ] Implement pooled/instanced/shared-resource presentation with no per-frame allocation.
- [ ] Bind to exact sockets/positions/directions and frame-origin/interpolation path.
- [ ] Add cue-priority/arbitration so critical state survives dense scenes while flavor degrades gracefully.
- [ ] Coordinate channels: camera cannot fight targeting; HUD cannot cover playfield; audio/flash cannot be the sole critical cue.
- [ ] Keep hidden/inactive UI/effects asleep and fully disposed.

### Phase 3 — independent motion review and tuning

- [ ] Review at normal camera, close diagnosis, far/readability, dense overlap, damage/failure, and reduced variants.
- [ ] Use a small predeclared parameter matrix tied to physical outcomes, not unrecorded taste iteration.
- [ ] Select values once from quantitative readability/performance plus independent player judgment; pin them in focused tests/profiles.
- [ ] One causal re-review verifies fixes; unrelated style ideas become future leaves.

### Phase 4 — route/performance closure

- [ ] Browser/Electron ordinary route with source fingerprint and exact cue IDs.
- [ ] Target/floor matched before/after: frame phases, particles/sprites/lights, draw calls/programs, DOM/compositor, resources, hitches, cleanup.
- [ ] Dense scene preserves critical cue accuracy and target selection while remaining within profile contract.
- [ ] No accepted visual quality removed or default settings lowered.

## Leaf write set

Name exact current profile, consumer, focused test/check, route harness, and receipt paths. Shared renderer/VFX/audio/HUD/camera changes need characterization and at least two representative consumers when they claim a general abstraction. Avoid `package.json`, input, gameplay owners, save schema, registry order, and unrelated CSS unless separately leased.

## Non-goals

- A universal aesthetic recipe, fixed palette, bloom ban, or one effect for all mechanics.
- Presentation-owned combat/physics/target/save truth.
- Full HUD rewrite during a propulsion leaf.
- Camera motion that steals control or obscures aiming.
- Full-screen fog/post effects used to hide weak assets.
- Reducing particle quality, render scale, shadows, bloom, content, or authored assets to pass performance.
- Exact effect-count tests that do not prove player perception.

## Performance and quality budget

Every leaf declares:

- maximum simultaneously active cue instances by priority/class;
- pool caps and exhaustion behavior preserving critical cues;
- emission/update cadence and distance/screen-size culling;
- instancing/batching/material/program sharing;
- dynamic light and post-processing budget;
- DOM/compositor/listener/observer behavior for HUD;
- no hot-path allocation/resource creation;
- baseline/peak/end resource high-water and cleanup;
- target/floor matched route and dense-scene thresholds.

Quality scales through hierarchy and priority, not wholesale deletion. When overloaded, retire low-priority flavor first while retaining mechanical state, direction, timing, and accessible fallback.

## Review questions

- Can a player infer what force/state happened, from where, to whom, and what decision follows?
- Are boost, Massline, gravity/fields, impacts, and weapon families mechanically distinct rather than recolors?
- Does spectacle reinforce scale and physics without burying targets, projectiles, or interaction cues?
- Do reduced-motion/flash, no-audio, forced-colors, and increased text scale preserve critical meaning?
- Are cue lifetimes/pools/resources bounded and fully cleaned up?
- Is the accepted result stronger in motion at the real camera, not merely more effects in an isolated preview?

## Stop conditions

- Mechanical owner event/state is ambiguous or unavailable.
- Leaf requires gameplay mutation or another cue truth store.
- Shared presentation path is actively leased.
- Dense critical cues cannot survive the proposed effect stack.
- Accessibility requires removing the only mechanical signal rather than adding an equivalent channel.
- Browser/Electron or interpolation/frame-origin identity diverges.
- Performance can pass only by lowering default quality or deleting required spectacle.
