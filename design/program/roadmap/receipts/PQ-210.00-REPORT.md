**Date:** 2026-09-21 · **Host:** owner's Intel iGPU (ANGLE D3D11), 14 logical cores

## Headline

Two things were found. Only one of them is this leaf.

1. **Master could not boot.** `src/render/renderer.js` at `8bd74e938` imported eleven names that
   no committed module exported. Fixed and landed: `1fb73f11a`, `65f58b9f9`.
2. **The roster prewarm costs more than it saves, and the result everyone quoted was measured in
   an empty window.** Five matched runs below. The leaf is **not closed** and the publisher is
   deliberately left unwired, with the reason written beside the missing lines in the code.

## 1. The broken link (landed)

`renderer.js` on master asked `visualFactory.js` for `asteroidLeafResources`,
`asteroidVisualExemplarSpecs`, `buildAsteroidLeafWarmGroup`, `combatSpawnableExemplarSpecs`,
`instantiatePackagedPrimitives`, `wreckVisualExemplarSpecs`; `asteroidInstancePool.js` for
`reserveAsteroidInstanceCapacity`, `warmAsteroidInstanceVariants`; and `partsLibrary.js` for
`warmRenderPackageShipPool`, `poolWitnessPalettesForState`, `rosterPoolWitnessFilePalettes`.

All eleven existed only in the working tree. A missing named export is an **ES-module link
error**, so `renderer.js` never evaluated and every route that draws the world came up blank.

Proof (not inference) — `git archive HEAD src` into a scratch snapshot, then link the module:

```
SyntaxError: The requested module './visualFactory.js'
  does not provide an export named 'asteroidLeafResources'
    at src/render/renderer.js:20
```

After `1fb73f11a` the same probe moved one import down to `partsLibrary.js`; after `65f58b9f9`
it prints `RENDERER LINKED OK`.

**Why no gate caught it:** `check:baseline` and every probe read the **working tree**, where all
three files carry their definitions uncommitted. Lanes ran green over a master that could not
boot. This is the `working-tree-green-masks-red-HEAD` failure in its most expensive form — not a
golden drifting, the whole renderer.

### The instrument defect this set exposed, and the fix that landed

The sample window opens at flight start and runs 30 s. Whether a wave arrival falls inside it is
**not controlled**, and in A, B and C **no wave materialized at all**. Their link counts describe
a window in which nothing spawned. Four runs were compared on link count before anyone noticed
that only one of them contained a wave — so the headline result of run B, "the prewarm takes
links to zero", is measuring an empty window, not a warm roster.

`scripts/probe-smooth-flight.mjs` now prints a `wave arrival in window` line directly above the
link counts, saying COVERED or NOT COVERED in words, so two runs can only be compared when both
say COVERED. That line is the first thing a follow-up should keep.

### The brief's diagnosis does not reproduce at today's master

The packet blames "the driver linking and uploading hull types the GPU has never drawn", about
22 s into seed 4242. With the emitter off, the probe's new link attribution names both links:

```
+0.5s   (depth,highp,srgb-linear,false,,uv,false,)   via Asteroid_308
+21.9s  (depth,highp,srgb-linear,false,,false,fal)   via Asteroid_369
```

Both are **asteroid shadow-depth programs**, not hulls — and the second is the ~22 s event the
brief attributed to a wave arrival. Six render commits have landed since the 2026-09-20 reading.

### Both wired configurations are regressions

- **With the part catalog** (B, E): launch-to-flight goes 63 s to 205–371 s. The catalog promotes
  1700–4600 instanced-pool roots, and `cook.rockPools` costs roughly **0.1 s per root** — that
  rate is the same with the prewarm off (7.8 s for 57 roots), so the prewarm does not make
  rockPools slow, it multiplies its input by about 30x. Run B looks *faster* than E only because
  its cook budget expired and skipped `cook.rockPools` entirely.
- **Without it** (D): 94 s, and in the one covered window it showed **more** program links (15)
  and 108 first-draw uploads, plus a 183 ms frame with **142 ms of admission** 0.7 s after
  `run:waveMaterialized w1`. The exemplar cohort drains its own compiles into flight.

The fps and p50 deltas are **not attributed**: every run was taken at 49–63 % whole-machine CPU,
and this host has previously read 59 fps and 40 fps on the same build minutes apart. Load time is
the contention-independent number, and it is the one that condemns the wire.

## 3. What landed

- **`1fb73f11a`, `65f58b9f9` — the broken link, repaired. Master boots.**
- `src/render/renderer.js` — the prewarm path scoped to what its own design says, so the dead
  code the next engineer inherits is not also a trap:
  - `_admitRosterPartCatalog` no longer appends the whole-ship archetype and LOD-sibling sweep
    (`spawnableShipArchetypePrewarmUrls()`), which is what took a catalog its own header calls
    "~30 small GLBs" up to 140 files, and it instantiates lod0 only — the live attach path mounts
    lod0, so lod1/lod2 holders are warmth the production draw never reuses.
  - the per-slot **palette band** is gone. A palette is a material colour, not a program feature:
    three.js keys the program cache on defines, so the band linked nothing the fallback band had
    not already linked, while producing 1598 seal units over 4588 pool roots.
  - the `settleCapMs` 45 s to 120 s raise is reverted. It was fitted to a cook this commit
    shrinks, and run C shows the cohort still did not fit inside it.
- `src/systems/survivalArena.js` — the publisher, built and documented, **deliberately not
  subscribed**, with the three missing lines quoted verbatim in `init()` beside these numbers.
  `enemyIds` publishes the full union every wave (the receipt of what the ruleset can field);
  `specs` carries only hulls this run has not published yet, because the renderer discards a
  repeat exemplar by id and the old code spent **1.28 ms** rebuilding the 12-hull swarm union on
  every `run:wavePlanned` — the exact frame this leaf exists to keep cheap. The warm ledger
  expires on `run:ended` (mirroring `_releaseSurvivalRosterPrewarm`) and deliberately **not** in
  `_reset()`, which also runs on every wave clear.
- `scripts/probe-smooth-flight.mjs`, `src/core/perfCounters.js`, `src/render/glInstrumentation.js`
  — the link-attribution instrument that produced every finding here: wave lifecycle times beside
  freeze times, per-link program name plus stack plus admission subject, in-frame vs off-frame
  link split, a hidden-exemplar readiness audit, and the new COVERED / NOT COVERED verdict.
  `perfCounters.js` and `glInstrumentation.js` were CRLF-damaged on disk (721 and 196 lines);
  normalized to LF before staging, which is why their real diffs are 36 and 4 lines.
- `test/survival-arena-roster-prewarm.test.mjs` — 7/7, including a guard that fails if the wire is
  restored without reading this receipt.

## 4. Leaf state: `ready`, not closed

The done-when is **0 frames over 100 ms in 30 s, worst 60 ms or less**, and no configuration
reached it; the best measured one is the unwired game at 2 frames and 167 ms, on a 58 %-busy host.
Nothing here is a number to sign the leaf off on. The next engineer's order:

1. **Make `cook.rockPools` stop being O(roots) at ~100 ms each.** It is the single reason the
   prewarm cannot be afforded, and it is a defect in its own right — 7.8 s for 57 roots on a cold
   Crucible launch with no prewarm at all.
2. **Re-measure on a quiet machine**, and only compare runs whose `wave arrival in window` line
   says COVERED.
3. Warm the two rock depth programs first (`buildAsteroidLeafWarmGroup` and
   `warmAsteroidInstanceVariants` already do exactly this). That is the whole measured defect at
   master today, and it needs neither the hull roster nor the catalog.
4. Only then restore the three `init()` lines, and re-check launch-to-flight against the 63 s
   baseline in the table above.
