1. DESIGN
Composing caller cancellation with runtime retirement into one effective signal conflates two lifetimes. A caller AbortSignal means "I no longer need this one package"; runtime retirement means "the whole renderer/generation is dead." The diff keeps them separate in some places (caller signal only races `waitForAuthoredAssetTask`, runtime signal drives fetch) but then merges them inside `createGpuResidencyAdmissionTracker.prepare` (lines 1318-1326) where `options.signal` and the entry's own controller are combined and forwarded as one `signal` to `prepare()`. That is the wrong shape: the downstream `prepare()` cannot tell a caller abort (drop one admission) from owner disposal (retire everything), and disposing the tracker cancels the combined signal, making a caller abort indistinguishable from a runtime teardown. The sound shape is to keep the caller's signal as an independent race/receipt (like `waitForAuthoredAssetTask`) while the runtime's own `AbortController` governs fetch/decoder lifetime; never forward a combined signal into work that outlives one caller.
2. THE BUG
Most likely the signal is dropped at line 235-238 in `loadAuthoredRenderPackagePilot`. The task passed to `admitAuthoredAssetTask` closes over `runtime.renderPackages.load(...)` and passes only `signal: runtime.signal`; the caller's `options.signal` is never forwarded into the package load. `waitForAuthoredAssetTask` only races the outer task promise, so if `renderPackages.load` ignores the runtime signal (or if the test probes an inner "effective" signal that expects both inputs), `external.abort()` leaves the composed promise pending and `composed.aborted` stays false. The single best hypothesis: the caller `signal` option is read for the early-return and race, but never wired into the actual `renderPackages.load` call, so cancellation never reaches the work.
3. RISK ON THE HOT PATH
The single most dangerous change is in `createGpuResidencyAdmissionTracker.dispose` (lines 1246-1265): it iterates pending entries and calls `entry.resolveCompletion(cancelled)` directly from the owner. If the underlying `prepare(subject, nextOptions)` also settles normally a microtask later, `finish()` will attempt `resolveCompletion` / `rejectCompletion` a second time. Double-settling the same promise is silent in JS, but the pattern creates a race where a late success can overwrite a cancellation receipt or vice versa, and any consumer keying on `entry.settled` can observe torn state. Combined with the boot path's shader-compile cohort, an early dispose can turn a load that used to finish into a settled-with-cancelled receipt while the GPU work still completes, or a never-resolving outer promise if the caller awaits the task instead of the receipt. That argues for shelving until route evidence exists.
