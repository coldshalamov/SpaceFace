# special-500 Phase 2 — build the 500 things the player encounters

Owner commission, 2026-11-04: *brainstorm 500 things to add, spread equally small, medium and
large, that the player can encounter or interact with — INFERENCE tasks, extended to give the game
character; orchestrate subagents to build them, iterate until they pass review, until 500 are added.*

## The decision (what the 500 things are)

The brainstorm already exists and is ratified: `CONSENSUS_500.json` (three-lens debate, round-4
ratification, 2026-10-27) plus its annex waves. Phase 1 authored all of it as a trigger catalog and
the director (`src/systems/special500Director.js`) fires it in the live game. What is **not yet in
the game** is the playable substance behind the catalog lines: the mechanic legs. Phase 2 adds
exactly **500 build units**, derived from live catalog truth (not the stale build log):

| Source | Units | What the player gets |
|---|---|---|
| Ratified followup legs | 335 | The bespoke mechanic each `followup` marker names (encounter file, choice scene, vendor, cache, counter, codex row, place record, NPC spawn…) |
| Ratified spectacle-only legs | 92 | The actual visual/audio moment for entries that currently fire only a noticing line |
| Dormant re-arms | 14 | The world backing each dormant entry needs, then the entry armed |
| Annex legs | 35 | Same two treatments for annex entries (29 followup + 6 spectacle-only) |
| Serial mail pass | 29 | Authored letters in `src/data/mail.js`, flag-triggered on `special500.<id>` — the pass Phase 1 explicitly deferred |

The 59 ratified entries already firing complete as authored stay as Phase 1 delivery and are not
double-counted. Unit ids: consensus ids for catalog entries; `MAIL-<id>` for mail legs;
`INFRA-*` for shared infrastructure (infra does not count toward the 500).

## Size contract — 167 small / 167 medium / 166 large

(Derivation note: five dormant entries also carry followup markers — they are counted once, as
dormant units. The mail pass therefore widens to 29 to land exactly 500.)

Per unit, judged by build surface and readers, not by word count:

- **small** — ≤ ~2 files, ≤ ~120 lines, one player-facing beat and one focused test. Letters,
  codex/lore rows, flag-counter chains, spectacle registry rows, single-beat encounter shells.
- **medium** — ~2–5 files, ≤ ~400 lines, a mechanic with two or more readers. Encounter files with
  choices wired to consequences, vendor/cache legs on existing systems, counters with a UI reader,
  light/mood spectacle legs, place records with a codex page.
- **large** — new or extended system behavior, multi-reader features. The spectacle registry
  (INFRA, then its first template families), dormant re-arms with world backing, named NPC spawns
  with AI/bark/save integration, minigame legs, serialized page-stores, choice scenes with lasting
  world consequences, new VFX template families or audio recipes for flagship setpieces.

Classification is derived deterministically by `tools/derive-units.mjs` from each followup's
mechanic keywords and rebalanced to the exact thirds by recorded promotions/demotions. The ledger
is the authority on each unit's size and status.

## Verification bar (every unit, no exceptions)

1. The player-facing behavior exists on the ordinary route — no hidden flag, no test-only path.
2. Deterministic: `state.simTime` / `state.rng` / seeded hashes only; no wall time; no `Math.random`
   in sim code; goldens never re-recorded to pass.
3. Single writers preserved; data modules stay pure data (`src/data/AGENTS.md`); the director stays
   the only writer of `special500.*` flags.
4. Focused behavior test green (`node --test test/<feature>.test.mjs`) with adversarial coverage
   (refire, stale save, missing anchor, duplicate event).
5. Copy in the game voice: gritty lived-in working space, dry wit, physics-as-spectacle, no memes.
6. Encounter modules: `node scripts/build-encounter-index.mjs` after adding files;
   `npm run check:encounter-index` green. Catalog: `validateSpecial500` stays clean.
7. Visual/audio legs go through the existing VFX/lamp/audio owners so
   `vfxAccessibility` (reduced motion/flash) applies automatically.
8. Batch rule (Finish README §5.3): one `player-truth --mode=adventure` gate per ~5 batches, when
   a batch changes something the harness can see; otherwise the focused checks are the claim.

## Orchestration protocol

1. `BUILD_LEDGER.json` (generated by `tools/derive-units.mjs`, hand-updated per batch) is the
   single status authority: `pending → assigned → built → approved → landed`.
2. Batches are grouped by leg family (mail, codex, encounter, spectacle, world/dormant), ~10–20
   units each, with per-batch worklists extracted from the ledger. Each build agent gets: the unit
   slice, the entry's consensus fields (`trigger/sees/payoff/seam`), the leg contract for its
   family, the verification bar, and exact owned paths. No agent touches another's files.
3. My approval per batch: read the diff, run the batch's focused tests + affected shared checks,
   judge the copy against the voice bar, then mark `approved` and commit exact owned paths
   (`git add <paths>` only — never `-A`) with the house style: `special500: <player-visible
   sentence>`. Fetch/merge before any push; never force-push.
4. Path ownership: this campaign owns new files under `src/data/encounters/` (numbered 1310+),
   `src/data/special500/`, `src/data/mail.js` appends, `src/data/codexPages.js` appends,
   `src/systems/special500Director.js`, its new presentation registry/system, and new
   `test/special500-*.test.mjs`. It does **not** touch the in-flight refactor files in the shared
   tree (`drill.js`, `asteroidSites.js`, `worldSiteRuntime.js`, `laneSystemFacades.js`,
   `screens.js`, prompt-deck CSS, the new `*ReadModel.js` files) — those belong to their current
   writers per `NOW.md`.

## Durable state and semantics (unchanged from Phase 1)

One-time semantics persist as `state.story.flags['special500.<id>']`; encounter-shaped firings
record `state.story.depthProgramEncounters.completed['special500.<id>']` which numbered encounter
files read through `crSituationKit.priorOutcome`. Mail letters trigger on `{type:'flag',
flag:'special500.<id>'}` (the mail system already evaluates story flags). Spectacle legs key on a
new `special500:spectacle` bus emission carrying the entry id — one small director change, then
every spectacle leg is data on the registry.
