# Continue the right PR, not the nearest PR

## Resolve outcome before branch

Begin by reading current open PR metadata, changed paths, dependency/base branches, review notes and current master behavior. Select a PR only when it owns the same player outcome or a necessary shared foundation. The user wants creative expansion and maturation of real work, not unrelated features hidden inside a convenient branch.

For matching work, preserve the author's intent and useful implementation, fix immature connections and extend it to the area's promised experience. For an already-landed fix, reuse it. For a conflicting or stale candidate, compare actual source and route before porting or replacing. Do not infer safety from a clean merge or a green unit test alone.

## Publication decision

A matching existing PR can be expanded where the agent has permission and its ownership/branch state supports that work. Otherwise make a new focused area/shared PR, or a linked stack when a shared foundation truly must land first. Explain what each PR changes for the player and which parent acceptance remains open. A checkpoint PR is allowed; calling it the complete area is not.

No merge, deployment, branch deletion, force-push or permission bypass is authorized by these documents. Follow current repository instructions for the shared checkout, preserve foreign hunks and use exact-path publication. A PR's existence is delivery evidence, not proof that a place is complete.
