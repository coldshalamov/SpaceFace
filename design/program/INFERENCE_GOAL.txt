INFERENCE

You are running SpaceFace INFERENCE. The owner throws agents here to make
the game better — not to hit a row count, and not to implement a detector
score. Copy this prompt as-is.

WHAT COUNTS — director's rule, 2026-11-09. This block wins over anything
below it and over INFERENCE_LANES.md wherever they differ.

INFERENCE makes what is already in the game right. It does not add features.
New places, people, modes and systems are built in the commission PRs
(design/program/experience-commissions on the EC-* branches). If your idea
needs a new content file, a new bark list or a new system, it is not an
INFERENCE unit: add one line under COMMISSION-CANDIDATES at the end of
INFERENCE_IDEAS.md and move on.

A unit is exactly one of three kinds:

  CLASS   You found a defect a player would notice. Fix it EVERYWHERE it
          occurs, through one shared helper or component, and add or extend
          the check that fails when it comes back. Then list it in
          design/program/INFERENCE_CLASSES.md. One screen at one window size
          is never a unit. A second fix for a class already on that list
          means the check has a hole: fix the check.
  FINISH  Something is in the game and only half works on the ordinary
          route: a job nobody can reach, an enemy that never spawns, a
          button that does nothing, a reward that never pays. Make it work
          completely.
  REMOVE  Delete noise: a duplicate, an unreachable thing, a line nobody
          needs, a dead test, a feature that makes the game worse. Less is
          a real improvement here.

Every unit:
  - Starts by LOOKING, not by reading code. Use the fast tools:
      node scripts/ui-bench.mjs --shot=<id> --walk          (a screen, seconds)
      node scripts/agent-loop.mjs sim <scenario> --trace    (behaviour, seconds)
      npm run player-truth -- --mode=swarm --rounds=3       (a real run, minutes)
    Do not boot the full game to look when one of these can show it.
  - Ends with the same look, after the change. Keep both. That pair is your
    --evidence.
  - Is recorded with --kind, --player and --evidence. The recorder refuses
    without them. If you truly could not look, record --verification unproven:
    the work is kept, and it does not count toward N.
  - Adds at most one new test file, and only one that would have caught the
    defect. Prefer extending a check that already runs.
  - Never adds a bark list, an audio recipe or a content file.

Before choosing, read design/program/INFERENCE_CLASSES.md. OPEN classes there
come first: they are known defects still waiting for their everywhere-fix.

Read, in this order, then start:
  design/program/INFERENCE_CLASSES.md
  design/program/INFERENCE_LANES.md
  design/inference-workflows/02_CREATIVE_CONVERGENCE_LOOP.md
  design/VISION.md
  design/program/NOW.md
  then the live owner for whatever you actually decide to touch
  (the WF-xx "One production unit" list is the depth bar, not the menu)

If the unit is flight/combat guts (the ship ignores you, shove does nothing,
camera loses the fight), switch to design/program/FUN_CONVERGENCE_GOAL.txt
and come back. Do not hide a handling bug inside new content.

If the owner explicitly asks you to take a section, develop an area, or fill
out the game/world, use INFERENCE_LANES.md §0.2 before catalog selection.
Work one bounded named slice under the existing FINISH_LANES.md area owner.
This routing rule does not authorize runtime changes in a planning-only task.
Bare INFERENCE and explicit catalog requests retain the directed repair loop.

For the directed repair loop, if design/program/INFERENCE_IDEAS.md has an OPEN catalog line, that line is
the job (law: INFERENCE_LANES.md §0.1). Do the line as written. Do not invent
a different feature, a new system, or a build_map.md §23 campaign. N counts new complete production changes from catalog lines, not already-true
checks, duplicate reconciliation, or status-only edits. The next line is a different group when one
is free. If the done check is already true, mark the line and take the next.

Look-then-rotate (below) is only when the catalog has no OPEN line, or they
named a domain instead of the catalog.

If the owner said only INFERENCE (no number, no MISSIONS/NPCS/WORLD/…) and
the catalog is empty:
  N = 5. Unscoped. You have to FIND what is weak or ill-built.
  Look at the ordinary route, the live owners, and the code a stranger hits.
  Name two or three real weaknesses in player words. Pick the one that would
  most help someone playing. Complete that whole thing. Then rotate to a
  different kind of weakness you also saw — not five edits to one registry.
  inference-detect.mjs is an optional count hint, at most once per batch.
  It cannot see architectural mistakes, thin missions, or empty cameras.
  If the hint disagrees with what you saw, ignore it. If you cannot explain
  the unit without a detect score, you have not inferred yet.

If they said INFERENCE N with no scope: same rule, that N. Catalog lines
first. Look-then-rotate only when no OPEN line remains.

If they named a scope (INFERENCE 3 MISSIONS): stay in that domain, rotate
kinds inside it, still by looking. N is the number they wrote.

The loop for every unit. Do not stop after a thin row.

On a catalog line, CONSIDER means: read the named owner, confirm the done
check is still false, then do that change. Do not invent a substitute.

On look-then-rotate, do not skip CONSIDER:

1. CONSIDER. Read the live owner. Name the deficit in player words. Invent
   two or three real alternatives (different verbs or places, not paraphrases).
   Pick the one a stranger would remember after thirty seconds. If you cannot
   say why the others lost, you have not considered yet.

2. COMPLETE. Build the whole playable thing through live owners. Logical
   extensions are in-scope: a mission includes placement, participants,
   script (assess → approach → commit → complication → resolve → aftermath),
   and enough density to go wrong. A tweak that makes an existing thing
   actually good counts. A new parallel system does not. If the first
   implementation is thin, iterate inside this unit — do not add a second
   thin row.

3. PROVE. Look again with the same fast tool you started with and keep the
   before and after (WHAT COUNTS, above). Inspect spawn, listeners, counts.
   Do not stall for a headed play session. GPU failure never blocks
   implemented. Never edit a test or golden to pass. Never add drag,
   momentum clamps, NPC gyros, shake, or particles to fake the moment.

4. SHIP. Commit the production slice. Record with inference-record.
   Report CONSIDERED (three ideas; why this one) plus the lanes §10 ledger.

5. ROTATE. Next unit is a different kind of weakness you found by looking.
   Scoped: different kind inside the domain. Consecutive units differ on
   at least two of verb, subject, sector, domain.

Thin does not count. A board entry, an encounter with nobody in it, a
prop scatter, or "go there and hold E" is not a unit. Hitting N with
first drafts is a failed run.

Stop at N complete units, when the owner stops you, or when every remaining
candidate collides with a live NOW.md hunk. Do not ask the owner to pick
technical options.

Hygiene loop (law: design/program/INFERENCE_CONVERGENCE.md): run
node scripts/inference-ledger.mjs, pick the weakest/stalest domain you can
verify by looking, INSPECT the live owner, GRADE it, IMPROVE one thing
completely (build, polish, simplify, optimize, or delete), RECORD the row
in place plus inference-record, ROTATE. Stale notes are rumors — re-inspect
before building on them. A catalog line is executed, not expanded. An
owner one-liner (INFERENCE 3 — <idea> / INFERENCE IDEA: <idea>) is EXPAND
first, then the loop. An idea never excuses a thin row.
