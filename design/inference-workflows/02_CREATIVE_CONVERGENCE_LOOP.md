# Bounded creative convergence loop

This is the **CONSIDER** step for one INFERENCE production unit
([`../program/INFERENCE_LANES.md`](../program/INFERENCE_LANES.md) §3.1).
It is required thinking. It is not a sequence of documents, subagents,
reviews, or acceptance gates.

The first idea is usually the thin one. Spend time here. Iterate the idea
before you iterate the git tree.

## 1. Observe

Inspect the ordinary behavior or current owner closely enough to state one
concrete deficit in player words. Do not survey the whole repository.

If working notes are useful, keep them to:

- current player-visible behavior;
- desired player-visible change;
- live owner;
- one focused way to falsify the change.

## 2. Generate

Invent **two or three real alternatives** — different verbs, places,
complications, or densities, not paraphrases of the same row. References
are optional. Do not create a candidate dossier.

Ask, for each idea:

- Would a stranger remember this after thirty seconds of play?
- What placement, people, script, and density does it need to be itself?
- Which live owners already do those jobs?

Choose the candidate with the best combination of player value, reuse of
current owners, and a result that is not a reskin of the last unit.

If you cannot say why the others lost, generate again.

## 3. Build the whole thing

Implement the coherent production path, including the logical extensions
the player would notice. A mission is place + people + script + density.
An enemy is a role in a reachable fight, not a data row. A pocket is a
verb the camera can name, not a scatter.

Finish this unit before beginning another. If the first pass is thin,
iterate **inside this unit**. A focused test may accompany the source
change; standalone infrastructure is not an implementation.

## 4. Verify

Perform the smallest direct verification sufficient for the claim. Default
proof is the live owner plus a number or a focused test. Escalate only when
the unit makes a broader route, visual, performance, save, or accessibility
claim that the narrower evidence cannot support.

A failed high-level harness is evidence about that claim, not an automatic
new project. Headed captures are not the review method.

## 5. Review

The implementer remains responsible for checking:

- what changed for the player;
- whether the discarded alternatives were actually different;
- whether the change is distinct, reachable, and dense enough to go wrong;
- the largest in-scope defect.

Fix verified causal defects. Additional investigation or review requires a
remaining material risk; confidence-only repetition and unrelated
discoveries do not reopen the unit.

## 6. Commit, then rotate

Commit the production unit and record its lifecycle/verification state.
Then select the next unit in a **different kind of value**
(`INFERENCE_LANES.md` §3.4 / §8). Do not ship the same thin pattern again.

No phase requires a standalone Markdown deliverable. Learning notes are
optional and should be captured only when they prevent a concrete repeated
mistake.

## Anti-loop rule

When the next action improves only the proof apparatus rather than the
production result, ask:

> Is this exact support change required to establish the claim this unit actually makes?

If not, leave the broader claim unproven, terminate the unit honestly, and
continue.

Thin content is not a production result. A second row that is just as thin
is also not a production result.
