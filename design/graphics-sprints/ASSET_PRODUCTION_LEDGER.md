## 2. Two truths that must stay separate

Every asset record has independent fields:

| Field | Values / meaning |
|---|---|
| Technical lifecycle | source → release → manifest → runtime map → visible in play |
| Production state | `unassessed`, `blockout`, `design_candidate`, `production_model`, `bake_candidate`, `surfaced_candidate`, `integration_candidate`, `accepted`, `blocked`, `deprecated` |
| Route result | `unproven`, browser, Electron, normal-route motion, dense/worst-case |
| Performance result | exact candidate + representative scene + target hardware, or `unmeasured` |
| Review result | exact-hash independent `accept`, `reject`, or `blocked` |

`VISIBLE_IN_PLAY`, a GLB, a Blender render, a green static check, “FULL FINISH,” a technique count,
or an author's self-review does not imply `accepted`. Historical completion prose in
`needed-assets.md` is inventory/history only. Numeric triangle, texture, byte, draw, or material
limits are diagnostic hypotheses tied to an asset and scene—not universal art ceilings.

### G0–G7 shorthand

| Gate | Required outcome |
|---|---|
| G0 | Exact identity/source/release/runtime/fallback, tier, role, views, brief, references and provenance |
| G1 | Designed silhouette, primary masses, negative space, orientation and functional role at real camera sizes |
| G2 | Production geometry: rooted construction, thickness, intersections, edge-radius families, topology and stable shading |
| G3 | Deliberate UV/trim/decal strategy, density/padding/tangents, controlled bakes and correct data/color channels |
| G4 | Physical material stacks, roughness hierarchy, mesh-aware masks, causal wear, decals and stable glass/transparency |
| G5 | Authored screen-space LODs plus representative-scene geometry/draw/texture/residency/frame evidence |
| G6 | Sanctioned export, exact reviewed hash, no fallback/swap/flicker, browser and required Electron normal-route proof |
| G7 | Independent exact-hash visual decision; no P0/P1 defect remains |

## 6. Safe parallel execution

At most three useful workers may be active for an explicitly launched graphics batch:

1. **One Blender/source owner** — the only worker allowed to edit `.blend`/source GLB for the active
   asset packet or use interactive Blender MCP.
2. **One non-Blender production worker** — reference/brief work, deterministic texture/decal source,
   runtime adapter, or evidence harness on disjoint paths.
3. **One read-only auditor/reviewer** — census, screenshot/motion critique, GLB inspection or
   independent exact-hash review.

Blender MCP is serialized because it controls one interactive application/session. Headless Blender
CLI jobs may run in isolated worktrees only when their input/output paths and GPU/CPU ownership are
disjoint and the interactive Blender owner has explicitly allowed them. The release build,
`parts_manifest.json`, runtime integration, and browser/Electron/GPU acceptance are always serialized.

Never let a worker write directly into another worker's worktree, reuse stale evidence, review its own
Tier A/B asset, or mark a PQ row integrated. Workers return candidates; the controller inspects,
integrates one coherent vertical, runs the normal route, and updates the global program surfaces.
