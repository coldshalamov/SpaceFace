# Directed INFERENCE workflow

The current repository defines INFERENCE as bounded production for an already-considered change. It is not a research essay or a license to improve the design freely. [S04, S18]

An item from this pack is initially NOT ADMITTED. The captain maps it to the native catalog, resolves its prerequisite and names the exact current owner. Only then should a low-context worker execute it.

## One assignment

Read the current task, its named file, the relevant nested instructions and the minimum neighboring definitions. Prove the stated symptom or verify the done sentence is already true. If true, use the native “already true” disposition and take a different available group. If the change conflicts with current vision, mark it CUT with a specific cause. If its required system is absent, report the named missing dependency—do not invent it.

Make the prescribed small change. Do not expand to a framework, mission type, UI redesign, faction or alternative idea. Test the stated positive case and one nearby negative/repeated case. Use the fixed seed specified by the native task; 4242 is an ordinary default only when the task does not name another existing fixture.

Verify the result on the live owner. Visual state needs actual viewing; an input fix needs real input transitions; a sound cue needs a listening check. Hand back exact changed paths and the done result. Release ownership after integration/rejection according to current policy.

## Escalation

Escalate when the actual cause lies outside the task, the named owner has changed, or a library/runtime dependency is genuinely required. State the smallest new fact and stop that mutation. The captain can redirect a strong agent while you take another bounded available task. Never silently transform a small INFERENCE item into a system rewrite.
