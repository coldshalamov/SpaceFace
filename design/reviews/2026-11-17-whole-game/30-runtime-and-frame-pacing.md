# Flight under load

**Production decision.** A clean throw is SpaceFace's most valuable performance benchmark. A player has to judge tension, the direction of a moving mass, and the instant of release. A 60 Hz HUD over a ship whose last three poses came late can report every number correctly while teaching the player that the Line is random. Protect the relationship between input, simulation and the picture before commissioning another expensive enemy effect.

## What the engine can already tell us

The main loop composes a fixed-step simulation owner and a presentation owner. The browser worker has its own clock, heartbeat telemetry and acknowledgement window. The code explicitly records time held for a missing heartbeat, outstanding replies and journal ranges. These are different failure surfaces from a GPU missing a presentation deadline. Preserve this split. A second gameplay clock or a second collision owner to mask late frames would make the hardest problem harder. The owner's prior report describes hitching during combined turn, acceleration, boost or tether while some models and interface animation continue smoothly. Several subsystems could produce that symptom. Four plausible signatures are a late authoritative tick, an old pose reapplied across fresh frames, a long render submission, and an intentional focus/time effect. A frozen-picture classifier covers some of these states. Its fallback returns `live: true` for insufficient deltas. In a source search the standalone classifier appeared in its own test and definition, while the presentation runner has its own error-streak handling. A green standalone test cannot certify the player's moving ship. ## An experiment a developer and a player can agree on

Record a seeded 90-second input tape in a real sector with a mobile enemy, one towable mass and a visible station edge to judge motion against. Divide the tape into coasting, turning under thrust, attaching under thrust, boosting around the anchor, releasing across the target's path, and recovering. Repeat with the same inputs in a quiet scene and with late-round debris. Keep the build, save, driver, driver settings, display refresh, canvas size, quality preset, UI scale and pixel ratio in the record. Use an unplugged/replugged or focus-loss trace as a **separate control**. Only compare the active-control windows at normal game speed.

| Observe together | Diagnostic decision |
|---|---|
| Input sequence and timestamp, worker tick applied, snapshot published/received, pose consumed by renderer | If ticks run behind while rAF continues, investigate fixed-step work, worker backpressure and heartbeat holds. If ticks stay current but the presented pose is old, investigate snapshot application and interpolation. |
| Presented ship and attached object's world position, relative screen position, draw sequence, camera motion | Detect repeated poses despite commanded movement, forward jumps, or reversals while all counters advance. Compare the ship to the held object. A camera correction can move both without any simulation failure. |
| CPU submit time, GPU timer where supported, draw/material counts, residency/compile events, long tasks, external scheduling | If submission rises with enemy count, batch the measured owner. If cold attachments cause creation/compile spikes, move only that work into bounded preparation. Keep unknown intervals visible. |
| Screen recording plus thumb/button witness, cold first occurrence and warmed repeat | A blink that makes the release cue unreadable fails the play check even at a good median FPS. An intentional hit pause should preserve input semantics and have a bounded, consistent duration. |

Use at least three paired runs per route, alternating A/B order. Split quiet and dense cases, and cold and warm starts. Publish median, p95, p99, worst clustered stall, long frames per gameplay minute, simulation/wall ratio, input-to-first-changed-pose and dropped input edges. Retain the raw chronological window around the worst throw. Across a short run a single number in the 99th percentile may represent only a handful of frames. For the decision to ship, extend the sample on physical hardware.

The fleet already names steady-flight and round-20 targets of **≥30% main-thread idle and ≥0.98 sim/wall**. The min-spec file separately names hardware WebGL2, an integrated Intel reference, a median 16.7 ms frame, no more than one gameplay hitch over 50 ms per minute, and a separate 2 s transition ceiling. Keep these as project targets. Label the preset and refresh rate. A deliberate 30 FPS profile has a different frame budget from the reference 60 FPS test. No new reference-hardware benchmark was performed for this review. Preserve explicit player settings and use the existing per-tier code when evaluating a lower-resolution mode. Keep the rendering and timing work bounded by this proof.
