# The whole interaction has to work

**Revised verdict, 17 November 2026.** The interface has not earned a positive usability judgment. The earlier review gave too much credit to visual direction, shared owners, option counts and passing fixtures. These establish implementation, not a player's ability to understand and control the game. The user's report and photograph of an awkward hand position while trying to steer and use Rig exposed a gap the review should have investigated. This is a priority correction across the game, not a request to add more features to an already crowded interface.

A professional interaction has a complete chain. A player recognizes a useful action, predicts its effect and cost, performs a comfortable gesture, sees the actual result, and can recover from a mistake. SpaceFace currently breaks that chain in concrete places. Having a description somewhere, an animation on keydown, and a settings toggle elsewhere does not repair the connection between them. The following findings are grounded in the pinned master `4bbe545d550a4c43e720df18c254b1c8d190d8a1`; the bounded patch described below is a subsequent correction, not evidence that the rest of the game is now usable.

## Findings that change the production order

### 1. A stateful tool was taught and presented like a held action

The player task is ordinary. Steer around debris, turn on the clearing cone, keep flying, then turn it off. Under the default preview preference, the original input policy treated the five powers as one class. That applies a preview-and-release interaction to both an aimed deployment and a persistent toggle. The Settings explanation reinforced the rule for keys 1–5. The tutorial literally said “hold Rig.” Even if a quick tap eventually produced the intended toggle, the interface taught the player to keep a distant number key occupied during steering. The defect is the combined interaction contract, not a player's failure to discover a workaround. [Input owner](https://github.com/coldshalamov/SpaceFace/blob/4bbe545d550a4c43e720df18c254b1c8d190d8a1/src/systems/input.js) · [Power policy](https://github.com/coldshalamov/SpaceFace/blob/4bbe545d550a4c43e720df18c254b1c8d190d8a1/src/systems/powerVerbs.js) · [Settings explanation](https://github.com/coldshalamov/SpaceFace/blob/4bbe545d550a4c43e720df18c254b1c8d190d8a1/src/ui/screens/settings.js#L1094) · [Rig lesson](https://github.com/coldshalamov/SpaceFace/blob/4bbe545d550a4c43e720df18c254b1c8d190d8a1/src/onboarding/powerSituations.js#L68)

The HUD made this harder to diagnose. The live adapter assigned `iconOnly = true` to every power, while the Cluster hid the text of collapsed inactive sockets. It also derived Rig's held/active display from raw input alongside the owner's state. A highlighted button can therefore explain a finger position rather than whether the cone remains operating. A toggle needs a persistent, unambiguous ON/OFF readout. A held control needs a visible hold/release instruction. These are different jobs. [Live adapter](https://github.com/coldshalamov/SpaceFace/blob/4bbe545d550a4c43e720df18c254b1c8d190d8a1/src/ui/orrery/hudAdapter.js#L185) · [Collapsed and phone labels](https://github.com/coldshalamov/SpaceFace/blob/4bbe545d550a4c43e720df18c254b1c8d190d8a1/src/ui/orrery/flightCluster.js#L130)

### 2. At least one lesson teaches a capability the power does not have

The Pin situation says a tumbling pod can be held with Pin. The shared power description instead describes a stationary anchor ahead of the ship, intended for the Line. A new player following the lesson is given the wrong causal model. Better prose rhythm cannot rescue that. The lesson must demonstrate placing an anchor, attaching the Line, and using the anchor as a turning point. It must not imply that the drifting prop has been immobilized. [Situation specification](https://github.com/coldshalamov/SpaceFace/blob/4bbe545d550a4c43e720df18c254b1c8d190d8a1/src/onboarding/powerSituations.js#L50) · [Actual Pin description](https://github.com/coldshalamov/SpaceFace/blob/4bbe545d550a4c43e720df18c254b1c8d190d8a1/src/data/arsenalWords.js#L71)

There is a second problem in the evidence. The registered onboarding owner starts this ladder after the first dock, despite older comments calling it first-minutes teaching. It resolves a situation as used when the action is held or pressed. That does not prove that a power deployed, affected the intended object, or taught anything. A preview, a denied attempt and a successful maneuver must not share a learning-success metric. Keep optional lessons optional, but distinguish **offered**, **attempted**, **executed**, and **demonstrated**. [Actual scheduling and resolution](https://github.com/coldshalamov/SpaceFace/blob/4bbe545d550a4c43e720df18c254b1c8d190d8a1/src/systems/onboarding.js#L2922)

### 3. Reading an Armory card and committing a purchase have inconsistent meanings

The concrete player task is to compare two unfamiliar items without spending, then choose one. In the dealt three, clicking the whole card selects, buys and fits. In the catalogue shelf, clicking selects an item for inspection and a separate action installs it. These are intentional code paths on the same Armory surface. They make a player infer transaction semantics from the card's location and treatment. Putting the price on the card does not establish that reading the card should spend it. [Immediate dealt-card transaction](https://github.com/coldshalamov/SpaceFace/blob/4bbe545d550a4c43e720df18c254b1c8d190d8a1/src/ui/screens/crucibleDraft.js#L1976) · [Shelf inspection](https://github.com/coldshalamov/SpaceFace/blob/4bbe545d550a4c43e720df18c254b1c8d190d8a1/src/ui/screens/crucibleDraft.js#L2093)

The information order is also questionable. Offer text can prefer the arsenal's identity sentence over the offer-specific blurb. The card then adds activation and hardpoint text. The largest equipment illustration does not itself explain the change in the ship's behavior. The current build and its hardpoint jig are inside a disclosure; demo and hold actions sit behind a generic “More.” All these ingredients exist, but a beginner's decision may still depend on searching several layers. [Offer text composition](https://github.com/coldshalamov/SpaceFace/blob/4bbe545d550a4c43e720df18c254b1c8d190d8a1/src/ui/screens/crucibleDraft.js#L245) · [Secondary actions](https://github.com/coldshalamov/SpaceFace/blob/4bbe545d550a4c43e720df18c254b1c8d190d8a1/src/ui/screens/crucibleDraft.js#L1079) · [Current-build disclosure](https://github.com/coldshalamov/SpaceFace/blob/4bbe545d550a4c43e720df18c254b1c8d190d8a1/src/ui/orrery/crucibleArmory.js#L29)

Make inspection safe and purchase explicit across the screen. The primary comparison should answer what changes on the next encounter, which existing item is replaced, what is lost, the total price and the remaining balance. For a proposed gun comparison, “fires twice as often, each hit is weaker” is the useful first sentence; the measured before/after figures should then come from the compiled weapon. Do not invent figures to make the copy sound concrete. Use “Install — 28 cr” for commitment and make the outcome visible on the actual mounting point. Preserve a clearly reachable Launch action for the player who buys nothing.

### 4. Control availability is not control discoverability

A rebind table and accessibility schema are valuable infrastructure. They do not establish that a player can locate the right setting, predict its scope, perform the action with their preferred device, and return to the same task. The original general “Powers” preference hid several different gestures under one term. A persistent tool should not need an accessibility workaround to become physically comfortable. Remapping should change the instructions at the point of action as well as the table in Settings. [Binding rows and labels](https://github.com/coldshalamov/SpaceFace/blob/4bbe545d550a4c43e720df18c254b1c8d190d8a1/src/ui/screens/settings.js#L245) · [Input bindings](https://github.com/coldshalamov/SpaceFace/blob/4bbe545d550a4c43e720df18c254b1c8d190d8a1/src/systems/input.js) · [Access settings](https://github.com/coldshalamov/SpaceFace/blob/4bbe545d550a4c43e720df18c254b1c8d190d8a1/src/ui/accessibility.js#L173)

Source review also found a dangerous boundary in the HUD activation path. When an action resolved to no key, its click handler could fall back to the original numbered key. An explicitly unbound power must not silently invoke a default key that may now mean something else. This is a small example of why a polished socket is not enough. The label, binding resolution, dispatch and authoritative result all need to agree. [Socket activation](https://github.com/coldshalamov/SpaceFace/blob/4bbe545d550a4c43e720df18c254b1c8d190d8a1/src/ui/orrery/hudAdapter.js#L411)

## The bounded correction in this working pass

Published as [draft PR 1118](https://github.com/coldshalamov/SpaceFace/pull/1118), with [verification scope and remaining blockers](01-evidence-and-playtest.md). The change is reviewable and has not earned live player acceptance.

The implemented policy separates three interactions. **Pull, Pin and Bomb** retain the selected aimed-power preference. **Shove** acts on press as a reaction pulse. **Rig** switches on or off on press and stays in that state after release. Existing bindings and stored preferences are retained. The shared policy is consumed by input, automatic preview and gesture descriptions.

The existing flight socket now reads Rig's actual fields/planet state, shows Cone or Scoop ON/OFF, and prints “Tap” with the current keyboard binding. Its narrow label retains ON/OFF. It no longer treats a held Rig key or a transient activation flash as proof that the tool is on. The existing other sockets remain compact because changing every label without a rendered layout check would create another unproven design. Unbound sockets no longer dispatch a default number. Settings now names the aimed powers and explains both preferences, while the tutorial and shared catalogue stop telling the player to hold Rig or use Pin to freeze a pod.

This corrects a specific interaction contract. It does not demonstrate that all labels fit on all viewports, that the Armory is comprehensible, that controller hints are correct in every context, or that an unfamiliar player can complete the opening. The focused UI and presentation run passed 43 tests, including remapped Tap J, persistent ON after release, OFF after the owner switches off, and an unbound socket dispatching nothing. These are source and DOM checks. The local screenshot runner could not start its browser in this environment; the public browser route also failed to create a WebGL context during the correction pass. No improved-layout screenshot or successful fresh-player flight is claimed.

## Work packets for the rest of the interaction chain

These are repairs to connected player tasks. They should precede new career systems, additional Armory stock, more lore panels, or another layer of tutorial notices. The full cross-game acceptance matrix is in [62 — Player experience acceptance](62-player-experience-acceptance.md).

| Packet | Ordinary task and concrete change | Acceptance evidence |
|---|---|---|
| **UX-01, fly and act** | Fly an obstacle course while using each available power. Label each gesture as tap, hold/release or on/off. Keep continuous state visible and derive it from the owner. A denial names a specific reason and recovery. | Actual device input, game state and visible result agree on first press, hold, release, second press and pause/resume. Repeat with rebound keys and a retained profile. No essential maneuver requires an awkward sustained chord. |
| **UX-02, learn the real action** | Replace false lessons with small physical problems that the taught mechanic actually solves. Pin teaches an anchor and a turn; Shove teaches an immediate escape; Rig teaches continuing to steer with the cone on. | An unfamiliar player predicts the result before using the power, performs it, recognizes success, then uses it without the prompt in a changed arrangement. Merely holding a key is recorded as an attempt. |
| **UX-03, buy with understanding** | Unify card inspection and purchase semantics. Put the selected item's behavioral change and tradeoff before identity prose, show the existing fit and remaining balance, and make the commit button explicit. | Inspect two items, cancel, buy one, inspect the receipt and launch. Repeat with insufficient funds and zero purchases. The player can state what changed and what they gave up; no inspection spends credits. |
| **UX-04, stop and resume** | From flight, find one control setting, change it, resume, save, reload and repeat the same action. Carry the active task and selection through Help, map, journal and back. | Current hints match the saved binding. Focus returns to a valid control. A controller disconnect, cancelled dialog or failed transaction leaves an understandable recovery route. |
| **UX-05, travel and work** | Accept a named job, identify its physical destination, travel, identify the interactable object, perform the work and understand the receipt. Use the same terms for owned, entrusted, reserved and free cargo. | A novice completes the whole route without a developer choosing targets or explaining hidden state. The receipt names actual cargo/payment/mission changes. A full hold, blocked route and wrong target produce recoverable explanations. |

The first packet should trace the action all the way through, not start another HUD framework. The Armory packet should use a small real offer set and the current transaction owner, not introduce another economy. The tutorial packet should reuse the actual mechanics and verify outcomes, not reward an input event. Where the existing owners are sound, keep them. Where an interaction is confusing, historical art rules should not outrank legibility.

## What to measure, and what to stop claiming

For each observed session, record time to first correct action, wrong-action attempts, unintended spending, assistance required, whether the player recognized the result, and whether they could repeat it after the prompt vanished. Capture the screen and input conditions. Report the denominator and the actual task rather than a single “UX score.” Five new participants form a useful initial discovery batch, not statistical proof of a population success rate. Expand observation when a design decision depends on uncertainty that remains.

Run the route at a normal desktop viewport and larger text before claiming readability. Exercise reduced motion and reduced flash separately. Use a physical controller and handset before claiming parity. A text-size floor is a minimum technical constraint, not proof of comfortable reading. A colored glow is not equivalent to a written state. A tooltip reachable only by hover is not a sufficient instruction during simultaneous aiming and steering. The repo's access tools and shared dialog owner are useful means for doing this work; their existence is not its result. [Shared dialog owner](https://github.com/coldshalamov/SpaceFace/blob/4bbe545d550a4c43e720df18c254b1c8d190d8a1/src/ui/confirm.js) · [Access owner](https://github.com/coldshalamov/SpaceFace/blob/4bbe545d550a4c43e720df18c254b1c8d190d8a1/src/ui/accessibility.js) · [UI operating guidance](https://github.com/coldshalamov/SpaceFace/blob/4bbe545d550a4c43e720df18c254b1c8d190d8a1/src/ui/AGENTS.md)

The earlier public-build Armory observation remains narrow evidence. One recorded purchase took 1,017 run credits to 989, fitted the chosen Pulse Laser M and carried the balance into round two. It proved that transaction on that public artifact. The same observation found wrapped item names, descriptions extending below the visible card area and duplicated equipment imagery. Neither result establishes current-master comprehension. Likewise, localization inventory totals establish string coverage, not a playable translated journey. Translate and test the title-to-first-job and title-to-first-intermission routes as complete units before making language promises. [Public demo](https://spaceface-play-demo.vercel.app/) · [Localization readiness](https://github.com/coldshalamov/SpaceFace/blob/4bbe545d550a4c43e720df18c254b1c8d190d8a1/src/localization/catalogs/readiness.generated.js)

Do not expand the choice set while the existing choices cannot be explained. Do not replace one obscure label with another poetic noun. Do not mark a task complete because a component mounts or a keydown was emitted. The next acceptance claim must describe a player who understood a concrete action, executed it comfortably, recognized the result and recovered when it failed.
