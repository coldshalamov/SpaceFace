# 00 — Production Constitution

**Status:** DRAFT process authority beneath `design/vision/ALPHA_PROGRAM.md`

## 1. The governing insight

**Workers do not complete tasks. Workers submit candidates.**

Only the orchestrator may promote a candidate after independent technical, runtime, and quality
review. This removes the need to persuade an authoring agent not to stop early: stopping merely
submits the current candidate, and a failed candidate is automatically returned for another pass.

## 2. What counts as progress

Progress is the number and importance of player-facing coverage items independently accepted at
their required maturity. The following are process telemetry, not completion evidence:

- files created or changed;
- iteration count;
- token/turn/time expenditure;
- self-authored scores;
- a GLB existing or loading;
- a check going green;
- a transcript saying the work is complete;
- touching every named surface once;
- a feature working only in an injected fixture.

No weighted average may hide a critical failure. A good hero ship cannot compensate for an
unreadable fight; twenty weak props cannot compensate for a missing station family.

## 3. Separation of powers

| Role | May do | May not do |
|---|---|---|
| Product director/orchestrator | choose work, own ledger, dispatch, verify, accept/reject | self-certify substantive work it authored |
| Research/spec agent | study references, create contracts and technique cards | implement or accept the resulting asset/feature in the same role |
| Implementer/artist | build the candidate and provide evidence | mark ACCEPTED, lower gates, edit reviewer verdicts |
| Evidence auditor | verify provenance, completeness, hashes, checks, route truth | judge taste from metrics alone |
| Independent critic | blind visual/play review and defect classification | edit the candidate under review |
| Integrator | publish accepted artifacts and run cross-system gates | promote a visually rejected candidate because packaging passes |

If the orchestrator directly authors a substantive change, it becomes the implementer for that
packet and must assign acceptance to a fresh reviewer.

## 4. Maturity ladder

Every coverage item has one explicit maturity. Only **L7** counts as complete for a milestone.

| Level | Meaning |
|---|---|
| L0 | Idea, prose, research, or reference |
| L1 | Mechanism executes in isolation |
| L2 | Canonical live path uses it |
| L3 | One real player-facing vertical application proves it |
| L4 | Reusable family with meaningful variants |
| L5 | Product surface: controls, UI, VFX, audio, readable consequence |
| L6 | Operational: save/load, determinism, performance, accessibility, migration |
| L7 | Independently accepted on public player routes with durable evidence |

## 5. Acceptance is conjunctive

A candidate is accepted only when every required class passes:

1. **Scope truth:** it satisfies the named player outcome and coverage contract.
2. **Technical truth:** canonical files/path, deterministic behavior, real asset contract, checks.
3. **Runtime truth:** browser/Electron route uses the candidate without fallback or injection.
4. **Temporal truth:** motion/interaction is understandable across setup, action, and aftermath.
5. **Quality truth:** independent review finds no unresolved critical or major defect.
6. **Operational truth:** performance, save/load, accessibility, compatibility, and migration as relevant.

Missing evidence is not a pass. “Not observed” is not “working.”

## 6. Anti-shortcut laws

- Self-scores are notes only and cannot affect acceptance.
- Scores may never be calculated from iteration number, pass name, elapsed time, or expected progress.
- Required shots may not be excluded from a pass decision.
- An iteration counts only if source/GLB evidence proves a substantive candidate change; camera,
  lighting, filename, metadata, or neutral-map-only changes do not count.
- Fixed iteration floors never imply completion. Hero/cast assets receive at least the planned
  review budget and continue until accepted.
- Technique counts never imply quality. Techniques must be selected because they solve an observed
  problem and survive the Blender-to-GLB-to-Three.js path.
- The worker may not weaken its evaluator, rewrite expected results, relabel assets, or stamp
  unsupported metadata to obtain a pass.
- Auto-approved terminal workers never write directly to the dirty live tree. A proven isolated
  transaction/lease boundary contains mutation and a separate integrator promotes allowlisted hashes.
- Workers cannot write campaign state, acceptance cards, reviewer verdicts, gates, or coverage truth.
- Fixture/injected routes are supporting evidence only.
- Exact acceptance seeds/routes are selected after candidate submission where feasible.
- A rejection creates a persistent defect ID. It cannot disappear without accepted evidence.

## 7. Continuation law

Agent/session termination is not task termination.

- If a candidate fails, the orchestrator resumes the responsible session with the exact verdict.
- After three materially similar failures, commission a fresh diagnostic/research pass.
- If the foundation is wrong, rebuild from the last accepted stage instead of polishing forward.
- Context or turn limits produce a continuation record and immediate redispatch, not completion.
- A hard blocker requires concrete external evidence; difficulty, fatigue, or elapsed time are not blockers.

## 8. Saturation before milestone exit

After all known milestone items appear accepted:

1. Run three fresh adversarial audits from different roles.
2. Run held-out player routes/policies/seeds.
3. Reset the clean-wave counter if any new P0/P1 or category-level omission appears.
4. Exit only after the milestone's required number of clean waves and no unresolved P0/P1.

The required clean-wave count belongs in each milestone contract; it is never inferred by the worker.
