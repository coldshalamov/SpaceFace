Read-only audit; no app launch; SwiftShader box — CPU-side numbers are node24 micro-benchmarks on a synthesized ~2.0 MB save-shaped envelope, per this lane's evidence convention.

**saturated: false** — one material residual remains: the W133 covering-spec consult introduced a dead-end where a covering arm that resolves non-ok (or empty) silently skips the lazy fill, leaving the selected row's portrait unfilled for the memo generation. ## Findings (ranked by evidence × impact)

### F1 · Covering-spec fill dead-ends when the arm's prepare resolves non-ok or empty — the once-per-spec emit never fires and `entry.attempted` already latched (hunts b+c) — MECHANISM_VERIFIED, impact L-M

Evidence: `saveLoad.js:814-822` — `fillSlotData` sets `entry.attempted = true`, consults `coveringSpeculativePrepare(slot)`, calls `spec.dispatch()`, and **returns**. The fill's continuation depends entirely on `save:envelopeSpecPrepared`, which the arm emits only when the worker prepare resolves `prepared.ok === true` while the spec is still current, sig-live, and in a menu/frozen mode (`saveSystem.js:2563-2579`). Three failure shapes all reach the same dead-end:

- `spec.dispatch()` resolves `Promise.resolve(null)` when `readRaw()` returns empty (deleted-slot race or a throwing `localStorage.getItem`) — `saveSystem.js:2553-2557`; the emit `.then` early-returns on `!prepared` (`:2564-2566`).
- A covering blob that parses but fails worker validation — checksum mismatch, unreadable/future version, oversize, preflight/normalize reject — resolves `{ok:false}` → emit skipped (`:2567`).
- `dispatch()` re-serve (`if (spec.promise) return spec.promise`, `:2550-2551`) means the emit is registered **once** at first dispatch; a spec whose first resolve was suppressed (any gate above) can never emit again — a second `fillSlotData` consult re-serves the promise but registers no new emit.

Meanwhile the pre-W133 lazy path (`entry.raw` via `readSlotBlob` + `unwrapSaveData(JSON.parse(raw))`, `saveLoad.js:825-828`) never runs — `attempted` latched and the consult returned. `unwrapSaveData(JSON.parse(raw))` performs no validation, so pre-W133 these blobs still rendered their portrait; post-W133 an occupied row's stage stays meta-only until a store write or LRU evict re-mints the memo.

Player-visible: a corrupt, future-version (switching between builds), or oversized-import slot card that never fills its stage reads as a stalled load — squarely the artifact this lane hunts. Frequency is low but the class is real.

Fix sketch: when the consult dispatches, chain a fallback — `spec.dispatch().then((p) => { if (!p || p.ok !== true) lazyFill(entry); })` where `lazyFill` is the existing `readSlotBlob`+parse tail hoisted out of `fillSlotData`. Cheapest correct variant: keep `attempted` for the covering path but let the non-ok resolution run the tail once. Effort S · Impact L-M · Risk L — the fallback is today's uncovered-slot path verbatim; the emit fills stay `!entry.data`-gated so a late emit cannot clobber a fallback's data.

### F2 · `specByteHit` pays a duplicate same-key `getItem` on stale-generation consumes (hunt a) — MECHANISM_VERIFIED, impact L

Evidence: `saveSystem.js:4833-4849` — on `loadAsync`, a same-slot spec minted under an older generation fails `specHit` (sig gate), so `raw` is materialized via `localStorage.getItem(LS_PREFIX + slot)` (`:4840-4841`), then `specByteHit` evaluates `(spec.readRaw ? spec.readRaw() : spec.raw) === raw` (`:4848`) — for an undispatched thunk arm `readRaw()` re-reads the identical key on the same click task. Measured bound on this box: ~1 ms per 2 MB blob for an equivalent string clone; `localStorage.getItem` for a mature save is the same order — so one duplicated multi-MB read, ~1-3 ms, on the click task. Reach requires a generation bump between arm and click that lands before `_onSaveStoreBump`'s task-hopped re-arm (`:394-401`) — an autosave racing a dwell click.

Subtlety worth noting for the fix: for a thunk arm that has *never* read, `readRaw()` is tautologically `=== raw` (same key, same task), so the byte compare can skip the read entirely; only an already-materialized `spec.raw` (string arm or already-dispatched thunk) carries bytes that can differ from `raw`. Fix sketch: `const specBytes = spec.raw != null ? spec.raw : raw; specByteHit = ... && specBytes === raw` — i.e. treat an unmaterialized thunk as byte-equal instead of forcing its getItem to prove it. Effort S · Impact L · Risk L — identical verdict, one fewer O(blob) read on a rare path.

### F3 · Sync `load()` cannot consume a resolved worker prepare — a covered click re-pays the full sync `_prepareEnvelopeString` even when the arm finished (hunt a) — MECHANISM_VERIFIED, impact L-M

Evidence: `saveSystem.js:4730-4745` — the sync lane consumes the spec (`specHit`) but the worker's promise is unreadable synchronously, so it pays `spec.readRaw()` (a thunk-armed click pays the multi-MB `getItem` on the click task) **plus** the whole `_prepareEnvelopeString` chain — JSON.parse, checksum `fnv1a(safeStringify(data))`, migrations, `clonePlain`, normalize. Measured components on this box at ~2 MB: parse ~11.5 ms, stringify ~6.7 ms, fnv1a ~2.4 ms, structuredClone of the parsed graph ~41 ms (clonePlain same order) — ~50-80 ms total on the click task, all of it redundant when `spec.promise` already resolved with the validated envelope.

Production exposure is narrow: `game:load` listeners prefer `deferLoadedGameRestore(loadDeferred)` → `loadAsync` (`saveSystem.js:363-370`); the sync lane serves when the painted defer is absent (headless/tests/console paths) — the same-lane 'latest' consult also pays `_slotStoreSignature`'s whole-store enumerate+getItem walk (`:2175-2200`) once per generation when no same-gen cache exists. Fix sketch: have the dispatch `.then` stash `spec.prepared = prepared` before the emit gates, and let `load()` consult `specHit && spec.prepared` — a sig-gated validated envelope skips the sync chain entirely. Effort S-M · Impact L-M (fallback lane only) · Risk M — reuses the worker result on a lane that historically re-validated; the `gen:` sig gate already proves byte-identity, but the restore path's `primary.env`/`data` shape contract must match `_prepareEnvelopeString`'s output exactly.

## Scanned clean / non-findings

- **(a) thunk-materialize seam — bounded.** Armed tasks pay zero blob reads (memo mints `raw:null`; the arm carries a thunk). A click beating the 200 ms debounce pays one `getItem` (~1-3 ms for a multi-MB blob; equivalent `structuredClone` of a 2 MB string measured at ~1 ms) + the postMessage clone inside `dispatch()` — the parse itself still rides the worker on `loadAsync`. On the sync lane the same click pays `readRaw` + the full sync prepare (F3). After dispatch, `readRaw` is memoized — no repeat reads. The window is real but bounded to one memoized read per arm; the pick task stays clean. The one non-designed double read is F2.
- **(b) single-slot cover — bounded.** Fills only ever run for `refs.selected`, and every `_select` re-arms — arm and fill always agree at settle; alternating picks collapse through `clearTimeout` on the prior arm's parked dispatch (`saveSystem.js:2520-2522`). An uncovered settle pays one `getItem` + `JSON.parse` (~13 ms at 2 MB, measured) inside the 180 ms timer task — off the input path. A settled spec (promise resolved, timer consumed) still covers: `dispatch()` re-serves `spec.promise` and the emit's resolve-time gates re-check liveness; see F1 for the once-per-spec emit consequence.
- **(c) dispatch-fail edge — no double read; the gap is F1.** `entry.attempted` latches before the consult (`saveLoad.js:815`), so a failed dispatch never re-materializes the thunk and never re-parses — the row simply never fills.
- **(d) emit/fill raw race — clean.** No reader expects `entry.raw` populated: `_select` emits `picked.raw` (null post-W133 → thunk arm), export rides `exportSlotAsync`/`exportSlot`/`exportSave`/`localStorage` (`saveLoad.js:1541-1558`), delete rides `sys.deleteSlot` (`:1512-1513`), the fan-in mints `raw:null` entries (`:1031`), and `fillSlotData` is the only consumer (via `readSlotBlob`). The emit's `entry.sig` restamp rides the same write as `entry.data` — a stale entry keeps its old sig and misses on the next `readSlotSaveData`.
- **(e) surviving synchronous legs — the rest are bounded.** Slot-index enumeration on the render path is `key()`-only per signature miss (`listSlotsIndexCards`, `saveSystem.js:2356-2375`) — no blob reads; the materialize+hash walk rides `_scheduleSlotIndexValidation` off the render task with 16-key `rAF`/`setTimeout(48)`-fallback yields (`_restoreFrameYield` `:5799-5825`) and bounded 4-wide worker verdict fan-out (`:2444-2447`). The whole-store blob materialize survives only on the *authoritative sync* consult — `load('latest')`'s burst walk on the fallback lane, once per write generation (`_slotStoreSignature` `:2175-2200` → `_scanStoredSlots` `:2679-2728`; trusted cards pay one `fnv1a` each, ~2.4 ms/2 MB measured). Title/mainMenu ride `listSlotsIndexCards` + pure-index `selectLatestOccupiedSlot` (`mainMenu.js:86-133`). Import: `FileReader.readAsText` async → `importString` → sliced async prepare (`importFile` `:7455-7477`, `_loadEnvelopeFromStringAsync` `:5069+`). Export: worker prepare on miss (`exportSlotAsync` `:7288-7312`), textual profile splice without an O(blob) roundtrip (`:7349-7360`), `Blob` mint + 30 s `revokeObjectURL` (`saveLoad.js:1560-1567`). Thumbnails: `img.decoding='async'` on card meta (`:1138-1147`); save-shot `toBlob` async (`capturePhotoPngAsync`, `:1483-1492`). Worker-reply structured clone of a parsed ~2 MB envelope measured ~41 ms — intrinsic to the worker design (restore needs the object); the card path already dodges it via `cardEnv` projections (`:2432-2443`).
- **Arm lifecycle — closed.** `disarmSpeculativePrepare` on `onHide`/`dispose`; parked timer drops a mode-moved arm before dispatching (`saveSystem.js:2585-2596`); consume clears the parked timer on both lanes (`:4732-4733`, `:4822-4824`); targeted `_onSaveStoreBump` re-arm dispatches immediate on the writer task with bytes already in hand (`:387-393`, ~1 ms clone — deliberate).

## Measurement notes

CPU-side node24 micro-benchmark on this box (SwiftShader; the app was not launched), synthesized ~2.0 MB save-shaped envelope: `JSON.parse` **11.5 ms/call**, `fnv1a` **2.4 ms/call**, `JSON.stringify(data)` **6.7 ms/call**, `structuredClone` of the blob string **1.0 ms/call**, `structuredClone` of the parsed envelope **41.2 ms/call**, 200 `key()`-style string slices **<0.01 ms**. `localStorage.getItem` is not measurable under node (no DOM backend); its bound is stated as a mechanism — one memoized multi-MB string materialization per task, sized by the campaign's standing multi-MB-per-slot premise.
