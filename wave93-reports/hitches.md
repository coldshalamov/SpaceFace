Three live mechanism-level findings remain, all on presented-frame pacing seams in the shadow-policy, env-rebind, and presentation-query machinery. Everything else enumerated below is bounded or documented.

## Findings (ranked)

### F1 — Presented shadow-policy lane has no pass-level wall: fresh 4ms wallet per root, parked resumes bypass the mint cap, withhold verdicts run atomic and uncounted

**Evidence.** `_syncShadowCasterPolicyChecked` mints `policyDeadlineAt = policyNow() + 4` **per call — i.e. per dirty root per presented pass** (`src/render/renderer.js:25028-25035`), handed to `driveShadowPolicySteps` (:25031-25035). The pass cap `SHADOW_ROOT_SYNC_PASS_CAP = 8` (:6742) counts only new mints: `_shadowRootSyncPassCount` increments at :25017-25019 only when `!hadParkedWalk`, and `traverseDeferred` at :25012-25016 explicitly excludes parked resumes — every parked root in `_policyStepsParked` resumes every pass with its own fresh 4ms (comment at :25007-25010 acknowledges the bypass; `driveShadowPolicySteps` re-parks on deadline at :26918-26946 so `P` persists until roots finish). The withhold/scoped path at :25036-25051 calls `syncShadowCasterPolicy` **atomically** — a whole-subtree traverse with no wall at all. The comment at :24996-25000 claims "verdicts are bounded by the same collect cap" — but the collect cap (`_depthCollectPassCount`/`_depthCollectNodesLeft`, :24904-24935) bounds `collectUnstagedShadowCastersFlag` *calls*, not verdict traverses. Asymmetry confirmed by the two sibling mechanisms that DO share a pass budget: the collect wallet (:24907-24935) and the arm-restore lane, which mints ONE `restoreDeadline` for the whole root set per slice (:25497-25574, `SHADOW_DEPTH_ARM_RESTORE_MS = 4` at :6718).

**Mechanism.** One presented pass can pay `min(mints,8) × ≤4ms` + `P × ≤4ms` (parked resumes) + `W × O(whole authored subtree)` (atomic withholds/scoped grafts). `P` and `W` are unbounded per pass: `invalidateShadowCasterPolicy` fires at partsLibrary.js:3342/:4280/:9169/:9201/:9455 and renderer.js:9248/:10700/:11268/:25074/:25691/:25731 (attach storms, upgrade admits, LOD cascades, census re-signs), and `_syncShadowCasterPolicyChecked` is called per visible ship/station/place row every frame (:22675) plus spawn/mount/rebuild/LOD-swap sites (:9251, :10314, :11274, :21985, :22167). A multi-root burst can stack >32ms of policy work on one presented frame — a visible hitch exactly during the mass-verdict windows (cohort band flips, station graft storms).

**Fix sketch.** Mint a pass-scoped deadline once per `_viewSyncSeq` roll alongside the :24904-24908 reset: `this._policyPassDeadlineAt = policyNow() + SHADOW_POLICY_PASS_MS`; pass `() => policyNow() >= this._policyPassDeadlineAt` to every `driveShadowPolicySteps` call in the pass. Spent roots return instantly and stay parked; `_policyStepsParked` is a Map so resume order = park order (fairness preserved). Withholds keep their atomic doctrine by design — optionally bound their count per pass and leave excess roots dirty (fail-open on `castShadow=true`, quality-preserving).

**Effort:** S. **Magic-frame impact:** M (realistic bursts 2–5 roots → 8–20 ms; worst-case path unbounded). **Risk:** M — sharing a wallet changes resume fairness ordering; the arm lane's separate wallet and the parked-iterator lifecycle must be left untouched.

### F2 — `drainSceneEnvRebindQueue` consults `pacedFrameSpend()` but never debits it, and carries no aging floor → unaccounted spend + indefinite starvation

**Evidence.** `src/render/renderer.js:26891-26909`: the drain breaks on its own `now() >= deadline` (4ms) OR `pacedFrameSpend() >= PACED_FRAME_BUDGET_MS` (:26907; budget = `GLTF_COMPILE_FRAME_MS` = 4, decodeTaskBudget.js:305-307) but never calls `notePacedFrameSpend` — the recurring "private-clock-only slicer" class. It runs inside `serviceRenderMeshResidency` at :2144, immediately after `drainDespawnDisposeQueue` (:2143) which DOES debit (:2024) and carries the `DESPAWN_DISPOSE_LEDGER_MAX_SKIPS` aging override (:1951-1956). The reattach path in the same function carries a `pacedFrameSpend() < 2` headroom floor (:2190). The env drain has neither a debit nor a floor; `serviceRenderMeshResidency` itself does not debit on behalf of its sub-drains.

**Mechanism.** (i) Up to ~4ms of env-rebind walk per presented frame is invisible to the shared paced ledger → every later paced lane in the same frame oversubscribes the frame budget — hitches stack precisely when the residency pass is busy (re-bake storms, sector-enter aftermath). (ii) When the despawn drain ahead of it has spent the wallet, the env drain exits instantly **every frame** → a deep rebind queue starves indefinitely: live envMap stays stale AND each queued entry's `disposeTarget` render target never frees (:26900-26905) — GL memory retention for the session's lifetime. The lane-brief hypothesis "the budget check already bounds it" is only half right: per-pass spend is bounded, but the spend is unaccounted and starvation is cumulative.

**Fix sketch.** Debit `notePacedFrameSpend` for the measured slice spend (or per-stepped-unit), and add a `MAX_SKIPS`-style aging floor — force-drain at least one queue entry every K frames regardless of wallet state. FIFO head-only drain already guarantees progress once any steps run.

**Effort:** S. **Magic-frame impact:** M (unaccounted per-frame ms + stale env + render-target leak in long sessions). **Risk:** L — additive debit and skip counter; no rebind semantics change.

### F3 — W91 doom mints drop VISIBILITY dirty marks on already-invisible rows → marks are never consumed → both query retains stay pinned for the slot's life

**Evidence.** `src/render/presentationWorld.js:964-976` (hiddenIds/skippedIds mint) and :986-997 (dense eligibility sweep) write `doomed=1; world.visible[slot]=0; markDirtyBits(slot, VISIBILITY)` with **no `world.visible === 1` gate**. The comment at :960-961 states the intended contract — "the hidden loop's clearDirty consumes the VISIBILITY mark and both retain paths restore" — but hidden-loop entry requires the row to have been in the *prior* visible set (`hiddenSlots` = prior-visible minus current-visible, `presentationQueries.js:342-352`). A row already at `world.visible === 0` (culled long ago, or fresh — `allocateRecord` writes `visible=0` at :621) never enters `hiddenSlots`, so `clearDirty` never runs for it — the only consumers are inside set-member loops (renderer.js:22482/:22534/:22932). The mark persists until `retireSlot`/`allocateRecord` overwrite (:633, :704-706). With `dirtyCount > 0` and a non-TRANSFORM bit present, the zero-dirty retain fails `dirtyCountNow === 0` and the pose-dirty retain fails `poseOnly` (`presentationQueries.js:191-225`) — every presented frame pays the full `collectSpatialBounds` + candidate sort + `exactVisible` walk.

**Mechanism.** Suppressed-feed windows (journal rebuild churn — exactly the hitch-prone frames) mass-mint dooms on every tombstoned/skipped id including never-visible ones. One stray tombstone pins both retains for the rest of its slot's life; doomed rows are off the push path, so nothing ever re-stamps or consumes the mark (a feed push only clears `doomed` itself at :943). Cost delta: the full query walk every frame vs the ~zero retained path — sub-ms to low-ms depending on candidate count, paid for the tombstone's whole residency. Preexisting stray-mark classes (alloc `ALL` at :633, `bindMesh` VISIBILITY at :781, feed TRANSFORM on off-set movers at :750) share the same never-consumed property, but the W91 mint is the new systematic mass-writer.

**Fix sketch.** Gate both mints on `world.visible[slot] === 1` — an already-evicted row needs no VISIBILITY notification (its mesh was hidden at eviction; doomed rows fail `exactVisible` at :133 and can't submit regardless). Optional belt-and-braces: after the presenter finishes the set-member loops, consume leftover dirty marks on slots that never entered either set — the completed full walk is the sync point those marks were notifying. That covers the preexisting stray classes too, but touches the dirty column so it needs the pose-delta-gating read at renderer.js:22595 accounted for (it runs before the sweep — safe).

**Effort:** S for the mint guard; M for the mark-consume variant. **Magic-frame impact:** M. **Risk:** L for the mint guard (visibility semantics unchanged — invisible doomed rows can neither draw nor submit); M for the sweep variant (the dirty column feeds the pose-dirty retain contract).

## Enumerations (a)–(e)

**(a) Doomed fast path per-frame cost — BOUNDED; the defect is on the mint side (F3), not the loop side.** A doomed row enters `hiddenSlots` exactly once — it is the prior-visible set-difference, not a per-frame membership (presentationQueries.js:342-352). The fast path itself (:22470-22491) is ~8 column reads + cheap writes: `applyEntityMeshVisibility` early-outs once `mesh.visible===false` (entityMeshVisibility.js:67-73), `clearDirty` is O(1) swap-remove (:1097-1101/:565-577), `markDirtyBits` early-outs on an unchanged mask (:579-586). No stamper re-dirties a doomed slot: mints are guarded by `doomed !== 1` (:969-970, :988-995); the clears are allocate :631 / retire :705 / unbind :794 / bind :782 / feed-stamp :943. Minor edge: `syncResolvingMarker(mesh)` at :22476 still runs inside the fast path — a doomed row pending admission materializes a resolving-marker child it immediately hides. Cosmetic waste, not a hitch.

**(b) 4ms policy budget under burst — F1.** The cap interacts as designed only for fresh mints; parked resumes bypass it and withhold verdicts bypass pacing entirely. Worst case = (8 + P) × 4ms + W atomic subtree traverses in one presented pass.

**(c) `hiddenSlots` churn with M doomed rows + N suppressed rebuilds — BOUNDED.** A doomed row pays the hidden loop once, at its single eviction. Re-entry requires doom→clear→re-doom, which needs the id to be pushed by a live feed then re-suppressed — source-state alternation, one hide+show cycle per row per oscillation, ~3 mark/apply ops each. Doom mints under repeated suppressed feeds are idempotent (`doomed !== 1` guard). No systematic per-frame churn.

**(d) Env-rebind drain starvation — F2.** Worse than the brief hypothesized: the drain is bounded per pass but never debits the shared ledger and has no aging floor, so a saturating residency pass starves it indefinitely.

**(e) Remaining whole-subtree/whole-scene walks on presented paths, ranked by worst-case node count:**

1. Atomic withhold verdict `syncShadowCasterPolicy(root)` — O(whole authored subtree, ~10³ nodes), unbounded count per pass → folded into F1.
2. `scene.updateMatrixWorld()` per presented frame (renderer.js:26161) — O(non-frozen subtree); `sfMatrixFrozen` prune (vendor/three.module.js:139-140) skips the static bulk. Documented basecost (PERF-59 lineage).
3. `guard.hide(scene)` full `traverseVisible` — amortized: steady-state early-outs on the programs latch + mount drain, full sweep ≤ every 30th pending-frame (`UNREADY_PENDING_SWEEP_FRAMES`, bloom.js:1247-1312).
4. `scanPresentedDrawables(root)` on mount drains — O(mounted subtree) per mount event (bloom.js:1291-1307).
5. Per-corpse `disposeObject` — inside the paced despawn queue with parked `disposeObjectSteps` iterators (renderer.js:1935-2024).
6. Bloom diagnostic traverses `describeUnstampedVisibleGeometries`/`describeNewGeometryOwners`/`describeNewProgramOwners` (bloom.js:1816-2062) — only on brick/threshold-blown frames, diagnostic-only.
7. `collectPresentationTextures` per released mesh — O(released subtree), bounded per release event.
8. `syncAuthoredInstancePools`/`syncAsteroidInstancePool` per frame — dense pool/slot iteration gated by dirty/version flags (partsLibrary.js:14267-14319), not tree walks.
9. `updateCameraOccluders` per frame — bounded `occluderCandidates` set (renderer.js:23253-23279).

Verdict: every remaining whole-scene walk carries amortization or pacing machinery; the lone unbounded whole-subtree walker on a presented path is the atomic withhold verdict (F1).
