## Findings (ranked)

### F1 — Post-await gen guard discards every `specByteHit` verdict — byte-equality reuse is dead, and the click re-pays the parse it just ran
- **Evidence: MECHANISM_VERIFIED**
- `src/save/saveSystem.js:4916` — the W136 deferred-consume guard is `if ((specHit || specByteHit) && spec && spec.sig !== 'gen:' + _saveStoreGeneration)`. `specByteHit` is defined at `:4875-4877` as `!specHit && spec.slot === slot && bytes-equal` — i.e. **spec.sig was already stale at latch** (otherwise it would be specHit). The condition `spec.sig !== 'gen:' + current` is therefore tautologically true for every byteHit consume: the guard always fires, discards the verdict the byte-equality proved identical, and re-prepares via `_prepareEnvelopeStringAsync(freshRaw)` — a second worker `restore_prepare` roundtrip + postMessage clone + `getItem` over the *same bytes* (`_prepareEnvelopeStringAsync` does not consult `_preparedEnvelopeCache` before dispatching, `:5052-5060`). Meanwhile `spec.dispatch()` was already flushed at `:4884-4886`, so the click pays the arm's clone+parse AND the discard+re-prepare — strictly worse than before W136, which consumed the proven-same-bytes verdict for free.
- **Mechanism the player sees**: a foreign-key write between arm and click (autosave landing on its own slot, `_queueSharedStoreMirror` writing `INDEX_KEY` — both bump `_saveStoreGeneration` without touching the armed slot's bytes) makes the next click re-run a multi-MB worker parse the W134 byteHit path existed to skip. The verdict is byte-identical either way — pure waste on the consume path, no correctness issue.
- **Fix sketch**: capture `const latchGen = _saveStoreGeneration` at `:4854-4856` (tracking already installed) and guard on `_saveStoreGeneration !== latchGen` — identical behavior for specHit (its `sig === 'gen:'+latchGen` at latch, so movement is the same predicate) while byteHit keeps its verified verdict when the generation didn't move during the window. If a real mid-window move is detected, the existing fresh-getItem re-prepare is already correct.
- **Effort: S. Magic-frame impact: M (re-pays the exact multi-MB parse class this lane exists to avoid, on a real cadence — any foreign write during menu dwell). Risk: low** — the mismatch path is already the miss path.

### F2 — `_pendingSlotRearm` fires without checking the live arm still covers its slot: steals a newer pick's arm, resurrects after disarm, retains the blob
- **Evidence: MECHANISM_VERIFIED**
- `src/save/saveSystem.js:394-404` — the coalesced re-arm snapshots `pending.slot = spec.slot` **at bump time** and unconditionally calls `speculateLoadPrepare(pending.slot, …)` on the `setTimeout(0)`. Three edge gaps, all verified in code:
  1. **Cross-slot steal**: a pick or mount restore between bump and fire mints an arm for slot B (debounced `spec._timer` parked). The pending fire calls `speculateLoadPrepare(A)`; the early-out at `:2637` requires `prior.slot === slot`, fails against the B arm, and `_armSpeculativePrepare` clears B's parked dispatch (`:2533-2534`) and replaces the arm with A's. The row the player is now selecting loses its warm — clicking B pays the cold prepare the arm existed to skip.
  2. **Resurrect-after-disarm**: `disarmSpeculativePrepare` (`:2666-2670`) and both screen teardowns (`saveLoad.js:1723` onHide, `:1756-1757` dispose) clear `spec._timer` but nothing clears `pending.timer`. A same-slot bump followed by hide/dispose in the same task window lets the pending fire mint a fresh arm **after** the disarm — with the mode still `'menu'`, the debounced dispatch (`:2596-2612`) pays `getItem` + clone + worker parse + the `save:envelopeSpecPrepared` visual-warm emit inside the next screen's window, exactly the cost the onHide disarm exists to prevent (`saveLoad.js:1719-1721`).
  3. **Retention**: the timer callback clears `pending.timer` but never `pending.raw` — the last same-slot bump's full multi-MB blob stays referenced on the save singleton until the next bump overwrites it.
- **Mechanism the player sees**: (1) a pick made in the same task window as a same-slot write silently loses its warm → cold click; (2) a hidden screen still spends a worker parse + decode warm on its last-armed slot; (3) one save blob's worth of heap pinned indefinitely.
- **Fix sketch**: inside the pending timer, re-arm only when a live stale arm still owns the slot — `const live = this._speculativeContinuePrepare; if (!live || live.slot !== pending.slot || live.sig === 'gen:' + _saveStoreGeneration) { pending.raw = null; return; }` — and null `pending.raw` after dispatching; also clear `pending.timer` inside `disarmSpeculativePrepare`. All drops are safe: a consumed/different-slot arm needs no re-warm, and a stale same-slot arm is exactly what this lane re-arms.
- **Effort: S. Magic-frame impact: M (kills the selected row's warm → cold click; one wasted clone+parse+decode-warm burst post-hide). Risk: low** — every added gate only narrows when the re-arm fires.

### F3 — Peek fill can stamp pre-bump card data onto a re-minted memo entry, then suppress its fresh refill
- **Evidence: MECHANISM_VERIFIED**
- `src/ui/screens/saveLoad.js:861-868` — the peek continuation re-resolves `entry = _slotDataMemo.get(slot) || entry` and writes `entry.data = cardData`, where `cardData` was parsed from `raw` captured at consult time (`:851`). If a same-slot write lands in the peek roundtrip window, the next `readSlotSaveData` consult mints a **new** entry stamped `sig: gen:N+1` (`:779-791`) — the `.then` then writes gen-N card data into the gen-(N+1) entry. `entry.data` set makes every later fill early-return (`:813`, `:850`), so the stale portrait persists until LRU eviction (cap 6, `:792-794`) or the next generation bump re-mints and refills.
- **Mechanism the player sees**: an autosave landing between a row's peek dispatch and resolve can pin a stale portrait on that row for the rest of the dwell — a cosmetic staleness stamped as current. W136 introduced this window: the old sync tail read+parsed+wrote in one task and could not interleave.
- **Fix sketch**: capture the filled entry's identity/generation at read time (`const fillEntry = entry` before dispatch — `entry` is already re-resolved at `:849`) and in the `.then` write only when `_slotDataMemo.get(slot) === fillEntry`; a re-minted entry reschedules its own fill (`attempted:false` → `scheduleSlotDataFill` at `:1292`) and refills from current bytes.
- **Effort: S. Magic-frame impact: L (cosmetic stale card, bounded by memo eviction). Risk: low.**

### F4 — `loadAsync`'s non-spec path restores click-window bytes with no generation re-check
- **Evidence: MECHANISM_VERIFIED**
- `src/save/saveSystem.js:4858-4869` — when neither specHit nor specByteHit holds, `raw` is materialized on the click task (`getItem` or the `slotBurst` raws), then two awaits open the window (`_captureRollbackSnapshotAsync` at `:4897`, `primaryPromise` at `:4910`). The `:4916` guard is `(specHit || specByteHit)`-scoped, so a same-slot write landing mid-window still restores the click-time bytes — the same bounded staleness class the W136 fix closed for the armed path, minus the "armed before the click" aggravation.
- **Mechanism**: restoring click-time bytes is arguably the intended load contract (there is no earlier armed snapshot), so this is a latent same-class asymmetry rather than a regression — but the contract the W136 fix established ("a stale verdict must never reach restore") applies identically once the window exists.
- **Fix sketch**: latch `rawGen = _saveStoreGeneration` next to the `getItem` at `:4867` and apply the same fresh-read + re-prepare on post-await mismatch; folds into the F1 `latchGen` guard for free.
- **Effort: S. Magic-frame impact: L (rare window, benign semantics — newer bytes stay on disk for the next load). Risk: low.**
