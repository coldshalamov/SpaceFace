## FINDINGS

1. **Suspended journal rebuild forces a full `world.rebuildFromEntities` inside every tick-advanced present** — `src/render/presentationPublisher.js:100-109` (fallback gate + call), `src/render/presentationWorld.js:804-822` (clear+realloc per row), `src/core/presentationJournal.js:604-608` (unconditional yield every 64 rows), `src/core/presentationRunner.js:771-774, 814-823` (4 ms collect deadline; publish iterator stashed shared collect only once minted).
   - Mechanism: while the stepped rebuild is in flight the mirror is invalid, so `fallbackFromState` runs `world.rebuildFromEntities(collect)` per present — an O(presentation rows) clear-and-republish on every rendered frame for the whole suspension window (a >64-row world always suspends; windows span several presents at ~1 present per yielded leg). While the *collect* leg is still walking, `rebuildCollectedEntities` is unset (`presentationRunner.js:867-871` requires `job.publishIter && Array.isArray(job.entities)`), so those presents also pay a **synchronous** `collectJournalPresentationEntities(state)` (O(entities + field.rocks + dressing + farActors)) before the rebuild — double whole-set cost inside one presented frame. This is the carried hitches-F3 residue, now precisely located: the diff-apply/K-capped variants were never implemented, so the window's per-present cost is still whole-world.
   - Fix sketch: keep a per-id `lastApplied` revision/row map on the publisher side and let the fallback do a bounded delta-publish — reuse mounted rows for ids whose journal revision is unchanged, insert/despawn only the pending range, cap work per present at K rows with a resume cursor. The world is already just collect→publishVisit; a faithful delta needs only alive re-filter parity and row-order/capacity invariants preserved (bridge slots, `rebuildCollectedEntities` membership). If the delta map is too invasive, a cheaper half-step: serve `job.entities` as soon as the collect leg finishes (before publishIter mints) to kill the sync-collect half, and K-cap `publishVisit` inside `rebuildFromEntities` with a resume cursor so the clear cost amortizes across presents instead of stacking per present.
   - Effort: M-L. Magic-frame impact: H (sustained multi-ms work inside presented frames exactly while a rebuild runs — the pop-in-adjacent hitch class this lane hunts). Risk: M — a wrong delta map strands or resurrects rows; keep the full rebuild as the escalation fallback.

2. **Authored-boundary commit continuations over-debit the paced ledger by the deferred-yield wait** — `src/render/partsLibrary.js:4285-4298` (`commitAuthoredPlaceBoundary`) and `src/render/partsLibrary.js:9356-9370` (`commitAuthoredBoundary`).
   - Mechanism: both seams restamp `commitLegStarted = monotonicNow()` immediately before `await waitForAuthoredAdmission(yieldToNextPresent(), options)`, then the `finally` charges `notePacedFrameSpend(monotonicNow() - commitLegStarted)` — the debit covers the whole between-presents wait (~16 ms typical, up to the 48 ms unstick) plus the real `disposeDetachedPlaceFallback` cost. On the resume frame the ledger reads ≥4 ms spent, so every `pacedFrameSpend() >= PACED_FRAME_BUDGET_MS` gate fires and sibling paced lanes (reconcile pump, decode drain, emit slices) defer ~one frame per commit leg; under a burst of commits the phantom spend serializes them. Contrast with the correct pattern already in the same file — `pacePolicyWalk` (8411-8418) debits work-then-awaits — and `visualFactory.js:4265-4274` (`driveLeg` debits before await).
   - Fix sketch: restamp `commitLegStarted` inside the `finally` (just before `disposeDetachedPlaceFallback`) so the debit covers only the dispose work; identical at both seams.
   - Effort: S. Magic-frame impact: M (pacing degradation — delayed paced work, not corruption). Risk: L — strictly reduces a recorded charge.

3. **`_applyFrameOriginRebase` is an unbounded O(_meshes) atomic walk inside the presented frame** — `src/render/renderer.js:22000-22035`, invoked at `23413-23417` before pose sync on every `frameOriginSeq` advance.
   - Mechanism: each rebase walks every mounted mesh synchronously (`m.position.x += dx; z += dz`, plus `updateMatrix()` on `matrixAutoUpdate===false` roots), then hazard-visual positions, a full contact-shadow record clear, `invalidateAsteroidInstancePool`, and `vfxReprojectFrame`. Correctness requires same-frame completion (a half-rebased scene renders displaced), so it cannot be naively sliced; but the row count is the whole mount set, unbounded and uninstrumented.
   - Fix sketch: fold the shift into the per-frame band walks that already visit every mount (the table pose sync re-poses dirty rows; untouched mounts could carry a `rebaseEpoch` stamp applied lazily at their next pose/compose read), or memo the shift per mesh and apply at read. Cheapest legal variant: stamp each mesh with the applied `frameOriginSeq` and let `syncEntityViews`' existing walk do the add when it touches the row — meshes the walk skips get the stamp lazily via `matrixWorldNeedsUpdate` propagation that already forces frozen roots through `updateMatrix`. Alternatively measure first: per-row cost is ~tens of ns, so at ~4k meshes this is sub-ms and only on rebase — if telemetry says it's cold, document instead.
   - Effort: M. Magic-frame impact: M-L (rare per event; row count unbounded). Risk: M — any laziness that lets one mesh render at the old origin for a frame is a visible glitch; the stamp must be applied before that mesh's compose this frame.

4. **`visualFactory` packaged-pipeline failure path leaks the detached compiled subtree** — `src/render/visualFactory.js:4393-4414`.
   - Mechanism: on `prepareAuthoredVisualPipelines(packaged)` throw, the catch returns `awaiting-authored-admission` / `orphaned-before-swap` / `fallback-after-error` without `disposeDetachedPackagedGroup(packaged)`. Every neighboring exit (4381-4387, 4417, 4425, 4435) disposes it; this subtree was already freeze/canonicalize-processed and pipeline-prepared, so its GPU payload leaks per failure event — residency pressure that can translate into evictions and late re-admissions.
   - Fix sketch: hoist `try { disposeDetachedPackagedGroup(packaged); } catch {}` ahead of the verdict returns inside that catch (same as the `detachCommitGroup` disposal the outer `.catch` already does at 4456-4459).
   - Effort: S. Magic-frame impact: M-L (leak → residency pressure → late admission risk, not direct pop-in). Risk: L.

5. **`settleRebuildBridges` iterates the whole bridge map every presented frame with no per-frame cap** — `src/render/renderer.js:2012-2035`, called from `serviceRenderMeshResidency` at `2044`.
   - Mechanism: each frame walks every pending bridge (`entities.get` + epoch + `rebuildBridgeDrawable` per row). `REBUILD_BRIDGE_MAX_SYNCS` bounds a slot's lifetime, not the per-frame scan; a burst of parkable rebuilds makes the scan O(in-flight bridges) inside every presented frame until they age out.
   - Fix sketch: per-frame cursor or empty-check early-out (already has `size===0`), or cap processed rows per frame and round-robin — releases are idempotent (`releaseRebuildBridge` deletes then releases).
   - Effort: S. Magic-frame impact: L (tiny per-row cost; worst case bounded by rebuild burst size). Risk: L.

## RESIDUAL ANSWERS

- **(a) hitches-F3 — suspended rebuild across TICK-ADVANCED presents:** still pays full `world.rebuildFromEntities` per present (finding 1). A journal-record-range diff-apply is legal: the publisher could keep `lastAppliedRevision` per id and apply only the pending retained range (insert/destroy/dirty) against mounted rows — what breaks if done naively: row ordering/capacity invariants inside `publishVisit`, alive re-filtering (804-809), and bridge-slot interplay; also the *collect* half of the fallback (sync `collectJournalPresentationEntities` while the stepped collect is still walking) must be served by `job.entities` earlier or it stays O(whole set). Both halves are fixable inside the contract.
- **(b) shared-collect staleness under suspension:** covered. `fillPose` reads live entity fields at publish (journal.js:81-102 inside `emitRebuildRow`); `world.rebuildFromEntities` re-filters `entity.alive === false` (world.js:809); suppressed `destroy`/non-member writes doom the attempt (272-275); suppressed TRANSFORM/VISUAL on an already-published member id are replayed live via `rebuildStalePublishedIds` (614-636); duplicate spawn → `requestRebuild` → invalidated (346-350, 261). Retained records carry write-time snapshots by design — queue lag, not staleness; no permanent-stale class found within the four tracked kinds. Fields outside the journal protocol are outside this mechanism's scope entirely (pre-existing, not a suspension defect).
- **(c) remaining synchronous whole-set drains inside presented frames, ranked by worst-case rows:** (1) `world.rebuildFromEntities` fallback — O(presentation rows) per suspended present [finding 1]; (2) sync `collectJournalPresentationEntities` inside that same fallback while `rebuildCollectedEntities` is still unset — O(entities + field.rocks + dressing + farActors) [finding 1, second half]; (3) `syncJournalRebuildEscalation` — the sanctioned atomic O(collect + publish) valve after 3 invalidations (runner.js:743-754) — deliberate, bounds livelock; (4) `_applyFrameOriginRebase` — O(_meshes) per origin rebase [finding 3]; (5) `settleRebuildBridges` — O(in-flight bridges) per frame [finding 5]; (6) `_flushMeshReleasePending` — O(pending release set), bounded. Everything else on the presented path is budget-gated (`_drainMeshBuildQueue`/`_drainPendingMeshBuilds` RUNTIME_MESH_BUILD_BUDGET, emit-slice caps, `drainDeferredEnterSlice` 4 ms, paced-ledger `shouldYield` on the unSliced admission lane at 10714-10715) or tick-latched (`ensureActivityClassified` membership/static-authority versions + quiet latch, activityRuntime.js:1824-1859).
- **(d) commit continuations under released/frozen ledger:** the ledger falls back to an 8 ms wall-clock window (`PACE_FRAME_WINDOW_MS`, epoch −1) only when the rAF pump is stale >250 ms, and `debitGate: () => state.mode === 'flight'` keeps loading-mode legs out of the tally — so pacing can't freeze a user-visible commit beyond one `yieldToNextPresent` unstick (≤48 ms). The real residue is the over-debit in finding 2, which *delays sibling paced work* ~one frame per commit leg; post-flight teardown commits hit the same shape.
- **(e) `JOURNAL_REBUILD_INVALIDATED_MAX=3` livelock:** bounded. Stepped attempts doom at invalidated-after-3 → `syncJournalRebuildEscalation` (runner.js:743-754) runs one atomic `rebuildFrom`+commit inside a single task — no yields means no write can interleave, so the atomic attempt cannot self-doom and the storm terminates it in one bounded sweep. A write storm worst-case costs ≤2 doomed stepped attempts (~2×(collect≤4ms + partial publish)) plus one atomic O(set) commit inside one present — the correct release valve; a retry/backoff alternative would let the mirror lag unboundedly. Only refinement worth noting: the doomed attempts' partial-publish cost is wasted work that a write-rate detector could skip by escalating on first invalidation under sustained storms — S effort, L impact.
