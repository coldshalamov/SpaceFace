## Findings (ranked)

### 1. Ghost mint-defer probe leg is dead code — `data.resolvingMarker === true` can never be true; the hidden-but-resolving defer never triggers via the marker path

Evidence: `src/render/crucibleGhost.js:154-155` — the probe counts `data.admissionStandInPending === true || (data.resolvingMarker === true && obj.visible === false)`. Every writer stores a **Mesh reference** under `userData.resolvingMarker`, never a boolean: `src/render/visualOverrides.js:467` (`data.resolvingMarker = marker`), `:672` (`substrate.userData.resolvingMarker = standIn`), `:675`, `:740` (`root.userData.resolvingMarker = marker`). The tag the leg intends is `authoredResolvingMarker === true`, written by `resolvingMarkerFor` (`:352`), `materializeBoundaryResolvingMarker` (`:468`), and `directAuthoredAdmissionSubstrate` (`:746` — the substrate root itself, which is also built `root.visible = false` at `:703`). `detachBoundaryResolvingMarker` (`:620-627`) purges stray nodes by that same key.

Mechanism: the comment at `crucibleGhost.js:47-49` states the contract — "a mint landing while the source hull is inside the admission hidden-but-resolving window freezes that transient visible=false into the clone forever — defer the clone while pending." With leg 2 dead, the only live defer is `admissionStandInPending`, which covers exactly one path: `directAuthoredAdmissionSubstrate` sets it only when **no** standInRecord existed at build (`:726-727`); `materializeBoundaryResolvingMarker` sets it only on the octahedron fallback (`:459-461`). A substrate built with a resident record (a real `lodStandInFor` stand-in) carries `admissionStandInPending` unset — its hidden marker/root window mints the ghost immediately. The minted clone freezes `visible=false` on every child at clone time; the live side's marker flips visible via `syncResolvingMarker` (`renderer.js:3424` `marker.visible = true` per pending-status frame — property-only, not structural), and the substrate root's own visibility flips through the same non-structural path, so `clonedChildren` never drifts and the stale clone persists until the next depth-1 structural event (`upgradeAdmissionStandIn` `substrate.remove(marker); substrate.add(standIn)` `:671-672`, `detachBoundaryResolvingMarker`, authored `commitAuthoredBoundary` `boundary.remove/add` `partsLibrary.js:9193-94`, or procedural-fallback `parent.add(fallback)` `renderer.js:3465` — all depth-1). Player-visible effect: during the crucible's own authored-pending window — exactly when the ghost exists — the ghost presents a hull missing its resolving stand-in (or fully invisible, when the mint catches `root.visible=false` on the substrate). Bounded and self-healing, but a real divergence between ghost and live silhouette.

Fix sketch: `data.authoredResolvingMarker === true && obj.visible === false` in place of `data.resolvingMarker === true`; alternatively delete the leg — live leg 1 already covers the no-record retry window, and the defer is bounded by `GHOST_MINT_DEFER_MAX = 60` presented syncs (`:50`, `:152-157`) so a permanently-hidden terminal marker can never block the mint indefinitely. Effort: **S** (one identifier). Magic-frame impact: **L** — ghost-only divergence, self-heals at every structural transition, and the ghost never shows *more* than the live hull. Risk: **trivial**.

### 2. Launch-warm census yields every 6 *instantiated* records — fat rows stack tens of ms inside one task, and skipped rows never tick the cadence

Evidence: `src/render/renderer.js:17020` (`if (instantiated % 6 === 0 && yieldStep) await yieldStep();`), `:17015` (`instantiated += 1` only when `holder.children.length > 0`), `:17023` (`budgetLeft() <= 4000` break), call site `:12971-12974` (`yieldToMain` defaults to `yieldToBrowser` = `scheduler.yield()`/`setTimeout(0)`, `startupGpuResidency.js:684-689`). Per instantiated row the loop pays `instantiatePackagedPrimitives` + `seenWarmPairs` twin minting + `paletteWarmSubjectsForRecord` per palette + `canonicalizeObjectSurfaceProgramKeys(holder)` + (renderPackage rows) `warmRenderPackageShipPool` await — six fat hull rows ≈ tens of ms in a single task. The sibling consumer of the same census, `_mintDeferredPaletteSubjects` (`:17722`), paces on a 4 ms wall-clock slice (`scanNow() - sliceStartedAt > 4 → await yieldToBrowser(); notePacedFrameSpend(...)` at tail) — this loop does not.

Mechanism: the census runs inside the crucible cook behind the loading shell, so a single ~30-80 ms block lands as one loading-screen micro-stall (DOM progress animation freezes for that task) rather than a multi-second freeze — it is the residual of the (d) hunt, already bounded by the 4 s budget break, but the pacing knob counts *mounted holders*, not elapsed time or visited rows: a run of records producing empty/skip rows contributes nothing to the yield cadence (cheap anyway — three `normalizeFile` calls each), while a run of six heavy records concentrates the worst case.

Fix sketch: mirror the sibling — replace the `% 6` counter with a per-iteration `scanNow() - sliceStartedAt > 4` wall-clock check (or `instantiated % 2 === 0` plus the clock), and debit `notePacedFrameSpend` so sibling slicers see the spend. Effort: **S**. Magic-frame impact: **L-M** (a class of 30-80 ms tasks inside the gated cook; ordering and budget semantics unchanged). Risk: **low** — more frequent `scheduler.yield()` inside a loop that already yields; no ordering or coverage change.
