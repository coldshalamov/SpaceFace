## Ranked findings

### F1 — `drainMeshBuildsBehindShell` re-pays `_drainMeshBuildQueue`'s prologue once per build: O(queued × entityList) atomic amplification inside the shell drain

- **Evidence.** `drainMeshBuildsBehindShell` (`src/render/renderer.js:11155-11192`) loops `while (_meshBuildQueueHead < length)` calling `this._drainMeshBuildQueue(1)` per iteration (`:11178`) — a fresh `_drainMeshBuildQueueSteps` instance per call. That twin's prologue (`:19873-19920`) mints, per invocation: the late-present gate (`:19878-19888`, skipped under loading), `drainScan = makeHoldExemptScanContext(state)` (`:19898`), `simNow` (`:19895`), `glassVerdictMemo` (`:19877`), and — the heavy term — the firstFlightIds newcomer census (`:19905-19919`): a full `state.entityList` walk with `isEntityRenderRelevant` + `entityWithinPlayerRadius` per entity, gated on `liveSectorFirstFlightIds` non-null AND `liveSectorGpuAdmission || sectorShellAdmission`. `liveSectorGpuAdmission` is set at `:11107` for the whole cook (cleared `:12498`); `liveSectorFirstFlightIds` is minted at `:11623`, so the census fires on the big post-widen drain at `:11668` (and any drain after ids publish), once per dequeued build.
- **Mechanism.** The shell drain is the path that builds the widened first-flight cohort behind the loading screen. With queue depth D (~hundreds after the widen pass enqueues the arena) and entityList E (~thousands on a populated/survival sector), the drain pays D × O(E) of pure-JS predicate work — hundreds of whole-entityList censuses — each an atomic block between `buildYield` slices. The loading presenter (the only rAF still presenting) freezes per census call, and the drain's wall-time stretches by the quadratic excess — measured class on this codebase's own numbers: ~2-6 ms per O(E) census × hundreds of calls ≈ seconds of extra shell time + spinner jitter. W79 made the drain's row loop stepped but left the *call granularity* at one-build-per-invocation, which is what makes the prologue re-run.
- **Fix sketch.** Drive `yield* this._drainMeshBuildQueueSteps(remainingBudget)` ONCE per `drainMeshBuildsBehindShell` call instead of `_drainMeshBuildQueue(1)` per row — the stepped twin already yields per examined row (`:19922`), so pacing is preserved while the gate/scan/census prologue mints once. Or hoist the prologue into a per-drain context ({drainScan, census results}) passed into each `_drainMeshBuildQueue` call — the queue-head consumption contract is unchanged either way. The only semantic delta is census frequency: newcomers minted mid-drain wait for the next invocation (same as flight drains already accept, `:19772-19774`).
- **Effort** S–M · **Magic-frame impact** H (dominant unsliced pattern in the boot cook; freezes the shell's own presenter and stretches wall time — both are the lane's bar) · **Risk** L–M — the stepped twin is already the flight path's contract; verify `firstFlightIds` still accumulates post-census newcomers correctly when the census runs once per drain session.

### F2 — Survival settle censuses are atomic traverses re-paid per wait-loop pass: `collectNeverLinkedSceneRoots` (full scene traverse × ≤4 sweeps) + `kickMountedBoundaries`/`pendingBoundaryLoads` (`_meshes` scans every iteration)

- **Evidence.** Inside the survival settle loop (`:12310-12370`): `collectNeverLinkedSceneRoots` (`:7545-7571`, called `:12340`) is one `scene.traverse` over the whole graph (~16-21k nodes on Crucible-class scenes — the code's own comment at `:13196-13201` sizes the same walk at ~21k), plus `renderer.properties.get(material)` per drawable material and an ancestor walk per never-linked hit; it re-runs each time stragglers exist, capped at `neverLinkedSweeps >= 4` (`:12341`). `kickMountedBoundaries` (`:12250-12263`) and `pendingBoundaryLoads` (`:12268-12306`) each scan `this._meshes` on EVERY settle-loop iteration — a 60-120 s settle window (`:12306`) with 4 s wait quanta can re-walk the mesh map tens of times.
- **Mechanism.** Every call is an uninterrupted synchronous block inside the cook task. During loading the only thing presenting is the shell itself, so each traverse is a visible spinner/progress hitch (tens of ms each on a populated scene), and the repeated `_meshes` scans multiply it across the wait loop. These are also the legs that run last — they sit between "everything queued" and "shell releases", so their cost lands entirely on the loading-screen freeze metric.
- **Fix sketch.** `collectNeverLinkedSceneRoots` gets a chunked twin on the `collectInstancePoolCompileRootsAndSubjectsSteps` pattern (`latePipelineAdmission.js:216-251` — stack + seen are already generator-safe) driven on `yieldAndFlushLiveSectorGpu`; fold `kickMountedBoundaries` + `pendingBoundaryLoads` into a single `_meshes` pass per iteration (they already both walk it); memoize the straggler list across sweep iterations (only re-walk roots whose material set changed — a `renderer.properties` version check bounds this).
- **Effort** M · **Magic-frame impact** M (shell freezes; no presented-frame cost — the cook is loading-only) · **Risk** L — the never-linked verdicts are read-only probes; order-independent.

### F3 — Receipt mint + settled-plan rebuild: a chain of full-scene walks and per-material hashing at the cook tail (`buildOpeningSubmissionPlan` ×4 call sites + `createOpeningSubmissionReceipt`)

### F5 — `compileSubjectColorAndDepth` stays per-subject atomic inside the issue loop (hunt-(b) residual)
