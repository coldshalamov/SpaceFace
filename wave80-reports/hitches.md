## Ranked findings

### F1 — The stepped refill is now sliced per drive but the memo discs are still module-global: two independently-clocked `warmNearbyLedgerRowsSteps` can interleave and tear the committed scratch

- **Evidence.** `warmNearbyLedgerRowsSteps` (`src/world/presentationSources.js:622-660`) writes the shared module scratches `_meshFarScratch`/`_meshRockScratch` via `yield* queryFarActorsSteps(state, _meshWalkOrigin, ..., _meshFarScratch, batchRows)` (`:644`) and `yield* queryAsteroidFieldSteps(..., _meshRockScratch, ...)` (`:655`); each inner generator's first statement is `out.length = 0` (`farActorTable.js:596`, same shape in `asteroidField.js:184+`). W79 minted this stepped twin at four independent drives that do not mutex each other: (i) `_reconcileIter` → `yield* warmNearbyLedgerRowsSteps(state)` parked inside the pump's reconcile generator (`renderer.js:19435`, drive at `:2117-2141`); (ii) `_residencyPollIter` → same `yield*` (`:19616`, drive at `:2170-2189`) — the poll mint at `:2159-2162` is gated only by the 250 ms cadence/zoom/focus triggers (`:2057-2074`), *no mode gate*, so it mints and drives during ordinary `'loading'` cook frames whenever the earlier branches don't engage (`_sessionRecookKeepGpu` false at `:1858`, no seam hold `:1873`, no `_seamDeferredDrain` `:1991`, `holdFirstFlightStreaming` is flight-only `:1382`); (iii) the cook's **local** `warmIterator` (`:11553` widen drive, `:13779` jump-cook twin) resumed by `await yieldLiveSectorGpu()` continuations — an entirely different clock, ownerless; (iv) `_holdExemptWarmIter` parked across hold beats (`:2567-2581`, remint `:2706-2715`). A suspended pump iter mid-far-leg + a resuming cook warm = two live generators on one scratch: B's `out.length = 0` discards A's partial fill, A resumes appending stale-plan rows past B's prefix, and whichever completes last calls `rememberMeshFarKey(state, walkX, walkZ, walkRadius, walkRadius + collectOverlap)` (`:646`) stamping ITS plan's key + `far.collectDisc` (`:319-324`) over the mixed contents. The chunked collect then snapshots whatever is committed (`_meshRockScratch.slice()`/`_meshFarScratch.slice()` at mint, `:699-700`) — torn rows serve downstream collects as if honestly covered.
- **Mechanism.** Any cook window that overlaps a parked sweep-warm (carried across the flight→loading flip: `:2094`'s epoch guard only abandons on enterSerial change, not mode change) or a poll minted during the cook produces a disc whose stamp claims coverage for rows it never gathered — the rows missing are exactly the far-edge rows (inbound hulls, decode-runway candidates) the disc exists to cover. Worse, it's sticky: `ridesFar`/`meshFarKeyMatches` (`:407-408`, `:292-302`) suppress re-refill while version/cell hold, so a quiet-sector tear persists into the first presented post-cook frames — entities pop in late or sit meshless until the next version bump. Pre-W79 this was unreachable — the sync warm never suspended.
- **Fix sketch.** Stage refills in own arrays: `const farRows = []; yield* queryFarActorsSteps(state, origin, r, farRows, batch)` then publish `scratch.length = 0; scratch.push(...farRows)` inside the same step that runs `rememberMesh*Key` — commit stays atomic, partial work is never visible, two drives degrade to last-writer-wins with an honest stamp (each commits the disc its own query actually walked). Alternative/addition S: a module `_ledgerWarmOwner` token — mint takes the token, a second drive's mint `.return()`s/abandons the parked one (cheap, keeps shared-scratch layout).
- **Effort** M (own-array staging + commit-time publish, all four drives share the one helper) · **Magic-frame impact** H (holes/late pop-in on the exact frames after a cook hands off to flight — the lane's core defect class) · **Risk** M — publish-at-commit must keep `collectDisc`/`rides` semantics and the tolerateMiss empty-disc contract (`:639-641`) byte-identical for readers.

### F2 — `rememberMesh*Key` stamps the live `far.version`/`field.version` at commit — a mid-walk membership bump is absorbed into the stamp instead of invalidating it

- **Evidence.** `rememberMeshFarKey` reads `far && ... far.version` at call time (`presentationSources.js:315`); `rememberMeshRockKey` likewise (`:289`). The commit runs after `yield* queryFarActorsSteps` completes (`:646`, `:657`) — i.e., beats after the plan minted. A `far.version` bump landing mid-walk (promotion/spawn into an already-visited column — the cell path reads `grid.get` per column at `farActorTable.js:628-630`, so only unvisited columns still see it) gets no row in the scratch, yet the stamped key claims the *post-bump* version: `meshFarKeyMatches` (`:301`) and `farCovered` (`:403-406`) still hit, `ridesFar` suppresses refill. The W79 comment asserts the opposite ("a mid-refill membership bump just makes the completed stamp stale", `:618-620`) — true only if the stamp carried the plan-minted version. Removals are benign both directions (`alive === false` filters at push `farActorTable.js:583` and collect `presentationSources.js:561`); movers self-heal via `catchUpFarRecord`'s rim-watch (`:316-318` comment); **stationary additions into visited columns never heal** until unrelated churn. Remint-with-toleration paths (`:2706-2712`) make it stickier — the remint's warm rides `ridesFar` and skips the leg.
- **Mechanism.** A parked sweep-warm or cook warm that spans a far-table membership event commits a stamp asserting coverage it doesn't have; the missed row sits invisible (no mesh enqueue) until the *next* bump — silent under-coverage, not a one-frame blip. Window is small per walk (a few beats) but exists on every bumped walk.
- **Fix sketch.** Carry the plan-minted versions through: the plan already computes `farVersionNow`/`fieldVersionNow` (`:402`, `:423`) — stamp those verbatim in `rememberMesh*Key` (add a version param) so a mid-walk bump leaves the stamp stale and the strict 'covered' gate honestly re-fetches, exactly as the comment promises. Sync path unchanged semantically (plan≈commit there).
- **Effort** S · **Magic-frame impact** M (sticky invisible far/field members; rare but silent) · **Risk** L — stamping an older version only ever causes an extra refill, the designed-safe direction.

### F3 — `_drainMeshBuildQueueSteps`'s prologue still lands gate + tail hoist + scan mint + O(entityList) newcomer census inside one `next()` — the largest remaining single sweep step

- **Evidence.** First `next()` of the stepped drain (`renderer.js:19855-19920`) runs: `shouldStartHeavyAdmissionEventually` gate (`:19879`), possible `hoistDeadlineGlassMeshBuilds` O(queue-tail) verdict scan (`:19885`), `makeHoldExemptScanContext` mint (`:19898`), then the `firstFlightIds` newcomer census (`:19905-19920`) — `for (const entity of this.state.entityList)` × `isEntityRenderRelevant` + `entityWithinPlayerRadius` per row — gated on `liveSectorGpuAdmission || sectorShellAdmission`, i.e. **every drain while the latches are armed** (all cook windows plus their persistence tail). Only then does `while (...) { yield; ... }` start yielding per row (`:19921-19922`). The pump's consults (`:2139`, `:2187`) can only measure the step whole.
- **Mechanism.** During cook-adjacent windows (latches armed — exactly when firstFlightIds exists and matters) every poll/reconcile drain's first step is O(entityList × 2 predicate verdicts) + gate + scan mint — multi-ms inside one `next()` on a fat sector; the same frame then still runs the drive's remaining slice.
- **Fix sketch.** Split the prologue into minted steps: `yield` before the newcomer census and per-1024 inside it (the loop is a flat scan, trivially chunked — `firstFlightIds.add` order-neutral); hoist `drainScan` mint into the caller's own step as the W79 pattern already does for the collect warm. The sync driver's parity is preserved — it drains every yield inline regardless.
- **Effort** S-M · **Magic-frame impact** M (one multi-ms step per drain during latch windows, recurring) · **Risk** L — chunking a mint loop; verdicts per entity already tolerate the drain scan context.

### F4 — `residency.releaseDetachedBoundaryOwners` is one atomic O(owners × ancestor-walk + claim checks) call inside a single step

- **Evidence.** `_releaseDetachedBoundaryOwnersSteps` yields per census chunk (`:19104`, `:19114`, `:19121`) then at `:19137` calls `residency.releaseDetachedBoundaryOwners({...})` — inside `assetResidency.js:397-412` that is `[...owners.entries()]` (full owner-map snapshot alloc) + per-owner `isDetached` root walk + `isClaimed` set/fallback chain + `releaseOwner` — all inside ONE `next()`. Owner teardown after it is per-owner-yielded correctly (`:19146-19159`); the scan itself isn't.
- **Mechanism.** ~1/s (gated by `residencyPruneSweepDue` `:2489-2497`), one step carries the whole owner census — bounded by owners count (tens-hundreds; sub-ms to ~1 ms typical, worse in pathological parked-boundary piles). Smallest of the residuals but still an unchunked unit inside the sweep.
- **Fix sketch.** Chunked twin in assetResidency (`releaseDetachedBoundaryOwnersSteps` yielding per K owners) or hoist the census into the outer generator's yield cadence. `[...owners.entries()]` can be iterated chunked without the spread.
- **Effort** S · **Magic-frame impact** L-M · **Risk** L.
