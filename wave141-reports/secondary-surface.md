### C3 — contextRestoreConsult latch via `.finally` on the assigned promise (`c01b8e2d5`) — MECHANISM_VERIFIED
The old in-body `finally` genuinely pinned the latch: with empty pendings the async body completes synchronously, so `contextRestoreConsult = null` ran BEFORE the assignment stored the promise — latch truthy forever → bloom held at :8825 and every later restore early-outed. Now `.finally(() => contextRestoreConsult = null)` runs as a microtask on the assigned promise (:1422): always after assignment, always before any later event-dispatched `webglcontextrestored` (DOM events are tasks; the microtask drains first). Ordering is airtight.
- **Early-out ordering**: `dropGeometryGpuResidencyLedger(renderer)` runs BEFORE the latch check (:1405-1406), so a second restore mid-consult still clears this renderer's stale `uploadedOn` stamps.
- **Residual window (asked)**: a SECOND restore during an in-flight consult early-outs — is the draw still correct? Collected pendings: yes — rehydrate is CPU-side (`entry.detached=false`, arrays refilled, `record.version` bumps force WebGLAttributes.update on next bind, packageCpuDetach.js:622-632), valid regardless of how many times the context dies afterward; three re-uploads real bytes on next bind. Uncollected case: a NEW detach between the consult's synchronous collect and its `.finally` stays pending with no follow-up consult until a THIRD restore — and a bind on it after latch-clear uploads emptied arrays (texture case throws inside render; `frame()` re-arms rAF first, asteroidScreen.js:2140, so the loop survives degraded). On THIS renderer such a detach cannot self-generate: `bloom.render` is suppressed while latched (:8825) and detaches only run inside residency passes (`prepareStartupGpuResidency`, startupGpuResidency.js:809/901) or package adoption — i.e. only a cross-context residency pass over shared manifests could land one in the window. Narrow, pre-existing (the early-out predates this commit), bounded by the next restore. Optional hardening: queue a re-collect when a restore lands mid-consult instead of pure early-out.
- The `!contextRestoreConsult` hold at :8825 sits inside `render()` — the rAF loop and all DOM/sim sync keep stepping; only the GL draw is held for the consult's duration.
