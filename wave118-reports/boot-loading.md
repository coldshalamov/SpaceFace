## Findings (ranked)

### F1 (M/S) — armed disposer slot survives the ship pre-graft stale bail; blocks the live run's install and leaks its prepared tree
- Evidence: `src/render/partsLibrary.js:9884-9893` (install guarded by `!== 'function'`), `:9908-9917` (W117 stale bail calls `disposePreparedShipBoundaryResources` **directly**, bypassing the armed `__disposePreparedAuthoredBoundary` slot), `:9288-9316` (`installPreparedBoundaryDisposer`/`disposePreparedAuthoredBoundary`), `:15632` (`preparedAuthoredRoots` is a strong `Map<boundary, Set<root>>`).
- Mechanism: run A (deferBoundaryPublication, e.g. renderer.js:11391/20209/22222/25547) arms the slot, then bails at the new pre-graft stale recheck — the slot stays armed with A's dead closure. Run B's install is skipped (slot armed). On B's own `!boundary.parent` bail under deferPub, `disposePreparedAuthoredBoundary(boundary)` fires **A's** closure: A's authored re-disposes idempotently (`preparedCleanupComplete` guard, :9228) but **B's live prepared root is never disposed** — composed tree, renderPackageInstances, and its `preparedAuthoredRoots` registration pin for the session. External teardown callers (renderer.js:20806/21358/22641/22674/25625) have the same blind spot.
- Fix sketch: inside `commitAuthoredBoundary`, capture the install return (`const installed = installPreparedBoundaryDisposer(...)`) or snapshot `boundary.userData.__disposePreparedAuthoredBoundary` at install, and on every post-install bail route through `disposeOwnedPreparedBoundary(boundary, installed)` / the armed slot instead of the bare `disposePreparedShipBoundaryResources` call — the place path's `(installedPreparedDisposer ? installedPreparedDisposer() : disposePreparedPlace()) || disposeOwnedPreparedBoundary(...)` contract (:3341, :4297-4342) is the model. Ship commit should receive the caller's `installedPreparedDisposer` like `commitAuthoredPlaceBoundary` already does (:4435).
- Effort S · impact M · risk: low (mirror of an existing pattern; `disposePreparedAuthoredShip` is idempotent).

### F2 (M/S-M) — driver-bank `finally` doesn't roll back `activate()`'s registry/userData side effects on abandon
- Evidence: `src/render/authoredMotion.js:212-223` (`updateWorkfleet`, `updateDriveState`, `updateCeresPhysicalState` stamped pre-yield), `:230-247` (`activate()` mutates module `registry` — `registry.set(entityId, ...)` + `site:` alias keys), `:249-251` (two `yield`s *after* `activate()` runs, inside the try), `:320-322` (`primeMotionTravelPad` yield also inside try), `:340-367` (`bankTransferred` then `finally` disposes `driverBank` only).
- Mechanism: a suspended attach abandoned at the post-activate or pad yields (`.return()` from a stale-verdict drive) disposes the banked drivers but leaves `registry.set(entityId, live)` + alias registrations live and the userData stamps on the orphaned root. The entity's controller set then keeps receiving authored-motion events against a dead tree — per-event waste + a pinned controller set, i.e. ghost dispatch the bank was built to kill. `retired`/`__authoredMotionDeclined` also never get stamped on the abandon path.
- Fix sketch: in the `finally` under `!bankTransferred`, when `registered === true` run the same teardown grammar `detach` runs for registration cleanup — `registry.delete(entityId)` + alias-key set deletes, `retired = true`, userData key deletes — then dispose the bank. Order: undo registration *before* driver disposes (detach's own order).
- Effort S-M · impact M · risk: low-M (must share the grammar with detach, not re-implement it; gate strictly on `!bankTransferred` to avoid double-clean on the normal path).

### F4 (L/S) — `installPreparedBoundaryDisposer` lacks the epoch guard its publisher twin just got
- Evidence: `src/render/partsLibrary.js:9288-9310` vs `:9355-9371` (publisher captures `installedEpoch` and refuses on mismatch).
- Mechanism: the disposer wrapper fires whatever closure is armed with no freshness check — the same stale-serve class W117 closed for publishers. Mostly masked today by `disposeOwnedPreparedBoundary`'s identity check and `releaseOwnerInstances`' `__ownerReleaseScope` filtering, but a fired stale slot still disposes dead work and self-deletes, blocking the live run's install (compounds F1).
- Fix sketch: capture `installedEpoch` at install and refuse (return false, no self-delete) when `boundary.userData.admissionEpoch` no longer matches — identical to the publisher guard.
- Effort S · impact L (M combined with F1) · risk: low — a refuse must not become a wedge for teardown callers that legitimately fire post-epoch (teardown always fires the *armed* slot to clean whatever generation is parked; guard only when the slot's own run is still prepared-not-committed).
