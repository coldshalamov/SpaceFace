## Findings (ranked)

### BOOT-F1 — In-flight loads pay a synchronous O(world) `serializeData()` inside the click continuation

- **Evidence: MECHANISM_VERIFIED** (code path + ordering read; CPU-side magnitude estimated from a node micro-bench — hardware-unverified on this SwiftShader box).
- **Where:** `loadAsync` captures the outgoing run at `src/save/saveSystem.js:4437` via `_captureRollbackSnapshotAsync` (:5122-5163). The capture branches on `_frozenTickBoundary()` (:965-968 → `shouldFreezeFlightSubmit`, `src/core/presentationFreeze.js:15-25`), which recognizes `mode==='paused'`, docked, non-empty screenStack, or `sectorShellAdmission` — **not** free flight and not the loading freeze (`enterLoadingMode` sets `mode='loading'` + `runtime:loading` scale-0 at `src/main.js:1181-1206`, and neither registers in `_frozenTickBoundary`). A load initiated while `mode==='flight'` with no covering screen — F9 quick-load (`src/ui/input.js:346`, `:537`), or any `game:load` emitted during live flight — therefore takes `data = this.serializeData()` (:5133): the full world/mission/faction/entity serialize as one uninterruptible task.
- **Ordering detail:** the capture deliberately runs before `_restorePreparedEnvelopeAsync` → `_openRestoreSession` (:5310) → the `mode='loading'` flip inside `_restoreChunks` (:5518-5526). So it lands on the click+1 task — the veil's DOM is up (`restoring-save` progress emit at `src/main.js:223-233`), but its first painted beats stall for the whole serialize.
- **Cost model:** `serializeData` is a fresh-object materialize over the world graph — strictly heavier than `JSON.stringify` of the same bytes. Bench (node 24, synthetic 0.56 MB envelope): stringify-equivalent ≈ 3.8 ms/MB, deep walk ≈ 0.9 ms/MB per pass → order **30-100 ms** on a mature multi-MB sector, uninterruptible. Continue-from-title is unaffected (`_hasPlayerEntity()` is false at the menu → `{notNeeded:true}` :4438-4440); paused/docked/stacked loads already take the sliced `_serializeDataFrozenAsync` lane.
- **Fix sketch:** for the non-frozen lane, defer the snapshot into `_restoreChunks` immediately after the `mode='loading'` flip + scale-0 (still before the first destructive chunk, `_clearEntitiesChunked` :5400 — rollback fidelity preserved), and extend the freeze predicate — e.g. `mode==='loading' && Number(state.timeScale)===0` or an explicit restore-session flag — so `_serializeDataFrozenAsync`'s generator slices the identical bytes across frames. The existing per-section re-check + atomic retake already guards coherence; the open question is whether scale-0 provably suppresses every serializing-visible mutation between yields (input/save/stationServices keepalives still run — they don't write captured state today, but that invariant needs a comment + a determinism test).
- **Effort M · Impact M · Risk M** (ordering-sensitive; golden-hash gates byte identity).

### BOOT-F2 — `'latest'` resolution still rides the atomic authoritative slot scan

- **Evidence: MECHANISM_VERIFIED** (scan structure + call sites read; magnitude from the same micro-bench — hardware-unverified).
- **Where:** `loadAsync('latest')` (:4395-4404) and the sync `load('latest')` twin (:4306-4315) resolve through `_newerUnplayableSkipAsync` (:2659-2683, worker-backed envelope preps but still calls `this._latestSlot(burst)` **synchronously** at :2667) and `_latestSlot` (:2622-2625) → `_slotIndexWithFallback` (:2154-2194). On a `_slotIndexCache` signature miss, that is: `_slotStoreSignature`'s enumerate+`getItem` walk (:2121-2149; reuses `_sharedStoreCollectCache` when fresh), then `_scanStoredSlots` (:2429+) / `_scanRecoverySlots` (:2475+) — `getItem` + `fnv1a(raw)` per stored blob — plus `_prepareEnvelopeMeta` (:2406-2422) per slot whose `_blobHash`/`_recoveryBlobHash` is absent or mismatched: `JSON.parse` → `preflightSaveImport` full-graph bound → `fnv1a(safeStringify(env.data))` → `runMigrations` → `normalizeRestorableData`. All of it inside one synchronous task on the click continuation.
- **Trigger surface:** every `game:load` emitter in `src/` names a slot, and the falsy default is `'quick'` (:4303, :4394) — so the in-app surface is `save.load('latest')` / `loadAsync('latest')` API calls (the documented Continue semantic; the INF-091 tests exercise it) plus `listSlots()`/`deleteSlot`/`_enforceQuota` (:2514, :2688, :1327 — save-side paths). Narrow — but on a sig miss it is the largest un-sliced leg left in the lane: the sliced twin `_scheduleSlotIndexValidation` (:2233+) already does the identical work with a yield every 16 keys, `_prepareEnvelopeMetaAsync` worker dispatches, and a verdict merge into `_slotIndexCache`, which `_slotIndexWithFallback` happily serves on a same-sig hit (:2158).
- **Cost model:** bench terms per MB — fnv1a ≈ 4.9 ms, JSON.parse ≈ 5.1 ms, stringify ≈ 3.8 ms, walk ≈ 0.9 ms. Hash-verify ≈ ~5 ms/MB/slot; untrusted meta-prep ≈ ~14 ms/MB/slot (≈ 40-70 ms on a 3-5 MB blob). A mature-store sig-miss scan (8+ slots, several MB each) lands ~150-350 ms in one task.
- **Fix sketch:** `_latestSlotAsync`/`_slotIndexWithFallbackAsync` that (a) serves the same-sig `_slotIndexCache` merge as today, (b) on a miss rides or awaits `_scheduleSlotIndexValidation`'s in-flight promise (or runs the same 16-key-yield walk itself), and (c) sends untrusted metas to `_prepareEnvelopeMetaAsync`. Same verdict semantics — this is a read-only lane change.
- **Effort M · Impact M (narrow trigger, largest residual brick) · Risk L.**
