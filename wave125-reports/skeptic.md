## Ranked findings

### F1 — M — `rotateSectorDeferred` pending marker leaks when the mint iterator is abandoned unstarted or mid-yield — complexity debt → correctness defect

`rotateSectorDeferred` mints its pending marker synchronously at call time — `assetResidency.js:1807-1808` (`pendingSectorTarget = exactNext; hasPendingRotate = true;`) — but clears it only inside the returned generator's `finally` at `assetResidency.js:1846-1849`. The caller hands that iterator to `queueWarmMint` (`assetLoader.js:1004-1006` → `renderer.js:19799-19805`), which either direct-assigns it as `self._sectorExitCleanupIter` or chains it FIFO behind the existing cleanup drive as `(function*(){ yield* existing; yield* mintIter; })()`.

Two abandonment paths leave the marker armed forever:

1. **Unstarted mint, direct-assigned.** When no cleanup is draining (the common steady-state case), `queueWarmMint` sets `_sectorExitCleanupIter = mintIter` directly. Before the residency drive's first `.next()` on it, a subsequent sector-exit arms `driveCacheCleanup`, whose first action is `self._sectorExitCleanupIter?.return?.()` (`renderer.js:19363`). Per spec, `.return()` on a never-started generator completes it *without executing the body* — the `try`/`finally` at `assetResidency.js:1816-1850` never runs, so `hasPendingRotate` stays `true` with `pendingSectorTarget` pointing at a rotation that was never applied (`currentSectorId` never repointed at `1839-1842`).
2. **Chained mint, abandoned mid-`yield*`.** When a cleanup *is* draining, the mint rides FIFO behind it. `.return()` on the chain while suspended inside `yield* existing` completes `existing`, then *resumes* the outer body into `yield* mintIter`: the mint's head runs — including `releaseOwner(warmOwner, 'warm-sector-expired')` at `assetResidency.js:1818` — up to its first `yield` (`1819`), at which point the delegation suspends the outer generator again and the caller's `return()` simply ends. `mintIter` is now parked inside its `try` with its `finally` armed but never invoked — same leaked marker, plus the old sector's warm hold released while its replacement coverage was never minted. The fault path (`renderer.js:3223-3224`) has identical mechanics.

End state after either path: `hasPendingRotate === true`, `pendingSectorTarget === B`, `currentSectorId === A` — a dead requested target shadowing the live pointer via `effectiveCurrentSectorId()` (`assetResidency.js:1654/1796`). Consequences until a successful rotate to some `C ≠ B` overwrites it:

- A request to rotate *into* B returns `false` at `assetResidency.js:1797` (`exactNext === effectiveCurrent`) — the swap reports `rotated = false` while the live pointer still sits at A. The natural retry of the dropped rotation is the one request that can never heal it.
- Departing-sector warm coverage and the `warmSectorId === effectiveCurrent` cheap paths (`1659/1799`) key off a sector that was never applied — warm mints for the wrong departure; the real departed sector loses its warm retain (case 2 released it mid-head) — i.e., the pop-in this machinery exists to prevent silently returns for that sector until the next rotate.
- `prepareSectorExit`'s default consults the *raw* `currentSectorId` (`1699`) while rotates consult `effectiveCurrentSectorId` — the two twins disagree on which sector is current for the duration.

Minimal reproduction reasoning: sector A→B entry queues the mint (call-time marker armed); a second exit-seam `driveCacheCleanup` (or the fault path) fires before the next paced drive step — a rapid cross-out/cross-in or a failed second prepare inside one 4 ms slice — then a re-entry request to B is dropped as already-current while the residency pointer remains A. Window is narrow but real; failure is silent and self-persisting (no log, no drift event — the ledger verifier doesn't cover the rotate marker).

Fix direction for the next wave (not implemented here — audit-only): on abandonment, drain the chain to completion (`while (!it.next().done)`) the way the non-Steps-registry fallback already does at `renderer.js:19367`, or add a call-time `hasPendingRotate` validity check that detects a dead queued mint and clears the marker before re-deriving.

### F2 — L — shared-store mirror patch is dropped on a failed push — attribution caveat, documented trade

`_queueSharedStoreMirror` (`saveSystem.js:573-615`) accumulates the delta then flushes once: `this._sharedStorePatch = null` before `pushSharedPlayerStore(keys, { keepalive: true })`. If the PUT resolves `false` (route absent/offline/non-2xx), the patch is discarded — no requeue. Deletes still land their tombstone in *local* storage before the PUT (`sharedPlayerStore.js:344-358`), so a dropped delete cannot resurrect on merge; what a failed push actually loses is **content freshness** — the remote keeps the previous generation of the primary/recovery/index keys until each key is rewritten, and a save written while offline exists in the shared store at its pre-write bytes indefinitely if that slot is never saved again. The "the mirror ships the delta this write just landed" claim holds only when the PUT lands; the health flag (`_sharedStoreMirrorHealthy`) records the failure but nothing replays the lost delta. Severity L: documented as best-effort in the comment; flagged because the wave log's phrasing implies guaranteed delta shipping.
