## Ranked findings

### F1 — Mesh-build drain's sync fallback is the one unbelted degrade in the cook

**Evidence:** `src/render/renderer.js:12452-12472` — `drainIter.next()` throw → `closeCookStepsIter` + warn + `drainIter = null` → the loop's else branch then runs bare `this._drainMeshBuildQueue(1)` (:12471-12472), permanently, for the rest of the shell drain. `_drainMeshBuildQueue` (:23670-23679) mints and atomically drives the same `_drainMeshBuildQueueSteps` generator — it *is* the sync twin in every sense — and it is not wrapped in `runCookSyncTwin`. Every other drive-guard site (~40 twin invocations + the honest degrade-only shapes) either belts the fallback or skips the section; this is the single site where a second throw escapes the section. The belt's own doc comment names this exact case: "the sync twin a degraded drive falls back to can throw on the same pathology" (:2049-2051).

**Mechanism.** The stepped drive can only throw from the drain's infrastructure — prologue scan-context mint (:23760), the O(entityList) newcomer census (:23773-23808), the gate/hoist machinery — because every per-row `vf.build` is already try/caught (:23914-23918). That same prologue re-mints inside the fresh `_drainMeshBuildQueue(1)` call, so a deterministic pathology re-throws and propagates out of `drainMeshBuildsBehindShell` → the cook's await chain rejects → cook tail dies → the arrival lands meshless (the tail-kill class the belt exists to exclude). Even when it doesn't throw, the degrade re-pays the prologue (scan mint + newcomer census) once per pass — the exact cost the Steps drive exists to amortize (:12436-12440).

**Fix sketch.** Wrap the fallback in the same belt: `built += Number(runCookSyncTwin('mesh-build drain', () => this._drainMeshBuildQueue(1), () => 0)) || 0;`

**Effort:** S (one-line wrap). **Impact:** M — requires a double fault (steps drive AND fresh sync drain), but the thrower is deterministic infrastructure so the two failures are correlated, not independent; when it lands it's the highest-severity outcome the belt exists to prevent. **Risk:** none — identical shape to the 40 sibling sites.

### F2 — Uncapped `countShadowReceivers` per parked warm root bypasses the -1 sentinel

**Evidence:** `src/render/renderer.js:21491-21516` — `_parkBoundedWarmRoots` calls `countShadowReceivers(root, measure)` with no `maxNodes` (:21500) inside presented frames. The paced ledger is debited *between* roots (:21515-21520) but each count is one atomic subtree walk. `isBoundedWarmRoot` (:9071-9074) is a provenance tag (`'bounded-cook'`/`'opening-species-warm'`/`'deferred-warm'`) — it bounds which cohort minted the root, not the root's node count; a packaged-hull warm root is ~1-3k nodes.

**Mechanism.** A roster-warm release storm (sector turnover retiring N warm roots) pays one atomic flag walk per parked root inside presented frames — the ledger gate defers the *next* root but can't slice the in-flight count. The exact machinery for this class already exists and is exercised: `countShadowReceivers(root, null, UNMEASURED_SHADOW_NOTE_NODE_MAX)` → `measured < 0` → `markDirty()` → paced recount (:28341-28343, :28362-28364). This call site just doesn't use it — it's the last uncapped whole-subtree count reachable inside a presented pass.

**Fix sketch.** Pass a cap and route the sentinel: `const receivers = countShadowReceivers(root, measure, WARM_PARK_COUNT_NODE_MAX); this._noteShadowMeshRemoved?.(root, receivers < 0 ? null : receivers);` — under-cap roots keep the exact settle; over-cap roots settle via the paced recount (legal direction).

**Effort:** S. **Impact:** M — cheap per node (flag tests, no matrix math) but atomic; ~3k-node roots under a release burst put ~0.3-0.5ms × roots-per-wallet into presented frames before the ledger intervenes. **Risk:** low — `null` → `markDirty` → paced recount is the already-exercised storm shape.
