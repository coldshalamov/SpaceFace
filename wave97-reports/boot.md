### 1. `syncVisiblePointLightBudget` pays ~2×O(scene) atomic traverses per call, inside four boot/cook legs — no Steps twin

- **Evidence:** `src/render/precompile.js:184-199` — every call runs `releaseVisiblePointLightBudget` (`scene.getObjectByName(POINT_LIGHT_BUDGET_STAGING_NAME)`, a full O(N) DFS when the staging group is absent — the common case) then unconditionally `countVisiblePointLights(scene)` (`scene.traverseVisible`, O(visible subtree) ≈ O(N) during boot, :166-170), then N stand-in adds. Call sites: `renderer.js:10073` (boot queue leg, right after `paceBootQueue`), `:11744` (`compileOpeningSubmissionPlan`, immediately before `captureLiveSectorCookStale` mint at :11746), `:13884` (inside the cook, between the envBind Steps loop at :13867-78 and the reveal arm at :13886), `:15458` (post-opening rescan pass head).
- **Mechanism:** each call lands two whole-scene walks (~tens of thousands of nodes in a dense sector — the pool census alone is documented as ~21k at :14629) atomically inside legs whose sibling work all paces under `paceCookStretch`/boot-queue yields. During `mode === 'loading'` these runs sit between rAF boundaries of the veil — one call is a multi-hundred-ms-to-second-class block on this box (SwiftShader makes the node cost real, not shader-side). Four mints per boot path ⇒ the single largest remaining atomic boot stretch by node count.
- **Fix sketch:** mint a `syncVisiblePointLightBudgetSteps` generator (iterative DFS for both the name search and the visible-light count — they can share ONE walk: count point lights while searching for the staging group), drive it under the caller's existing pace fn (`paceCookStretch` / `paceBootQueue` / the rescan's `postPace`), keep the stand-in add loop + both `noteShadowCensusLightMutation()` notes verbatim at the tail. Sync fallback preserved for Steps-less hosts like every sibling twin.
- **Effort:** S-M (mechanical Steps twin; the two walks fuse cleanly).
- **Magic-frame impact:** M-H — largest remaining O(scene) atomic blocks on boot/cook paths; 4 mints per run.
- **Risk:** low. The count only sizes the stand-in cohort; identical verdicts preserved by construction. Must keep both mutation notes so the epoch machinery sees the light-set drift.

- **Mechanism:** W96's epoch memo replaced the per-`_viewSyncSeq` latch — verified strictly better (one traverse per mutation batch vs one per frame). But each re-mint is still an unstepped O(N) traverse inside whatever paced leg or sync path happened to read first — the traverse is invisible to `pacedFrameSpend` bookkeeping until after it runs, so the leg overruns its slice behind the veil.
- **Fix sketch:** two options, in order of value — (i) incremental census: maintain a live `Map<object, key>` of rendered lights updated by the existing mutation-note sites (plus a dirty flag for visibility-chain uncertainty); the sig then computes in O(#lights) sort+join instead of O(N) traverse. - **Risk:** medium for (i) — a sig that under-reports mints stale keys → cold depth links in presented frames (exactly the NOVEL class this machinery exists to prevent). Low for (ii).

### 3. The census-epoch note set is incomplete — un-noted light mutations can freeze the memo on a stale signature

- **Evidence:** all `noteShadowCensusLightMutation` call sites are light mount/dispose/`castShadow` flips (weaponLights.js:41/:113; flightOverheadPresentation.js:32/:66; precompile.js:180/:198/:876/:880/:911/:918; renderer.js:9226/:26228/:26262/:26317/:27482/:27505). Uncovered vectors: (i) `vfx.js:14939-14952` `_initEventLights` adds `EVENT_LIGHT_POOL_SIZE` PointLights directly to the live scene (`this._scene.add(l)`) with NO note — benign today only because `_initPools` (:2169) runs before the first census mint; (ii) the sig counts a light only when its whole ancestor chain is `visible` (:412-414) — an ancestor `visible` flip notes nothing; (iii) detaching a light-bearing subtree (park/unpark machinery) changes traverse membership with no note.
- **Mechanism:** `memo.epoch === epoch` is the whole validity check — an un-noted mutation leaves the memo serving a signature that no longer describes the rendered light set for the rest of the session (no recovery — the epoch only moves on noted mutations). Casters then mark/query under a stale `lightSig` term and their real depth programs link cold inside presented frames — the same failure class W96's machinery exists to catch. Today it's latent (init ordering makes (i) land pre-mint; nothing ships lights under flipped/detached subtrees), but nothing enforces it staying latent.
- **Fix sketch:** note at the choke point, not every site — a tiny `addSceneLight(root)`/remove helper used by vfx (and any future light-bearing attach), plus either (a) a dev-only assertion that re-derives `lightCensusSignature` at a paced boundary and compares against the memo (fires on coverage gaps before they ship), or (b) extend the note to `Object3D.add/remove` of subtrees containing `isLight` via a scene-level mutation hook.
- **Effort:** S (vfx note + audit assertion) / M (choke-point hook).
- **Magic-frame impact:** M latent — fires only if init order or light usage drifts; catastrophic-per-incident class when it does.
- **Risk:** low — extra notes only cost bounded re-mints; under-noting is the dangerous direction and stays unchanged for vectors not yet covered.
