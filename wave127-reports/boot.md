## Findings (ranked by evidence × materiality)

### F1 — `pushSharedPlayerStore` UTF-8-encodes every PUT body even when keepalive was never requested

**Evidence (MECHANISM_VERIFIED)**

- `src/save/sharedPlayerStore.js:417-422` — `const body = JSON.stringify({ keys: patch })` is immediately followed by `let byteLength = 0; try { byteLength = new TextEncoder().encode(body).byteLength; } catch { byteLength = body.length; }` — the encode runs **unconditionally**. The comment directly above says the encoder "only runs when the guarantee was actually requested" — the code does not honor that.
- `byteLength` is only consumed by `carriesKeepalive = keepalive === true && byteLength <= KEEPALIVE_BODY_BUDGET_BYTES` (:422). When the caller passes `keepalive: false` (default), the encode result is dead work.
- Dead-work call site: `src/save/saveSystem.js:559` — the boot reconcile's `await pushSharedPlayerStore(delta)` passes no keepalive flag, so on a divergent-remote boot (delta = most of the store, multi-MB) the full body is UTF-8-encoded and allocated and the result is thrown away, all inside `_syncSharedPlayerStore`'s task.
- Keepalive callers still overpay: mirror flushes at `saveSystem.js:617` pass `{ keepalive: true }` with real save bodies (~220 KB each, multi-MB with index) — always larger than `KEEPALIVE_BODY_BUDGET_BYTES` (60 000, :11). The encode runs to prove what a cheaper bound could: a conservative estimate `body.length * 4 >= budget` (UTF-8 is ≤4 bytes/char) would reject every real envelope without touching the buffer. So the encode is only ever *needed* for bodies that could plausibly fit — which is never, for save envelopes. Tombstone-only patches do fit, but their `.length` is already under budget by inspection (ASCII-only payload — `JSON.stringify({slot,deletedAt})` at :404), so a `body.length <= budget` fast path (length === bytes when pure-ASCII) could also cover them.
- Cost: one full O(body) allocation + encode pass per push — ~0.2–0.5 ms per 220 KB, several ms on a full-store boot delta. Small, sync, and thrown away.

**Mechanism**: every mirror flush and the boot delta push pay a wasted multi-hundred-KB–multi-MB encode inside whatever task made the call — a frozen-ish microstretch at boot and a recurring small tax per save flush.

**Fix sketch**: `if (keepalive === true) { byteLength = encode; }` — preserves the exact verdict for keepalive callers, zero cost otherwise. Optionally, on the keepalive side, short-circuit `body.length > KEEPALIVE_BODY_BUDGET_BYTES` before encoding (max-4x char bound is already exceeded then, no encode needed) — saves the same pass on every real save flush.

**Effort**: S | **Magic-frame impact**: L-M (multi-MB only when the boot delta is large; per-save flushes are ~220 KB) | **Risk**: L

### F2 — the boot delta push's `JSON.stringify({ keys: patch })` is the one un-sliced O(store-bytes) leg left in `_syncSharedPlayerStore`

**Evidence (MECHANISM_VERIFIED)**

- `src/save/sharedPlayerStore.js:417` — `JSON.stringify({ keys: patch })` runs synchronously inside `pushSharedPlayerStore` before the first await, so it executes inside the caller's task.
- `src/save/saveSystem.js:539-559` — the boot reconcile now yields everywhere except here: chunked collect (:532), chunked apply via `applySharedStoreKeysChunked` (:542), delta compute (:556-558 — O(#keys) identity compares, cheap), then `await pushSharedPlayerStore(delta)` at :559 — whose stringify runs inside this same task segment. On a mature profile with a divergent or absent remote, `delta` is most of the store → a multi-MB sync stringify (~5-30 ms) during the boot window while `isSharedStoreSyncPending()` gates Continue.
- A `JSON.stringify` cannot itself be sliced, so the honest fix is moving the leg onto its own bounded task — consistent with the wave's own framing (the pre-worker save lanes keep "the same two passes on their own bounded tasks", :1600-1619). The per-save flush path at :617 has the same shape but with ~220-500 KB bodies (~1-3 ms) — sub-frame; only the boot/divergent-delta call is material.
- Contiguous but distinct from F1: with F1 fixed, the push still pays this stringify; the two fixes compose into "push's main-thread cost on the boot path ≈ zero".

**Mechanism**: one bounded but potentially multi-tens-of-ms stringify inside the boot reconcile task on mirror-equipped shells — a dropped frame or two while "Checking saves…" is up, worst case on the heaviest profiles.

**Fix sketch**: in `_syncSharedPlayerStore`, `await this._restoreFrameYield()` immediately before `pushSharedPlayerStore(delta)` (the stringify then runs on its own scheduled task, after the chunked apply's last yield — no semantic change; delta is already computed). That isolates the leg rather than slicing it — a chunked encode would require worker-side stringify, which the store client doesn't have.

**Effort**: S | **Magic-frame impact**: L (once per boot, mirror-equipped shells with divergence only) | **Risk**: L
