### F1 — Door-staged crucible warm is adopted by a mid-run restore without re-scoping its wave eligibility → the resumed wave fields every post-wave-1 archetype cold

**Evidence:** `_beginMenuCrucibleRosterWarm` (`src/render/renderer.js:16816-16840`) mints a warm while `!state.run` → inside `_beginCrucibleBoundedRosterWarm` `waveBase = Math.max(1, swarmScoped && state.run.wave... ? state.run.wave : 1)` collapses to **1** (`:16311-16313`), so `launchEligibility = swarmEligibleEnemyIds(1)` = `wasp_swarmer` only (`swarmMode.js:295-447`, `atWave:1`/`fromWave:1`), and `warm.coveredEnemyIds`/`covered+1` marks stamp that single archetype (`:16317-16326`). Adoption never checks the scope: `_beginEarlyCrucibleRosterWarm` keeps the staged warm whenever `survivalRunHoldsArena(state) && run.ruleset === SWARM_RULESET` (`:16755-16775` — ruleset compared, wave never compared), and the cook consumes `this._earlyCrucibleWarm` unconditionally before deciding whether to `begin` (`:12820-12826` — `if (!crucibleWarm ...)` guards on presence, not scope). The non-swarm and wrong-ruleset branches already discard+remint for exactly this class of scope mismatch (`:16761-16772`, comment "the scoped cohort would leave its hulls cold — restart unscoped"), but the wave axis has no equivalent.

**Mechanism:** preview the Crucible door/draft in the menu (warm mints + kicks wave-1 exemplars), then load a wave-N survival save. The wave-1-scoped warm rides through loading into the cook; the cook skips its own fresh begin; `run:ended` never fires on restore so the marks stand. Archetypes unlocked at waves 2..N (`pincer_grappler`, `reaver_pirate`, `mantle_crusher`, `stacker_foreman`, `mantle_farstriker`, `overload_sapper`, `warden_escort`, `bruiser_brawler`, `field_anchor_controller` and the boss-package ids) got **no** exemplar and **no** kick — the resumed wave's first live spawn of each pays the in-round compose + program link, one at a time, inside the fight. The wave-(N+1) deferred warm eventually covers them (fresh filter sees `covered=0`), i.e. exactly one fight late. The reverse direction (post-run menu where `state.run` lingers at wave N → wave-N-scoped warm adopted by a wave-1 New Game) over-warms — wasted loading budget, correct coverage. The under-scope direction is the contract violation.

**Fix sketch:** persist the minted scope on the warm (`warm.waveBase` — one line next to `warm.swarmScoped` at `:16311`), and at the adopt site (`:16755-16775`) require `staged.waveBase === state.run.wave` for swarm rulesets; mismatch → run the same discard+remint the ruleset branch already takes. Cheap alternative: top-up the missing eligibility slice by iterating `swarmEligibleEnemyIds(run.wave) \ coveredEnemyIds` through the same kick builders.

**Effort:** S–M (the scope field is one line; the adopt check reuses the existing discard path; the top-up variant is M). **Magic-frame impact:** H — every unlocked archetype of a restored deep wave pops in at first spawn; this is the single largest remaining producer of the exact failure the warm machinery exists to kill. **Risk:** low — discard/remint is an exercised path; a wrong-scope discard only re-pays a warm.

### F2 — Coverage marks outlive never-kicked exemplars: `!ship` continue and missing `requestAuthoredUpgrade` keep `covered` with zero kicks dispatched

**Evidence:** marks mint unconditionally for **all** of `launchEligibility` at `renderer.js:16321-16322`; the build loop then skips with the mark still standing in two ways — `const ship = this.vf.build(spec); if (!ship) continue;` (`:16461-16462`, no `unmarkWarmCoverage` — contrast the catch right below at `:16502-16509`, which does unmark; the deferred lane fixed this same hole at `:17736-17738` `unmarkEnemy(...)` on `!ship`) and the `typeof ship.userData?.requestAuthoredUpgrade === 'function'` guard (`:16470`, hulk twin `:16525`, deferred twins `:17742`/`:17777`) — a boundary that builds but carries no upgrade hook dispatches no kick and keeps its mark. `vf.build` returning null is reachable on the silent-failure tail (`visualFactory.js:5749-5756` — `buildFallback` catch → `return null`; `:5714` null entity). Missing-hook is reachable for any spec whose resolved visual isn't authored-backed (hook is only stamped by the authored-boundary builders, `partsLibrary.js:2908/2997/3667/3836`).

**Mechanism:** the ledger's release discipline is settle-driven — a mark only ever decrements when a kick's settle fires `unmarkOnRetriableOutcome`/the deferred equivalents. A mark with **no kick dispatched** has no settle: `covered(id) = 1` permanently. Every later deferred-warm `fresh` filter (`:17531-17533`, `covered <= reKickClaims`) skips the archetype for the whole run → guaranteed in-round compose pop-in at its first spawn — a *permanent* coverage lie, strictly worse than a skipped row. W77-F2 fixed the pre-resolution variant (unresolvable ids minting marks); this is the post-resolution twin the W77 fix didn't reach.

**Fix sketch:** `if (!ship) { unmarkWarmCoverage(spec?.data?.lootTableId); continue; }` at `:16462`, same for the hulk at `:16520` (`hulkVisual.lootTableId`), and unmark on the missing-hook branch in all four kick sites (or push the marks to dispatch time — mint `covered` only for ids that actually dispatched a kick, keeping the same-dwell double-queue protection the upfront marks provide).

**Effort:** S. **Magic-frame impact:** M (rare trigger — needs a silent build failure or hook-less boundary — but unbounded consequence: the archetype never re-warms for the run). **Risk:** low — releasing a mark for genuinely-undispatched work can only cause a redundant retry, never a lost kick.
