# 08 — Studio recovery program
## Converge through playable outcomes, not another competing queue

The studio should preserve the current program machinery and change what it dispatches and how it closes work. The repository already has a central build map, ordered units, exact-path collaboration, and separate implementation/acceptance states. A new independent backlog would create another authority fork. The work orders below are **audit recommendations to attach to the existing packets**, not newly claimed queue units. [PROGRAM] [BUILD]

No repository changes were made by this audit. The ZIP is a decision and implementation aid. Its references are pinned to the reviewed commit; another agent must re-read a relevant owner at its working base before changing it.

## 8.1 Executive sequencing

| Stage | Outcome | Existing program surfaces to reconcile | Exit evidence |
|---|---|---|---|
| A — Correct the compass | Agents receive current controls, current defects, and unambiguous acceptance | Build map, GDD, orientation, fun loop, performance operator/campaign | Contradictions resolved in place; old fixes marked for verification, not reimplementation |
| B — The physical toy is trustworthy | One ship responds clearly; a sling, a throw, a brake, and a physical fight are readable | PQ-137, PQ-139, PQ-140, PQ-146, PQ-173/174, minimal PQ-158/159/164/165 | Production-profile traces and normal-speed captures; one shared control/physics path |
| C — The toy pays off in Adventure | A physical undertaking creates a local consequence and a useful fitting choice | PQ-138, PQ-148, PQ-163, a narrow PQ-176/177 slice | Ordinary-route delivery, transaction, world response, fitting, and save/load proof |
| D — Industry becomes authorship | One mine becomes one durable operation with an exterior consequence | PQ-130/131/185, PQ-145 and current site/logistics owners | The same site returns after reload; output arrives exactly once; blocked work is understandable |
| E — Expand proven variation | More encounters, build identities, regional pockets, story consequences | PQ-175/176/178, PQ-143/152/153/171 | New content creates a distinct decision with shared rules, without invalidating previous routes |
| F — Ship the actual product | Stable distribution, onboarding, input, access, saves, performance and coherent presentation | PQ-033 and relevant release packets | End-to-end release-candidate acceptance, not a sum of isolated receipts |

Performance runs across every stage. The current map's PQ-129 campaign and PQ-144 guard should not be treated as a distant final phase. Minimum audio, input truth, and accessibility needed to judge response also move into Stage B. Broad soundtrack production, photo-mode depth, and localization expansion can still follow later. [BUILD]

Do not use a single gate to hold every unrelated task hostage. While one integrator validates the physical slice, other agents can do bounded data validation, UI copy correction, source-contract reconciliation, and compatible asset work. They should not simultaneously tune the same physics owner under different hypotheses.

## 8.2 The first twelve work orders

Each order below names a bounded outcome, the likely ownership surface, evidence, and a characteristic wrong turn. They intentionally contain enough direction to execute without inventing a new product spec.

### Order 1 — Reconcile the control contract

**Route:** existing input-truth work, including PQ-164 and the opening packet. Read `src/systems/input.js`, the relevant propulsion input path, README, GDD controls/onboarding, and drill control mapping. Preserve the current shipping scheme during this task. Generate or centrally resolve displayed binding labels, correct contradictory prose, and verify remapped hints in flight and rover.

**Done:** each taught action produces its stated action on the normal route; the same remap appears consistently. Test release, focus loss, and a mode transition. **Wrong turn:** silently replacing keyboard steering with mouse steering to make one old paragraph true. [INPUT] [FLIGHT] [DRILLUI] [GDD]

### Order 2 — Repair acceptance polarity and stale work routing

**Route:** program/integrator-owned documentation. Correct the central any-yes blocker list and the mixed-polarity fun score. Reconcile the scheduler's contradictory current status. Mark old zero-damage, governor, rover-cadence, and fixed-K diagnoses as historical where the code already changed.

**Done:** a positive reachability result cannot fail the blocker list; a bad visual stand-in cannot improve the score; the next performance task reflects current evidence. **Wrong turn:** replacing every file with a new comprehensive plan instead of fixing authoritative doors. [BUILD] [FUN] [PERFORDER] [PERFCAMPAIGN]

### Order 3 — Establish a current production baseline

**Route:** PQ-129/144 and the existing laboratory/capture tools. Capture the named baseline machine and normal production profile on opening, dense combat, and a transition. Record foreground frame intervals, CPU phases, valid GPU samples when available, input age, shed ticks, and a matching run manifest.

**Done:** one dominant observed cost or a clearly bounded uncertainty is identified; every displayed number traces to a current run. **Wrong turn:** quoting the historical shadow improvement as a new benchmark, using legacy47a to prove modern behavior, or building another generic harness before using the existing one. [SIM] [PRESENT] [PROFILES] [PERFCAMPAIGN]

### Order 4 — Characterize the present flight and contact response

**Route:** PQ-137. Use the current Hitch and contrasting hulls in the existing physical bench, then in Adventure. Test forward-held earned overspeed, explicit braking, conditional strafe/yaw, side impacts, glancing station contact, and repeated contact. Log command, suppression reason, expected kinematics, actual contact delta, and displayed result.

**Done:** each unwanted response is assigned to an owner and a reproducible cause; a bounded change improves that cause without erasing the preserved maneuvers. **Wrong turn:** globally raising acceleration or deleting all stabilization because “momentum.” [FLIGHT] [PHYSICS] [FEEL]

### Order 5 — Validate the existing rope envelope

**Route:** PQ-137 and the existing head packets. Exercise load-scaled stiffness rather than reimplementing it. Sweep mass ratio, line length, radial/transverse velocity, and active reel. Test attachment creation, release, exceptional break, save/load, and mode transfer.

**Done:** a specified admitted envelope holds the intended rope behavior with bounded numerical error; failures have explicit causes. **Wrong turn:** applying a second spring outside the physics owner, auto-breaking ordinary use, or clamping earned tangential velocity to make a screenshot taut. Use the included analytical diagnostic only to select cases. [PHYSICS] [ATTACH] [WINCH]

### Order 6 — Prove one complete physical combat exchange

**Route:** PQ-139/140/146 and minimum audio/camera work. Choose an existing enemy and a meaningful nearby obstacle. Make its commitment, the player's physical response, and the consequence readable together. Reuse collision feel and time-effect ownership. Include a failed attempt as well as the successful stunt.

**Done:** normal-speed evidence shows anticipation, input, contact, result, and recovery; the same rule works outside the bench. **Wrong turn:** replacing the absent gameplay consequence with a larger explosion or making a kill possible only under a debug flag. [IMPULSE] [FEELFX] [ENGAGE]

### Order 7 — Test Swarm's earned breathing room

**Route:** PQ-174/175 and current Swarm owners. Compare the existing deficit-adaptive refill against one bounded alternative that preserves a short, visible payoff after a substantial clear. Keep the same roster, broad difficulty intent, and shared physics. Measure the opportunity to collect, reposition, or set up another stunt—not just average hostile count.

**Done:** the preferred curve maintains challenge while making successful play perceptibly change the space. **Wrong turn:** lowering every population, or making a faster clear automatically trigger an invisible harder replacement. [SWARMCURVE] [SWARMARENA]

### Order 8 — Give automated cargo explicit custody

**Route:** automation, economy, cargo, and the relevant progression/economy packets under one integration owner. Trace the programmed-miner sell path, separate operation inventory from the player's manually gathered cargo, and route delivery through a transaction with a durable receipt. Characterize station pricing at the exact sale call.

**Done:** manual cargo cannot be accidentally sold or discounted by an unrelated worker; retry and save/load do not duplicate or lose goods or credits. **Wrong turn:** direct credit writes from automation or a newly invented global wallet service that bypasses current ownership. [AUTO] [ECON] [AGENTS]

### Order 9 — Replace one opaque industrial limit with a visible one

**Route:** PQ-145/177 and the current site/automation balance owners. Choose one representative operation. Show gross output, the limiting physical stage, realized sale, and operating cost. Compare the passive-cap policy to a bounded throughput/demand alternative using existing-save migration fixtures.

**Done:** the player can explain why adding a machine helps or does not help; returns remain bounded under tested loops. **Wrong turn:** deleting the global cap without replacing its economy-wide effect, or adding arbitrary raids to punish ownership. [AUTO] [SITES] [ROVERLAW]

### Order 10 — Complete the first durable site loop

**Route:** PQ-130/131/185 and industry integration. Use one small geological arrangement. Verify cut-preview truth, exact tap/hold behavior, first anchoring, machine relation, local buffer, one export, and return after save/load. Clarify claim survey versus visible material information.

**Done:** the site becomes a useful persistent operation with an outside-world consequence. **Wrong turn:** spending the entire task on the rover's chrome, making a flat tile replacement, or leaving output in an invisible counter that never reaches the economy. [DRILL] [DRILLUI] [SITES] [ROVERLAW]

### Order 11 — Approve the visual style slice

**Route:** current visual production packets and VFX/asset standards, admitted by the integrator. Use the starter, one enemy, one object, one machine, one background composition, and representative action effects. Re-author material/light priorities for matte structure and expressive luminous states. Revise technique prohibitions only where the new candidate demonstrates a better result.

**Done:** the normal-camera mixed scene is coherent, legible in motion, and within its measured budget. **Wrong turn:** treating “glowy” as permission for transparent spheres, or treating a physically plausible shader as proof of artistic quality. [ASSETLAW] [VFXLAW] [SECTORART] [BLOOM]

### Order 12 — Connect one Adventure incident end to end

**Route:** PQ-138/143/148/163 with the existing event owners. Re-read current producers and consumers before accepting the packet's older missing-listener claims. Connect one useful chain: an event changes a nearby actor's decision, changes cargo or service state, and leaves a relevant trace at the return destination. Use only consequences that serve the incident.

**Done:** the player can see the causal link without a debug overlay; save/reload preserves the meaningful result; distant unrelated traffic is unchanged. **Wrong turn:** forcing every incident to emit five traces, making all civilians flee everything, or turning every failed clause into another mandatory mission. [WORLDPLAN] [ENGAGE] [JOBS]

## 8.3 Organize agents around ownership and uncertainty

Keep one integrator responsible for shared schema, registry/profile changes, queue truth, and overlapping mutation surfaces. A system owner should execute one causal hypothesis at a time. Separate reviewer work from author work whenever practical, but do not confuse a second model's confident prose with independent player evidence.

Parallelize low-coupling work: catalog consistency, localization-ready copy, isolated UI presentation, pure math tests, material candidates within an agreed style, encounter configurations using existing verbs, and source-provenance cleanup. Serialize changes to propulsion, contact response, save schema, economic commit semantics, and shared scheduling until their interfaces are stable.

The scarce resource is not the number of generated tasks. It is integration attention and the ability to notice when a plausible patch changes the game. Keep work units small enough that their causal effect can be reviewed, but large enough to close an actual player-facing loop. “Write a test” can be useful work; a hundred tests for a misunderstood behavior are not convergence.

A task brief should contain the outcome, exact authority, current owner/read set, observed baseline, forbidden regression, bounded write set, evidence path, and rollback condition. It should also state the main uncertainty. A useful uncertainty is “the hull may be following the route clock rather than actual dock arrival.” “Make it AAA” is not an uncertainty the agent can test.

## 8.4 Verification without letting verification become the product

Use risk-tiered checks. Pure data and local UI changes should run focused validation and their normal-route witness. A change to physics, save state, canonical money/cargo ownership, or runtime profiles needs the relevant integration and replay suites. The integrator should run broader checks at the shared merge boundary, not encourage every tiny edit to launch an unrelated expensive campaign.

Do not weaken a behavioral assertion merely to get green. But do not preserve a historical design mistake because a golden records it. Classify assertions: mathematical invariants, ownership/schema constraints, intended product behavior, tuned values, visual expectations, and legacy compatibility. Each changes under a different evidentiary burden.

For a changed intended behavior, retain a causal record: old behavior, current owner direction, proposed change, affected scenarios, before/after evidence, and why the new golden represents the intended game. For an unchanged invariant, keep strict protection. For a visual expectation, use the current approved style rather than a stale exact coordinate or material parameter.

Determinism has levels. Exact same-build replay, save/reload equivalence, cross-runtime reproducibility, and cross-platform bit identity are not interchangeable. The production/legacy profile distinction makes this especially important. Record which level was actually proven. [PROFILES] [DETERMINISM]

## 8.5 Release acceptance: the complete route is the unit of truth

A release candidate must demonstrate a coherent normal route: start, learn accurate controls, perform a physical undertaking, survive a readable conflict, receive the correct economic consequence, make a meaningful fit choice, establish or ignore an optional industrial operation, save, reload, and continue without losing identity or value.

Swarm must sustain its intended intensity while rewarding useful play, keeping terrain available, avoiding unbounded retained state, and preserving input clarity under load. Adventure must demonstrate that physical actions and economic consequences share a world rather than existing as disconnected demos.

Art must hold together across quiet flight, dense effects, station screens, and Asteroid Works. Performance must be measured on named supported hardware with the intended content and visual target. Input remapping, reduced motion, text scaling, focus handling, and recovery from interruptions must not depend on the player knowing a debug workaround.

None of those criteria guarantees commercial success or “A-list” reception. They define the controllable craft necessary for a premium game. The studio should not expand release scope merely because a procedural generator or a large agent budget can produce more content.

## 8.6 What remains uncertain and who should resolve it

The rendering owner must establish the current CPU/GPU/driver split on the target machine. The physics owner must characterize the current extreme rope/contact envelope and replay behavior under time effects. The economy owner must trace final station quote, custody, and transaction boundaries. The world owner must verify the present event-consumer gaps rather than rely on older packet annotations. The design owner must accept the visual style slice and the pacing tradeoff in Swarm.

These are bounded verification jobs, not reasons to postpone the whole recovery. The inspected code already supplies enough structure to begin. The project moves forward when the next ordinary play session becomes clearer, more expressive, and more causally satisfying—not when another document announces that every system is sophisticated.
