# Wave 102 — lod-in-frame audit

Audited `devin/1791064509-perf-w60` @ `230b88e42` (W101 docs commit on PR #220). Read-only audit; no code changed, no app run.

`saturated: false` — W101 paced the freeze mint but left the unfreeze as a synchronous 2x O(subtree) walk on the two hottest churn seams (F1), a real undercount defect sits inside the verified notedWalk machinery (F2), and the freeze queue has no flap hysteresis (F3). Three bounded residuals remain (F4-F6) — all with concrete implementation paths.

## Findings (ranked)

### F1 — mass-unfreeze storm: `unfreezeHiddenSubtreeMatrices` pays ~2x O(subtree) inline per re-shown/unbound-frozen root — the atomic O(scene) moved from cull to un-cull

**Evidence:**
- `renderer.js:23234-23238` — inside `syncEntityViews`'s visible loop: `userData.sfHiddenFrozen === true` -> flag restore + `unfreezeHiddenSubtreeMatrices(mesh)` synchronous per root, per pass, uncapped.
- `renderer.js:21216-21221` — `_unbindPresentationMesh`: same inline unfreeze per unbound mesh with `ud.sfHiddenFrozen === true`. Mass-unbind sweeps (reconcile 21806, rebuild 22777, releaseRebuildBridge->2151, entity:destroyed 16574, F9 sweep 12746, sector-departure 15526) each pay it per frozen row.
- `src/render/staticChildMatrices.js:177-202` — unfreeze = one restore traverse (:180-189, restores `matrixAutoUpdate` + clears `sfMatrixFrozen` on stamped nodes) + ancestor-chain clear (:190-193, O(depth)) + `markStaticMatrixSubtrees(root)` (:199, a SECOND full-subtree recursive walk) + `root.matrixWorldNeedsUpdate = true` (:200). W100 minted the freeze as two walks; W101's re-mark made the unfreeze two walks too — still synchronous.

**Mechanism:** the freeze mint rides `_pendingHiddenFreeze` at <=6 roots/pass, but a mass re-show pays its restore cost atomically: sector re-entry un-hiding N minted-frozen hulls in one pass, a camera snap/zoom-in over a culled fleet, or a mass unbind (sector teardown, reconcile evictions) each cost 2x Sigma(subtree) inside one presented pass — the same atomic O(scene) class the queue exists to amortize, just relocated from the cull edge to the un-cull edge. Storm scale: ~50-200 nodes/hull x tens of hulls = ~10k node-visits inside one pass, plus the unbind sweeps' per-row tail inside paced legs (each unfreeze inside a paced leg can exceed the leg's own time bound — legs yield BETWEEN rows, not inside one).

**Fix sketch:** queue the subtree restore symmetrically. The root-level writes already happen inline and cheaply (`ud.sfHiddenFrozen = false; mesh.matrixAutoUpdate = true` at :23235-36) — keep those, and move only `unfreezeHiddenSubtreeMatrices(mesh)` onto a bounded drain (reuse the `_pendingHiddenFreeze` pattern, <=6/pass inside `syncEntityViews`, same stale drops: detached/unbind/re-frozen cancel, re-hidden merges with the freeze queue). Deferred unfreeze is correctness-safe: the vendored `updateMatrixWorld` override descends marked subtrees under force (`vendor/three.module.js:139-142`), and the un-hidden root's pose write + `matrixWorldNeedsUpdate` forces the recompose — the re-shown subtree just keeps paying the unfrozen compose it paid pre-W100 for the deferral window. Optional follow-on inside the queued unfreeze: stamp one bool at mint recording whether the freeze skipped any `matrixAutoUpdate === false` interior (staticChildMatrices.js:160); when none was skipped, the :199 re-mark can only re-find what the restore already cleared — skip it and halve the restore cost. Effort **M**. Magic-frame impact **M-H** (kills the largest remaining presented-frame storm class). Risk **low-medium** — deferral is provably correct under the force path; `_unbindPresentationMesh`'s unfreeze needs care (a corpse/pooled leaf about to be disposed or reused must not inherit stale marks — keep its inline unfreeze or make the queue drop unbound meshes safely).

### F2 — `noteRemoved` undercounts: a pre-existing root removed mid-recount gets excluded by `detached` AND has its `-delta` folded — double-subtract

**Evidence:**
- `src/render/shadowReceiverTally.js:139-162` — `noteRemoved` with `pendingRecount`: `detached.add(root)` always; for a root with no prior add-note the else-branch writes `notes.set(root, { delta: -delta, seq })` (:157); `count -= delta` always (:160).
- `:56-64` — the pop-time detached check skips the removed root: the fresh walk never counts its receivers — `stamped` is already post-removal correct.
- `:71-73` — `visits` is stamped ONLY for nodes that had a note at pop time (`if (notedWalk.notes.has(object))`) — a pre-existing root carries no note, so `visits.get(root)` stays `undefined` forever.
- `:222-226` — stamp fold: `visitSeq === undefined || visitSeq <= note.seq` — `undefined` -> the `-delta` folds on top of the exclusion.

**Mechanism:** walk minted (dirty recount) -> root R (no add-note) is removed mid-walk before the paced walk reaches it -> `detached` excludes R from `stamped` AND the `-delta` note folds -> `count = stamped - deltaR`: an undercount by R's whole receiver delta. The non-conservative direction — `_shadowReceiverCount` gates `shadowMapActive`/`_activeShadowCamera`/asteroid submission (renderer.js:27037-27050, 24037-24050) as `> 0` — a storm of mid-walk removals can drive the count to 0 while receivers remain, disabling the directional depth pass (visible: all shadows vanish) until some later dirty re-mints a clean walk. Ordering is common, not exotic: the paced recount runs across presented beats precisely during churn windows (kill bursts, sector departure, despawn drain) that generate `noteRemoved` on meshes anywhere in the scene. The `-delta` note's correct use is narrower: it must retract only a root the walk ALREADY counted pre-removal (the ghost case: visited-then-removed — folded correctly today by coincidence since `visits.get` is also `undefined` there).

**Fix sketch:** fold the `-delta` only when the walk actually measured the root. Minimal-change option: at the pop-time detached skip (:58-64), when a skipped object holds a `-delta` note, delete it — the skip already retracts the subtree. (The add->remove pair still nets via the unvisited-note delete at :149-152.) Alternative: stamp `visits` for every popped node and write the `-delta` note only when `visits.get(root) !== undefined` — costs a Map write per visited node per recount. Effort **S**. Magic-frame impact **M** (wrong-direction shadow disable — a visible quality regression, not a crash). Risk **low**.

### F3 — freeze queue has no flap hysteresis: minted-then-shown-then-reculled roots pay ~4 subtree walks per flap cycle

**Evidence:** `renderer.js:21016-21023` — queue dedup is `ud.sfHiddenFreezeQueued === true` only, cleared at unfreeze — a minted root re-queues freely. `:21029-21045` — minted flappers cost mint (freezeHiddenSubtreeMatrices = traverse + mark walk) + restore (2 walks, F1) per hide->show->hide cycle. `:21035-36` — queued-but-unminted flappers drop cheap on `visible === true`.

**Mechanism:** per node visited, mint+restore costs ~4 subtree visits vs ~1 compose-visit/frame saved while hidden — breakeven needs ~4+ consecutive hidden frames. A hull flapping on the cull boundary (combat churn at mid-distance, camera zoom bob) with a sub-4-frame hidden dwell pays the freeze machinery as pure overhead. Mitigating reality: the FIFO backlog self-protects unminted flappers — during a sustained storm they sit behind the 6/pass drain and drop on re-show without ever minting; the residual is only minted-flappers (hidden long enough to mint, then cycling). Two adjacent drain defects — the unbind's cleared `sfHiddenFreezeQueued` never consulted by the drain (post-unbind mints on doomed/pooled meshes) and O(n) `shift()` per stale entry — are already reported by the W102 popin lane's F2; not duplicated here.

**Fix sketch:** stamp `ud.sfHiddenFreezeLastShowSeq = this._viewSyncSeq` at the :23234-36 un-hide (and at enqueue time for re-culls); drain defers (does not drop) mints whose `viewSyncSeq - lastShowSeq < K` — K ~2-4 passes costs nothing on steady-hidden roots and filters boundary flap to zero mint churn. Effort **S**. Impact **L-M**. Risk **low**.

### F4 — every per-entity `noteShadowMeshRemoved`/`Added` call site passes no measured value -> `countShadowReceivers(root)` O(subtree) inline at remove/add seams

**Evidence:**
- `renderer.js:8132-8146` — `noteShadowMeshRemoved/Added(owner, root)` forwards with no `measuredReceivers`; `_noteShadowMeshRemoved(root, measured = null)` (:26965) falls through to `countShadowReceivers(root)` = `root.traverse` (shadowReceiverTally.js:8-24).
- Unmeasured call sites: entity:destroyed listener (:16580 — kill bursts), releaseRebuildBridge (:2155), reconcile paced legs (:12752, :15532, :21815), retire/rebuild (:21992, :22807), noteShadowMeshAdded on mounts (:22745, :22845), `shadowMeshNotes` hooks fired inside partsLibrary LOD subtree swaps/composition on presented frames (partsLibrary.js:9140-9193, 13670-13679, 14097-14210).
- The measured path already exists for sector boundaries: `disposeBoundaryObject` paces `disposeObjectSteps(boundary, boundaryDisposeMeasure)` and notes `record.boundary` with `boundaryDisposeMeasure.receivers` (:10449-10495). The `_despawnDisposeQueue` drain runs the same `disposeObject(m)` walk — but with no measure plumbed back.

**Mechanism:** every corpse/unbind pays one standalone subtree traverse at note time in addition to its queued paced dispose — for kill bursts, ~1 walk/corpse inside the presentation listener (bounded only by the ~8 listener runs/frame drain); for LOD subtree swaps, O(subtree) per attach/detach hook inside presented-frame composition. The receivers are counted twice anyway — the paced dispose walk already visits the same subtree for `measure.receivers`.

**Fix sketch:** carry `{ mesh, measure }` on `_despawnDisposeQueue`; the drain's `disposeObjectSteps`/`disposeObject(m, measure)` fills `measure.receivers` during the teardown it already does, then calls `noteRemoved(m, measure.receivers)` — the standalone walk vanishes; the only delta timing change is receivers hold in the count a pass or two longer (conservative-on direction — correct). For `shadowMeshNotes` subtree hooks, partsLibrary's composition passes could export the receivers count they already compute, or batch `markDirty` (one paced recount beats N subtree walks under churn). Effort **M**. Impact **M**. Risk **low-medium** (delta lands a pass later — boolean consumers unaffected; `preCountRoot`/`needsAtomicOut` callers keep their atomic path).

### F5 — `disposeObject` (sync) still lands atomically inside the two paced departure sweeps — per-mesh subtree teardown between legs, not inside the slice clock

**Evidence:** `renderer.js:12743-12764` — F9 leftover sweep: `disposeObject(mesh)` sync inside a loop that yields only every >=8 ms iteration boundary; `:15521-15540` — sector-departure sweep: same sync call inside `providerSliceDue()`-gated legs. `disposeObjectSteps` exists (:28250-28264) and the sector-boundary lane already wires it through the 4 ms + paced-ledger drive (:10449-10485).

**Mechanism:** sweeps pace BETWEEN meshes but each corpse teardown (traverse + per-node dispose calls, GL resource frees) lands atomically inside one leg — a fat packaged boundary or dense hull subtree still bricks the leg on a departure/cook seam that presents frames concurrently. Same iteration also calls `noteShadowMeshRemoved` unmeasured (F4).

**Fix sketch:** drive `disposeObjectSteps` on the sweep's own slice clock — mint the iterator per mesh, `.next()` under the 4 ms + paced-ledger bound, park it on the loop until done (disposeBoundaryObject's drive is the template). Effort **S-M**. Impact **L-M**. Risk **low**.

### F6 — `entityVisualCullRadius` cache misses pay O(subtree) `Box3.setFromObject` inside the per-visible-slot loop

**Evidence:** `renderer.js:23242-23247` (`refreshVisibleEntity` arg) and `:23299-23302` (lodRadius union) — `entityVisualCullRadius` runs per visible slot per pass. `visualCullRadius.js:60-93` — `drawnCullRadiusForMesh` memoizes on `{assetState, compositionId, lodLevel, childCount}`; a miss runs `_drawnCullBox.setFromObject(mesh)` — full-subtree world-bound measure. `:22-50` — `motionTravelPadFor` misses once per binding.

**Mechanism:** on the frame a LOD level flips, an authored composition commits, or direct-child count churns, the miss lands O(subtree) inside the visible loop — once per transition per root, then hot. Bounded, but it taxes exactly the churn frames the rest of the pass already pays.

**Fix sketch:** cache per `wholeShipLodActiveLevel` value (the two or three levels a root flips between are few — a Map keyed by level reuses prior measurements); or stamp a monotonic `visualBoundsEpoch` at mount/composition and keep one measured bound per epoch scaled by band. Effort **S-M**. Impact **L**. Risk **low**.

## Lane residuals (a)-(d)

- **(a) deferred-freeze queue starvation:** drain = <=6 mints/pass once per `syncEntityViews`. A >6-culls/pass storm grows the queue unboundedly but cannot regress below pre-W100 (unfrozen entries just keep paying the compose); the FIFO backlog self-protects flap-churn (queued-not-minted flappers drop on `visible === true`, costing only queue ops). The unprotected class is minted-flappers cycling mint->restore -> F3. Doomed-row freeze enqueues (:23139) are largely dead work (the mesh unbinds/disposes shortly after) — the unbind-time flag clear already keeps them cheap. `Array.shift()` O(n)/entry + unstopped stale drains are the popin lane's F2 — not duplicated.
- **(b) unfreeze re-mark cost -> F1.** Yes: the atomic O(scene) moved from cull to un-cull — the mint side queues but the restore side (2 walks incl. the W101 re-mark) runs inline at BOTH the visible loop and every unbind site.
- **(c) late-PBR stamp gap:** **benign, verified** — `openingSubmissionLateInstancedPbr` has exactly one consumer (`scripts/check-game-playable.mjs:679`, external probe, `|| []` guard); every in-repo write sits behind `_rendererLifecycle`-guarded `setTimeout` + `armedPlanForPbr` staleness guards. No same-task reader exists.
- **(d) remaining presented-frame whole-subtree walks, ranked by worst-case node count:**
  1. `unfreezeHiddenSubtreeMatrices` ~2x O(subtree) per re-shown/unbound-frozen root, inline uncapped (:23237, :21220) -> F1.
  2. `countShadowReceivers(root)` O(subtree) per unmeasured `noteRemoved`/`noteAdded` at destroy/unbind/reconcile/LOD-swap seams (:16580, :2155, :21815, :22807, :22845, partsLibrary `shadowMeshNotes`) -> F4.
  3. `disposeObject` sync O(subtree) per corpse inside the paced departure sweeps (:12749, :15529) -> F5.
  4. `drawnCullRadiusForMesh` / `motionTravelPadFor` cache misses: `Box3.setFromObject` O(subtree) inside the per-visible-slot loop -> F6.
  5. `bindEnvironmentToStandardMaterials` sync O(subtree) per touch leg (`:10719`) — inside paced admit loops, leg-bounded — acceptable.
  6. `applyProjectedDetailLod` O(subtree) only on LOD band flips (hlod.js:23-60) — band-gated by `_appliedLodLevel` + `lastDetailLevel` — acceptable.
  7. `scene.traverse` in `_syncShadowMapEnabled` (:27009) — else-branch reachable only when `_shadowReceiverTally` is absent; the tally is minted at init — effectively dead.
  8. Vendored `scene.updateMatrixWorld()` per presented frame (:27348) — needsUpdate-driven + `sfMatrixFrozen` elision — the baseline the freeze machinery defends; further shrink needs per-subtree dirty tracking (a design change, not a walk).

Also verified clean: `applyEntityMeshVisibility`/`syncResolvingMarker` O(1)/O(degree) per row; `updateLod`/`classifyEntityViewBand` band-gated; `applySnapshotPoseToMesh` carries the `matrixAutoUpdate === false -> updateMatrix()` hook (snapshotFence.js:287); hidden-loop sets `visible = false` then queues — no stale-pose hole (drain composes the just-written pose at mint :21039-40).
